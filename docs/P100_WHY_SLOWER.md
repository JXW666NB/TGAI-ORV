# P100 上 ORV 为什么慢 22%：证据与结论

> 2026-11-21　｜　数据：使用者回传的公平 2×2（`ORV_fair_2x2_P100.md`，两边 fp32、独立进程）

## 1. 先把差距分解（这一步决定一切）

| 注意力路径 | torch | ORV | ORV 相对 torch |
| --- | ---: | ---: | ---: |
| 低显存（各走自己的内核） | 1.76 s | 2.14 s | **慢 22%** |
| 物化（两边都走 cuBLAS GEMM + softmax） | 2.25 s | 2.32 s | **慢 3%** |

反过来看"自己的低显存路径比自己的物化路径快多少"：

| | 物化 | 低显存 | 低显存带来 |
| --- | ---: | ---: | ---: |
| torch | 2.25 s | 1.76 s | **−22%** |
| ORV | 2.32 s | 2.14 s | **−8%** |

**结论：差距几乎 100% 集中在"低显存注意力"这一条实现上。**

物化路径只差 3% 说明：**GEMM、FFN、RMSNorm、优化器这些主路径是打平的** ——
所以这不是"引擎整体慢"，也不是 CUDA / PyTorch 版本差异导致的（两边都调同一个 cuBLAS）。

## 2. 为什么它慢：Pascal 的 48 KB 共享内存上限，把我们逼成了**降级版内核**

这是我们自己代码里的注释写明的（`python/tgai_go/train/cuda.py`）：

```
L3512  （如 P100，48 KB）仍能用**常驻**内核而不是滑窗版
L3515  BC=32 -> 69,632（默认）；BC=11 -> 48,128（P100 可用）
L3525  2026-11-15：P100（sm_60，动态 smem 上限 48 KB）专用变体 attn_bwd_flash_w
L3534  默认 16：真机实测反向 82.8 -> 77.6 ms（-6%），且 45,056 B 仍装得进 48 KB
L3535  保持滑窗而非常驻，是因为 BC=32 的常驻版要 69,632 B，48 KB 卡装不下
L10085 if lim and _ATTN_FLASH_WIN_SMEM <= lim < _ATTN_FLASH_SMEM:
L10086     self._attn_set_dyn_smem("attn_bwd_flash_w", _ATTN_FLASH_WIN_SMEM)
```

翻译成人话：

* 我们的反向注意力内核正常版本要 **69,632 B 共享内存**（BC=32 常驻）；
* V100（96 KB）、4090（100 KB）都装得下 ⇒ 走常驻版，效率高；
  （A100 有 164 KB，从容量上当然也装得下 —— 但**我们没有 A100 的实测数据**，只作硬件容量说明）；
* **P100 动态共享内存上限 48 KB，装不下** ⇒ 退回 `attn_bwd_flash_w`：
  **BC 从 32 降到 16 + 滑窗分块**，每块算得更少、重算更多、寄存器/共享内存复用率更低；
* 更糟的是 `cuFuncSetAttribute(..., 45056)` 在 P100 上返回 `rc=1 invalid argument`
  （我们 L10097 的实测记录），所以只能用 40,448 B —— 余量更小。

而 PyTorch 的 memory-efficient attention（xFormers 血统的 cutlass 内核）**本来就是按小 smem
预算设计的算法**，在 sm_60 上仍能保持高效率 ⇒ 同一张卡上它 1.76 s，我们的降级版 2.14 s。

所以对你那个猜想，精确的回答是：

| 你的猜想 | 结论 |
| --- | --- |
| CUDA / PyT 版本差异 | ❌ 不是。物化路径两边都走 cuBLAS，只差 3%，说明底层库调用是一致的 |
| PyTorch 对 Pascal 有"特化" | ⚠️ 部分成立，但不是隐藏优化：它的**内存高效注意力内核**是手写的高质量实现，能在 48 KB 预算下工作；我们的是**受限降级版** |
| "P100 与 PyT 都是 2016 年产物" | 这个因素存在但不决定性：真正决定的是**共享内存容量**这条硬件约束，它把我们的内核挤到了低效分支 |

## 3. fp32 放大了这个问题

P100 没有 Tensor Core，fp32 是唯一高性能路径。注意力在 fp32 下本来就"算得少、搬得多"
（softmax 与中间量都是 fp32），此时**分块大小与重算次数**对性能的影响被放大：
BC 减半不只是并行度减半，重算比例也上去了。在有 TC 的卡上这部分会被 GEMM 的吞吐掩盖。

## 4. 能不能修（按性价比排序）

| # | 方案 | 预期 | 代价 | 评价 |
| --- | --- | --- | --- | --- |
| 1 | 给 sm_60 写"48 KB 预算专用"的常驻版：把 K/V 分 D-chunk 常驻、Q 走寄存器，目标仍是 BC=32 常驻 | 可能追回一半的 22% | 需 GPU 迭代调优，P100 属淘汰卡 | **ROI 低** |
| 2 | 用 cuBLAS 分块两段式注意力（GEMM+softmax+GEMM），限制 chunk 以控显存 | 最多到 torch-math 的 2.25 s —— **比现状 2.14 s 更差** | 低 | ❌ 不做 |
| 3 | 什么都不改，文档写清"P100 用 torch" | 0 | 0 | ✅ **当前选择** |
| 4 | 把精力放在有 TC 且**已实测**的卡（V100/3090/4090/5090）| 4090 1.47×、5090 1.59×、V100 1.42×(seq512) | — | ✅ **最划算** |

**建议：不为 P100 专门优化注意力内核。** 它是 2016 年的卡、无 Tensor Core、
我们的加速点全部失效；把同样的人力投到**已实测**的 V100 / 4090 / 5090 上回报高得多。

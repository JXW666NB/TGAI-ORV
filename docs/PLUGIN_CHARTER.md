# 插件系统宪法

> **性质**：**规范性**文档（normative）。写的是「必须 / 禁止」，不是「大概如何」。
> **效力**：任何改动插件系统的提交必须先改本文；与本文冲突的代码视为 bug，无论它能不能跑。
> **定位**：本文是**插件语言的地基** —— ORV 要按用户声明、针对不同后端
> **生成对应代码并编译到 C 端**，Python 只作兜底。§3 是这套设计的核心。
> **版本**：对应 0.9.48。
>
> 本套文档的分工（**只有一套说法**，不要另起）：
>
> | 文档 | 角色 |
> | --- | --- |
> | **本文 `PLUGIN_CHARTER.md`** | **规范**：不变量、承诺、兼容、安全、评审 |
> | `PLUGINS.md` | 算子插件**入门**（怎么写第一个插件、contrib 流程、打包） |
> | `PLUGIN_DISPATCH.md` | 能力模型与分派（实现说明 + 实测开销） |
> | `PLUGIN_NATIVE.md` | C 端四通道（JSON 清单 / C ABI / NVRTC / 组合式） |
> | `PLUGIN_DSL.md` | 插件语言（声明式内核 → 各后端代码生成），S1–S5 |

---

## 第 0 条 为什么要宪法

插件一旦对外承诺，别人的代码就会依赖它。**承诺被悄悄改掉，比功能缺失严重得多** ——
缺失是「用不了」，破坏是「昨天能跑今天算错」。

本文把承诺写死，目的是让后续开发**不能无意或有意地破坏契约**。

---

## 第 1 条 扩展的唯一通道

**1.1** 核心**不得**接受「仅此一次」的特例代码。新增能力一律走六条轴（§2）。

**1.2** 核心可以增长的条件只有三个之一：该能力**每一步都会走到**、或**决定数值语义**、
或**必须跨后端一致**。三者皆不满足的，必须做成插件。

**1.3** 一等公民白名单（改动需修宪）：Tensor / autograd / 分派 / 后端抽象 /
core ops（GEMM、elementwise、norm、softmax/SDPA、conv）/ 优化器基类与 AdamW /
AMP / checkpoint / DataLoader / 层与骨架的**基类** / **代码生成器（§3）**。

---

## 第 2 条 六条轴不得随意增减

| 轴 | 语义 | 注册后生效 |
| --- | --- | --- |
| ① op | 算子 | 立即 |
| ② backend | 计算后端 | 需 `activate()` |
| ③ optimizer | 优化器 | 立即 |
| ④ layer | 层 | 立即 |
| ⑤ arch | 模型骨架 | 立即（`T.build`） |
| ⑥ api | API 兼容层 | 需 `activate()` |

**2.1** 新增轴必须同时给出：注册 API、能力声明方式、跨后端语义、回退策略、测试门禁。

**2.2** 六条轴的名字与语义**不得**改变。要改就是新轴 + 弃用旧轴。

---

## 第 3 条 生成优先、Python 兜底（**本法的核心**）

这一条是插件语言的地基。**ORV 的插件应当被"编译"，而不是被"解释"。**

### 3.1 四档实现，必须从高到低优先

| 档 | 形态 | 谁把数学变成机器码 | 热路径 |
| --- | --- | --- | --- |
| **B1 声明式内核** | 用户写数学（逐元素/归约/广播） | **ORV 生成各后端源码并编译** | 原生 |
| **B2 后端源码** | 用户写 CUDA C / GLSL / 厂商语言 | 该后端工具链 | 原生 |
| **B3 预编译库** | 用户编译好的 `.so`/`.dll` | 用户自己的工具链 | 原生 |
| **P 组合式** | 用已有算子拼（Python） | 不需要 | Python 胶水 |

**3.1.1** 任何能用 B1 表达的自定义算子，**不得**只提供 P 档实现。
理由：P 档在热路径上是逐算子的 Python 调用，与 §4.1「热路径不得有 Python 逐元素」冲突。

**3.1.2** ORV **必须**为每个已支持后端提供 B1 的代码生成器。
缺生成器的后端，B1 插件在该后端上视为**不存在**（由 §3.3 处理），不得静默降级成 P 档。

### 3.2 声明式内核的契约

**3.2.1** 声明必须是**可静态分析**的受限形式：四则、白名单数学函数、输入元素、标量常量、
带 axis 的归约。**禁止**任意 Python 控制流（否则无法生成代码）。

**3.2.2** 注册时**必须**做静态检查并拒绝不合规声明：形状能否广播、类型是否一致、
是否用了非白名单原语、归约轴是否合法。**错在注册阶段报，不是编译出跑错的代码。**

**3.2.3** 生成结果**必须可审计**：`plugin.dump_code(name, backend)` 返回生成的确切源码。
用户不能对「ORV 到底生成了什么」一无所知 —— 这是信任的前提。【待实现，见 §9】

**3.2.4** 数值契约**按后端分别声明**。同一份声明在不同后端上允许有实现层面的舍入差异，
但必须落在登记时声明的容差内；超出即视为该后端不支持。

### 3.3 后端缺失时的行为

**3.3.1** 某后端缺该算子的任何实现时，分派**必须**抛错并说明缺什么
（缺哪个能力 / 计算能力不符 / dtype 不符 / 该后端无生成器）。

**3.3.2** 允许显式回退到 P 档，**但必须可见**：回退要能被统计到
（`plugin.stats()` 里能看到「本次运行有多少次走了兜底」）。
**禁止静默兜底** —— 用户必须能发现「我以为在跑内核，其实在跑 Python」。

**3.3.3** P 档兜底的性能不构成承诺。文档必须写明它与原生的量级差。

### 3.4 生成器是后端的一部分

**3.4.1** 接一个新后端 = 实现「IR → 本后端源码」的生成器 + §6.1 的后端接口。
**不得**要求修改插件声明（DSL 与后端解耦，这是"一份插件适配多后端"的唯一可行路径）。

**3.4.2** 生成器自身必须可测：给定 IR，产出的源码要能被该后端编译，
且编译后的结果与 CPU 参考在声明的容差内一致。

## 第 4 条 七条不变量（永不破坏）

### 4.1 热路径不得有 Python 逐元素
Python 只允许出现在图构建与调度。逐元素循环必须下沉到原生内核或组合算子。

### 4.2 分派开销 ≤ 1%
实测缓存命中约 627 ns。对单次 >100 µs 的算子可接受；对小算子（~15 µs）占 4.2%，
**必须用 `plugin.bind()` 静态绑定**。若某改动让开销超 1% 且无法用 bind 规避，
该改动必须回退，并在 `PLUGIN_DISPATCH.md` 记录实测数字。

### 4.3 能力不足必须报错，禁止静默退化
见 §3.3.1。错误要逐条说明每个候选缺什么。

### 4.4 非原生档必须为原生档提供回退
原生实现只保证在某后端正确。缺回退时，它在其它后端上必须表现为**不存在**。
由 `backend="*"` 通配 + 能力检查保证。

### 4.5 注册不得有副作用；有副作用的必须显式激活
②backend 与 ⑥api 会改变进程全局状态（切后端、改 `sys.modules`），**只能登记**。

### 4.6 出式更新的优化器不得用于共享存储参数
`p.data = p.data - ...` 会替换数组、断开视图，导致「权重更新了、视图还是旧值」。
只有声明 `works_inplace=True` 的优化器可用；由 `plugin.require_inplace()` 在
**注册/构造阶段**拒绝。这是实测过的真实故障模式（有测试故意执行出式赋值并断言共享失效）。

### 4.7 插件不得改变核心的数值语义
dtype 提升规则、累加顺序、边界行为（nan/inf/空张量）属于核心。插件**可以更快**，
不可以「更准」或「更省事地不同」。

## 第 5 条 对插件作者的六条承诺

**5.1** 已发布的注册接口在 1.0 之前**只增不改**。必须废弃时：先新增替代接口，
旧接口保留至少两个次版本并在文档标注弃用。

**5.2** 错误信息必须能指导修复：写清「哪个对象 / 什么条件 / 怎么修」。
这条由 AST 门禁测试强制（`tests/test_error_messages.py`），不是靠自觉。

**5.3** 命名空间不得被污染：条件化实现（带 `backend=`/`caps=`）只进分派表，
不进 `T.functional`；无条件实现才挂成属性。

**5.4** 重名不得静默覆盖：重复注册必须报错，覆盖要显式 `replace=True`。

**5.5** 插件之间互不干扰：一个插件的注册失败不得留下半成品状态。

**5.6** 可复现性：已加载插件清单带 sha256（`plugin.manifest()`），能复现「当时装了什么」。

---

## 第 6 条 后端接口与兼容

**6.1** 一个后端**必须**提供：设备初始化、缓冲分配/释放、H2D/D2H/D2D、内核编译、
内核启动、同步与事件计时、**能力声明 `caps`**、GEMM 等价、归约原语、**§3 的代码生成器**。

**6.2** 插件的 `PLUGIN` 声明必须含 `name` / `version` / `api_version`；
`api_version` **主版本**必须与引擎 `API_VERSION` 一致，否则拒绝加载。

**6.3** 声明了 `ops` 的必须真的注册了；声明了 `test_inputs` 的必须能被数值自检。
不允许「声明了但没实现」。

**6.4** 主版本只在**破坏第 4 条或第 5 条**时递增。加轴、加参数、加能力名不构成破坏。

---

## 第 7 条 安全与信任

**7.1 加载原生库 = 执行任意机器码。** 核心**不做**沙箱、**不**校验来源、**不**检查签名。
这一点必须在文档与 API 文档字符串里写明，不得含糊。

**7.2** ⑥api 轴会改 `sys.modules`，必须显式 `activate()`，且**不得覆盖真实现**
（例：`torch-compat` 检测到真 PyTorch 已加载时**拒绝安装**）。

**7.3** 核心不得为了方便而绕过 7.1 / 7.2（例如「自动加载同目录下的原生库」是禁止的）。

**7.4** 代码生成器产出的源码**不得**包含用户提供的任意字符串拼接
（防注入：用户声明只作为数据参与生成，不作为代码片段注入）。

---

## 第 8 条 宪法自身的修订

**8.1** 修宪要求：说明动机、列出受影响的插件作者、给出迁移路径、加对应测试。

**8.2 禁止的修宪方式**：
为了通过某个实现而放宽不变量；
把「未验证」改成「已验证」而不提供实测；
删除某条不变量而不说明替代保障；
为某个后端的特殊性开通用口子（应做成该后端的生成器/能力声明）。

**8.3** 本文（规范）与 `docs/DESIGN.md`（现状与路线）冲突时**以本文为准**。

## 第 10 条 评审清单（改插件系统时必须逐条过）

- [ ] 是否新增了轴？若是，§2.1 五项是否齐全？
- [ ] 是否让某能力**只能**用 P 档实现？（违反 §3.1.1）
- [ ] 某后端缺生成器时，行为是「报错/显式兜底」还是「静默降级」？（§3.3）
- [ ] 是否引入了新的静默退化路径？（§4.3）
- [ ] 是否让分派开销超过 1%？（§4.2，须有实测）
- [ ] 是否让某条不变量失去测试覆盖？（§4）
- [ ] 错误信息是否都带「修法」？（§5.2，AST 门禁会查）
- [ ] 是否引入注册期副作用？（§4.5）
- [ ] 生成的源码是否可审计、是否防注入？（§3.2.3 / §7.4）
- [ ] 文档是否同步？【未验证】是否被写成了「已支持」？

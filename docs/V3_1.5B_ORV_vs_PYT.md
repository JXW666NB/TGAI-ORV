# V3 1.5B：ORV vs PyTorch 真实训练步对拍

> 2026-11-13 起。**产线已停、110 个 TGAI 计划任务已禁用**，V100 32 GB 独占。
> 所有测试都是**完整训练步**（带优化器、真实更新权重、真实学习）。

## 0. 为什么是 V3 1.5B

V3 是 ORV 未来必须训的模型，1.5B 是能在 32 GB 卡上跑完整训练步的规模上限。
3B（V2.7）在 fp32 全状态下 44.7 GiB，**两家都装不下**（见 `V27_SFT_BENCH_2026-11-13.md`）。

## 2. PyTorch 基线（实测，`03_src/train_v3.py`）

命令（**别人的代码、别人的训练器**，不是我写的 harness）：

```powershell
C:\Python311\python.exe -X utf8 D:\TGAI-V3-1.5B\03_src\train_v3.py ^
  --preset save_v3_1_5b --data D:/TGAI-V3-1.5B/01_corpus/packed ^
  --out D:/orv_bench/v3_pyt_s512 --seq-len 512 --optim adamw --lr 3e-4 --stop-at-sec 90
```

| 项 | 值 |
| --- | --- |
| preset | `save_v3_1_5b` |
| 数据 | `01_corpus/packed`（`part-*.npz`，每片约 41 MB） |
| seq / batch / accum | 512 / 1 / 1 |
| 优化器 | AdamW，lr 3e-4，warmup 线性（1.5e-6 → 9e-6）|
| **梯度检查点** | `grad_ckpt=1`（脚本默认开） |
| ce_chunk | 0 |
| **峰值显存** | **29.20 GB**（脚本自报 SCAN metrics）|
| **平均吞吐** | **1319.6 tok/s** |
| 步数 / 用时 | 67 步 / 90 秒 ⇒ **1.34 s/步** |
| 产物 | `last.pt`（18.3 GB，含优化器状态）|

逐步（每 10 步一行）：

| step | loss | gnorm | tok/s |
| --- | --- | --- | --- |
| 10 | 11.6292 | 6.612 | 1417 |
| 20 | 11.6770 | 6.920 | 1465 |
| 30 | 11.6597 | 6.556 | 1487 |
| 40 | 11.6119 | 6.598 | 1499 |
| 50 | 11.5889 | 5.917 | 1502 |
| 60 | 11.6025 | 6.015 | 1506 |

**判读**：loss ≈ 11.6 在 96K 词表下仍偏高（`ln(96000) ≈ 11.47`），说明 67 步几乎没学到东西 ——
这是**从零/近零开始的真实训练**，短时间看不出下降属于正常。要看曲线要跑几千步。

**这就是 ORV 的靶子：峰值 29.20 GB、1319.6 tok/s、1.34 s/步。**
余量只剩 31.86 − 29.20 = **2.66 GB**，任何比 PyTorch 多占一点的做法都会直接 OOM。

### 2.1 第二个规模点：0.5B（同一口径，同为真实训练步）

| preset | 参数 | seq | 峰值显存 | 吞吐 | 每步 | 步数 / 时长 |
| --- | --- | --- | --- | --- | --- | --- |
| `save_0_5b` | 0.5B | 512 | **9.12 GB** | **3529.8 tok/s** | 0.59 s | 111 步 / 1.1 min |
| `save_v3_1_5b` | 1.5B | 512 | **29.20 GB** | **1319.6 tok/s** | 1.34 s | 67 步 / 90 s |

两点都是 `--optim adamw`、`grad_ckpt=1`、`ce_chunk=0`、B=1、真实语料、**权重真的被更新**。

**参数 ×3 时：显存 9.12 → 29.20 GB（×3.20），吞吐 3529.8 → 1319.6 tok/s（×0.374）。**
显存近似线性随参数量增长，吞吐近似反比 —— 这就是"显存决定生死"的量化版本：
按这个斜率外推，7B 全参 AdamW 在此卡上远不可行。

另注：`w10m` 预设（词级小模型）**不能**用这套 96K 词表数据，会 device-side assert（索引越界），
不要拿它做基线。

## 2. 踩过的坑（我自己的，不是模型的）

* 第一次跑 seq 512 报 OOM，我一度以为"1.5B 也装不下"。真相是**我上一轮的后台任务还占着约 10 GiB**
  （`--seq 1024/2048` 那个探针）。杀掉后同一配置 67 步跑通。
  **教训：开跑前必须核对 `nvidia-smi --query-compute-apps`，而不是只看总占用。**
* `--data` 必须指向含 `part-*.npz` 的目录（`packed`），`packed512` 里没有分片。

## 3. ORV 侧要做什么

V3 与 V2.7 不是一套架构，ORV 现在的 `V27Trainer` 服务不了它。缺口（已用 AST 盘点）：

| 组件 | 说明 | ORV 现状 |
| --- | --- | --- |
| `CompressedSparseAttention` | V3 招牌：压缩稀疏注意力（日志里 `CSA插桩: chunks=1344`）| ❌ 缺 |
| `SiTUGLUFFN` / SiTU 激活 | V3 的非线性 | ❌ 缺 |
| `GlobalAttention` | 全局注意力 | ⚠️ 有 SDPA 可复用 |
| `MoEv3` | MoE 路由 | ⚠️ 有 V2.7 版，需对齐 |
| `BlockAttnRes` | 块级注意力残差 | ⚠️ 引擎侧有，训练侧要对齐 |
| `optim_v3.py` | AdamW / Muon 双优化器 | ❌ 缺（ORV 只有 AdamW/Fp16MomAdamW）|

移植顺序：**算子 → 层（逐层比 logits）→ 整模型 → 完整训练步对拍**。

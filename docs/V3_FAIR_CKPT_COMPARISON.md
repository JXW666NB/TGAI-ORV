# 同口径对拍：两侧都开梯度检查点（2026-11-13）

> 修正上一版的关键缺陷：先前 PyTorch 侧**没有开检查点**，与 ORV 的检查点版不同口径，
> 比出来的差异不算数。本页是修正后的第一份**真正同口径**数据。

## 0. 口径拉平了什么

| 项 | PyTorch | ORV |
| --- | --- | --- |
| 优化器 | AdamW | AdamW |
| 梯度检查点 | `model.enable_gradient_checkpointing(True)` | 手写层级重算 |
| 触发条件 | 必须 `forward(ids, targets=ids)`（模型内部平移）| 每层 `y.backward(g)` |
| 规模 | d=512 / 8 层 / 8 专家 / seq=2048 / B=1 / vocab=4096 | 同 |
| 显存指标 | `torch.cuda.max_memory_allocated()` | `pool_stats().peak_live_bytes` |
| 预热 | 丢弃第 0 步计时 | 同 |

## 1. 结果（seq = 2048）

| 指标 | PyTorch | ORV | ORV / PyT |
| --- | --- | --- | --- |
| **峰值显存** | **4645 MiB** | **16582 MiB** | **3.6× 更费** |
| 每步耗时（稳态）| **0.33 s** | 1.55 s | 4.7× 慢 |
| 吞吐 | **4740 tok/s** | 868 tok/s | 0.18× |

## 2. 检查点各自带来了什么（这才是关键）

| 侧 | 无检查点 | 有检查点 | 变化 |
| --- | --- | --- | --- |
| PyTorch | 6516 MiB / 0.32 s | **4645 MiB / 0.33 s** | **−29% 显存，速度不变** |
| ORV（我的实现）| 11979 MiB / 1.53 s | 16582 MiB / 1.55 s | +38%（**反效果**）|

**PyTorch 的检查点为什么又省又不掉速**：它省的是层间激活，而它**层内的注意力本来就不物化**
（V100 上走 mem-efficient SDPA）。两层机制叠加才有这个效果。

**ORV 为什么不行**：检查点只省层间；层内 `H·S²` 的分数矩阵（S=2048、8 头 ⇒ 134 MB/层）
照样活到反向。而我这版编排还多花了显存（16.6 GB > 基线 12.0 GB），原因尚未定位。

## 3. 旁证：引擎无泄漏（已排除一个假设）

单层重复 `fwd/backward` 8 次，`live_bytes` **每轮恒定 1608 MiB**，不增长 ⇒ 图能正常释放。
同时给出：**一层（attention + MoE，S=2048）≈ 1.6 GB 活跃**；8 层不检查点 ≈ 12.8 GB，
与实测基线 11.98 GB 吻合 ⇒ **激活是主因**，不是权重（权重+梯度+Adam ≈ 3.8 GB）。

## 4. 结论

**ORV 在 V3 的长序列训练上落后 3.6× 显存、4.7× 速度**，症结是注意力物化 `S²`。
PyTorch 在 V100 上没有 flash，用的是 mem-efficient（分块、不物化）——ORV 缺的正是这个内核。

## 4.1 补记（同日稍后）：块化注意力接入后的同口径数据

把按 PyTorch 内核算法实现的块化注意力（`--flash`）接进训练步后：

| seq | **ORV flash + 检查点**（n_q=4）| PyT（开检查点）| 显存比 | ORV 步时 | PyT 步时 | 速度比 |
| --- | --- | --- | --- | --- | --- | --- |
| 1024 | **3,043 MiB** | 4,563 MiB | **0.67×** ✅ | 0.93 s | 0.38 s | **2.4×** |
| 2048 | **3,153 MiB** | 4,645 MiB | **0.68×** ✅ | 2.08 s | 0.33 s | **6.3×** |

### ⚠️ 口径修正（重要）

早先 ORV 一直用 `--n_q 8` 跑，而 PyT 侧是 `n_heads=4`（`tools/v3_pyt_train.py:50`）——
**两侧注意力头数不同，ORV 多一倍注意力参数与计算**。上表已改为 `n_q=4` 对齐后的实测。

**仍存的一处不对称（必须随数字一起说）**：PyT 的配置是
`n_activated=1, n_shared_experts=1`，即 **top_k=1 + 1 个共享专家**；
ORV 目前 **只有 top_k=1，没有共享专家**。

| 项 | 参数 | 显存影响 |
| --- | --- | --- |
| 共享专家（每层 `2·d·d_ff + d_ff·d`）| 3.15 M/层 × 8 层 = 25.2 M | 权重 96 + 梯度 96 + Adam 192 = **约 384 MiB** |

⇒ 若 ORV 补上共享专家，seq2048 约为 **3,153 + 384 = 3,537 MiB**，对 PyT 是 **0.76×** —— 仍在红线内，
但**本文所有"0.6x×"的数字都应理解为"缺共享专家时"的下界**。

**块大小是速度的主开关**（同一算子、S=2048、前向+反向）：
64/64 = 1.140 s，128/128 = 0.342 s，256/256 = 0.181 s，512/512 = **0.149 s**（7.7×），
显存 4~40 MiB 几乎不变。此前只试过把块变小（32/32 更慢），从未试过变大 ——
代价在**启动次数** ∝(S/cq)·(S/ck)，不在算术。

**2048→4096 的增量**：ORV **+163 MiB**，PyT +171 MiB —— **斜率已经同级**，
说明 ORV 的显存曲线不再是"结构性劣势"，而是与 PyT 同一个量级（都受一层重计算工作集支配）。
1. **显存已在红线内（≤1.0），三档全部达标**，最差 0.69×。
2. **曲线斜率已大幅收窄**：ORV 从 512→2048 只涨 **+287 MiB**（改前是 +2,506，比值 2.85 的超线性）；
   PyT 涨 +124。剩余斜率来自"**一层重计算的工作集**"（实测 113 MiB/层 @2048），
   而 PyT 的一层更小 —— 它的 norm/激活是单内核、注意力不留掩码。
3. **速度是纯工程差距**：块化注意力仍是 Python 循环发上千个小 kernel（每次启动 ~10 µs）。

## 4.6 检查点为什么之前失败、现在为什么成功

失败两次的根因是引擎的两个开关都只关了一半：

| 开关 | 修复前 | 修复后 |
| --- | --- | --- |
| `requires_grad` | 只信调用方传值 | 遵循 `_GRAD_ENABLED` |
| `_parents` | 无条件记录 | grad 关闭时不记 |
| **`_backward` 闭包** | **无条件保存**（→ 保留一个输出就钉住整条输入链）| grad 关闭时丢弃 |

第三条是最隐蔽的：`out._backward = bw` 里的 `bw` 捕获了输入张量，于是"只留层边界"这个前提根本不成立 ——
层边界张量本身也拖着整层激活。最小复现：no_grad 下保留 200 个 131 KB 输出，live 涨 **279.8 MB**
（每个拖 ~1.4 MB 祖先）；修复后只涨 25.5 MB（正好等于保留量）。

**曲线的形状比单点更重要**：PyT 几乎平坦（4,521 → 4,563 → 4,645，seq ×4 仅 +2.7%），
而 ORV flash 仍随 seq 上升（3,269 → 3,920 → 5,820，×1.78）。
⇒ ORV 在短/中序列**低于** PyT，在最长序列落后，且落后的是**斜率**而不是常数偏移。

显存倍数从 **2.58× 收窄到 1.25×**（seq2048），是自对拍以来该比值首次下降；
速度代价则很大（Python 每层上千次 kernel 启动，对照 PyT 一次融合启动）。

⇒ 现在的取舍很明确：**显存敏感就用 flash；速度也要就得写 CUDA 内核**。
数值保证：前向 1.2e-07、反向八组组合 1e-9~1e-8（`tools/probe_flash_op.py` 可复验）。

## 4.2 剩余差距的分解（flash，seq2048，单层对照组）

为定位 1.25× 的来源，固定 1 层、只改一个变量：

| 配置 | 峰值活跃 | 归因 |
| --- | --- | --- |
| E=8, seq=2048 | **2,841 MiB** | 基准 |
| E=1, seq=2048 | 1,973 MiB | 专家数 → **≈868 MiB** |
| E=8, seq=512 | 810 MiB | 序列长度 → **≈2,031 MiB** |
| 8 层（E=8, seq=2048）| 5,820 MiB | 层数 → ≈425 MiB/层 |

**结论：固定开销的主因是序列长度，不是层数**。1 层就要 2.8 GB，说明每层为 2048 个 token
分配的一批 `N×d` / `N×d_ff` 级缓冲在自动微分里**全部活到反向**。
⇒ 优化方向从"层间检查点"改为"**MoE 分派的逐专家流式**（不 cat 全部专家输出、减少中间量）"。

对照：PyT 8 层 4,645 MiB，二者差 1,175 MiB ≈ 2.4 个 ORV 层开销 —— 差距在"每层开销"，不在层数。

## 4.3 那批内存是"留存激活"（1 层、seq2048、E=8 实测）

| 阶段 | 峰值活跃 |
| --- | --- |
| **只前向**（`no_grad`，含 CE）| **1,142 MiB** |
| 前向 + 反向 | 3,891 MiB |
| **反向额外** | **+2,748 MiB** |

⇒ 前向本身很省；2.7 GB 是**自动微分为反向留存的中间量**，不是作业缓冲、也不是 MoE 的 `cat`。

**这也修正了 4.0 节对"层级检查点失败"的判断**：当时实测 +38% 并只写"原因未定位"。
现在可确认——**可省的正是这 2,748 MiB，检查点方向是对的，那次是实现 bug**（我在反向循环里
每层 `leaf()` 重建整层图并同时持有旧引用），不是机制无效。

### ⚠️ 最终结论（2026-11-13 晚，追溯更正）

上面这段仍然是错的。真正的原因是**引擎缺陷**：

```
PyTorch C++（torch/csrc/autograd/VariableTypeUtils.h:49）：
    if (!requires_grad || !GradMode::is_enabled()) { ... return false; }
ORV（修复前）：
    obj.requires_grad = bool(requires_grad)      # 完全没看 _GRAD_ENABLED
```

⇒ `with T.no_grad()` 只是清了一个没人查的标志，**图照样建、激活照样留**。
实测（2 层、E=8、seq2048）：`no_grad` 前向增量 **+1,978 MiB**；补上那行后 **+54 MiB**（36×）。

修复提交 `467a4f2`。这解释了两次检查点失败——不是机制错，也不是我的编排错，是开关无效。
修复后检查点不再爆炸，但本规模下不划算：8 层 seq2048 峰值 **6,024 MiB**（79 s/步）
vs 普通路径 **5,820 MiB**（11 s/步），因为可省的激活只有约 2 GB，多一次前向的时间代价更大。

**更大价值在别处**：修复前所有 `no_grad` 路径（推理、eval、采样）都在白占内存。

## 4.5 最后一处定位：`tanh` 没有内核，是组合出来的（每次分配 11×）

逐算子、每次清池单测（N=2048、d=512、d_ff=2048）：

| 算子 | 输入 | 峰值 |
| --- | --- | --- |
| 空操作 | 16 MB | 4 MiB |
| `x @ w1.T` | 512→2048 | 12 MiB ✅ |
| **`big.tanh()`** | **16 MB** | **176 MiB ❌ 11×** |
| `big * big` / 反向 matmul | 16 MB | ~0 |

原因（`train/__init__.py:1821`）：

```python
def tanh(self):
    """组合式（2*sigmoid(2x)-1）⇒ CPU/CUDA 都能用。"""
    return _O.tanh(self)
```

`cuda.py` 里**没有任何 tanh 内核**。`situ_glu_orv` 一次调用有 **3 个 tanh**
⇒ 3 × 176 ≈ **528 MiB**，正是该算子 756 MiB 的主体，也是 MoE 每层 450 MiB 的来源。

**结论：补一个融合 `tanh` 内核（前向一次分配，反向用 `1−t²`）是进 1.0 红线最直接的一步。**
PyTorch 的 `tanh` 就是单个融合内核；与"速度差 34× 需要融合内核"是同一类工作。

下一步：按 `V27Trainer` 的既有模式（`forward_all` 不建图 + 逐层重算）重做，而非自创。
验收：1 层 `peak_live` 从 3,891 降到接近 1,142 + 参数梯度；8 层随之从 5,820 下降。

## 4.4 剩余显存的大头在 **MoE 分派**（8 层、seq2048、flash 实测）

| 专家数 | 峰值活跃 | 说明 |
| --- | --- | --- |
| E=8 | 5,820 MiB | 基准 |
| **E=1** | **2,949 MiB** | 比 PyT 的 4,645 还低（**0.63×**）|
| 差 | **2,871 MiB** | 约占总量的 **一半** |

### ⚠️ 勘误（同日）：这 2,871 MiB 是**参数与优化器状态**，不是分派的中间量

按参数核算：

```
每专家 W1+W2+W3 = 2048×512 ×2 + 512×2048 ≈ 3.1M 参数
E=8：3.1M × 8 × 8 层 ≈ 201M 参数；×4 份（权重+梯度+Adam m/v）×4B ≈ 3.2 GB
E=1：≈25M 参数 ⇒ ≈0.4 GB
差 ≈ 2.8 GB ≈ 实测 2,871 MiB   ✅ 对上了
```

⇒ **E=8 与 E=1 的差是专家权重，砍不掉**；而且 **PyTorch 同样 E=8、同样有这笔开销**，
所以这一项**不是** ORV 相对 PyT 的差距来源。

真正的差距（对齐参数口径后）：

| 项 | ORV | PyT |
| --- | --- | --- |
| 峰值 | 5,820 MiB | 4,645 MiB |
| 参数+梯度+Adam（E=8, 8 层）| ≈3,840 MiB | ≈3,840 MiB |
| **其余（激活/中间量）** | **≈1,980 MiB** | **≈805 MiB** |

⇒ 要进 1.0 红线，目标是压掉约 **1.2 GB 的激活/中间量**（约一半即可），
位置在 **MoE 分派的激活与 norm/残差**，不是注意力（已被块化压过），更不是参数。

优化顺序（按收益）：

1. **块内 online-softmax + 反向重算的注意力**（唯一能同时省显存与时间）
2. 修我这版检查点的编排问题（它现在比不开还费）
3. 修完再补 CSA / top_k=2 / BlockAttnRes，把"架构差异"从结果里剔除

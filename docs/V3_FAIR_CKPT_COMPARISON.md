# 同口径对拍：两侧都开梯度检查点（2026-11-13）

> 修正上一版的关键缺陷：先前 PyTorch 侧**没有开检查点**，与 ORV 的检查点版不同口径，
> 比出来的差异不算数。本页是修正后的第一份**真正同口径**数据。

## 0. 口径拉平了什么

| 项 | PyTorch | ORV |
| --- | --- | --- |
| 优化器 | AdamW | AdamW |
| 梯度检查点 | `model.enable_gradient_checkpointing(True)` | 手写层级重算 |
| 触发条件 | 必须 `forward(ids, targets=ids)`（模型内部平移）| 每层 `y.backward(g)` |
| 规模 | d=512 / 8 层 / 8 专家 / seq=2048 / B=1 / vocab=4096 | 同 |
| 显存指标 | `torch.cuda.max_memory_allocated()` | `pool_stats().peak_live_bytes` |
| 预热 | 丢弃第 0 步计时 | 同 |

## 1. 结果（seq = 2048）

| 指标 | PyTorch | ORV | ORV / PyT |
| --- | --- | --- | --- |
| **峰值显存** | **4645 MiB** | **16582 MiB** | **3.6× 更费** |
| 每步耗时（稳态）| **0.33 s** | 1.55 s | 4.7× 慢 |
| 吞吐 | **4740 tok/s** | 868 tok/s | 0.18× |

## 2. 检查点各自带来了什么（这才是关键）

| 侧 | 无检查点 | 有检查点 | 变化 |
| --- | --- | --- | --- |
| PyTorch | 6516 MiB / 0.32 s | **4645 MiB / 0.33 s** | **−29% 显存，速度不变** |
| ORV（我的实现）| 11979 MiB / 1.53 s | 16582 MiB / 1.55 s | +38%（**反效果**）|

**PyTorch 的检查点为什么又省又不掉速**：它省的是层间激活，而它**层内的注意力本来就不物化**
（V100 上走 mem-efficient SDPA）。两层机制叠加才有这个效果。

**ORV 为什么不行**：检查点只省层间；层内 `H·S²` 的分数矩阵（S=2048、8 头 ⇒ 134 MB/层）
照样活到反向。而我这版编排还多花了显存（16.6 GB > 基线 12.0 GB），原因尚未定位。

## 3. 旁证：引擎无泄漏（已排除一个假设）

单层重复 `fwd/backward` 8 次，`live_bytes` **每轮恒定 1608 MiB**，不增长 ⇒ 图能正常释放。
同时给出：**一层（attention + MoE，S=2048）≈ 1.6 GB 活跃**；8 层不检查点 ≈ 12.8 GB，
与实测基线 11.98 GB 吻合 ⇒ **激活是主因**，不是权重（权重+梯度+Adam ≈ 3.8 GB）。

## 4. 结论

**ORV 在 V3 的长序列训练上落后 3.6× 显存、4.7× 速度**，症结是注意力物化 `S²`。
PyTorch 在 V100 上没有 flash，用的是 mem-efficient（分块、不物化）——ORV 缺的正是这个内核。

## 4.1 补记（同日稍后）：块化注意力接入后的同口径数据

把按 PyTorch 内核算法实现的块化注意力（`--flash`）接进训练步后：

| seq | ORV 物化 | **ORV flash** | PyT（开检查点）| flash/PyT 显存 | flash/PyT 速度 |
| --- | --- | --- | --- | --- | --- |
| 1024 | 5,276 MiB / 0.77 s | **3,920 MiB / 3.35 s** | **4,563 MiB / 0.38 s** | **0.86×** ✅ | 8.8× 慢 |
| 2048 | 11,979 MiB / 1.53 s | **5,820 MiB / 11.35 s** | **4,645 MiB / 0.33 s** | **1.25×** | 34× 慢 |

显存倍数从 **2.58× 收窄到 1.25×**（seq2048），是自对拍以来该比值首次下降；
速度代价则很大（Python 每层上千次 kernel 启动，对照 PyT 一次融合启动）。

⇒ 现在的取舍很明确：**显存敏感就用 flash；速度也要就得写 CUDA 内核**。
数值保证：前向 1.2e-07、反向八组组合 1e-9~1e-8（`tools/probe_flash_op.py` 可复验）。

## 4.2 剩余差距的分解（flash，seq2048，单层对照组）

为定位 1.25× 的来源，固定 1 层、只改一个变量：

| 配置 | 峰值活跃 | 归因 |
| --- | --- | --- |
| E=8, seq=2048 | **2,841 MiB** | 基准 |
| E=1, seq=2048 | 1,973 MiB | 专家数 → **≈868 MiB** |
| E=8, seq=512 | 810 MiB | 序列长度 → **≈2,031 MiB** |
| 8 层（E=8, seq=2048）| 5,820 MiB | 层数 → ≈425 MiB/层 |

**结论：固定开销的主因是序列长度，不是层数**。1 层就要 2.8 GB，说明每层为 2048 个 token
分配的一批 `N×d` / `N×d_ff` 级缓冲在自动微分里**全部活到反向**。
⇒ 优化方向从"层间检查点"改为"**MoE 分派的逐专家流式**（不 cat 全部专家输出、减少中间量）"。

对照：PyT 8 层 4,645 MiB，二者差 1,175 MiB ≈ 2.4 个 ORV 层开销 —— 差距在"每层开销"，不在层数。

## 4.3 那批内存是"留存激活"（1 层、seq2048、E=8 实测）

| 阶段 | 峰值活跃 |
| --- | --- |
| **只前向**（`no_grad`，含 CE）| **1,142 MiB** |
| 前向 + 反向 | 3,891 MiB |
| **反向额外** | **+2,748 MiB** |

⇒ 前向本身很省；2.7 GB 是**自动微分为反向留存的中间量**，不是作业缓冲、也不是 MoE 的 `cat`。

**这也修正了 4.0 节对"层级检查点失败"的判断**：当时实测 +38% 并只写"原因未定位"。
现在可确认——**可省的正是这 2,748 MiB，检查点方向是对的，那次是实现 bug**（我在反向循环里
每层 `leaf()` 重建整层图并同时持有旧引用），不是机制无效。

下一步：按 `V27Trainer` 的既有模式（`forward_all` 不建图 + 逐层重算）重做，而非自创。
验收：1 层 `peak_live` 从 3,891 降到接近 1,142 + 参数梯度；8 层随之从 5,820 下降。

优化顺序（按收益）：

1. **块内 online-softmax + 反向重算的注意力**（唯一能同时省显存与时间）
2. 修我这版检查点的编排问题（它现在比不开还费）
3. 修完再补 CSA / top_k=2 / BlockAttnRes，把"架构差异"从结果里剔除

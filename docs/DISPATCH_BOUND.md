# ORV 是「派发受限」，不是「算力受限」

> 实测日期 2026-11-20 / RTX 4090 24 GB（sm_89, driver 550.107）/ ORV 1.0.8→1.0.9 / 独立复验
  
## 1. 一句话

**一步 4038 次内核发射，每次摊到约 59 µs 的主机侧 Python/ctypes/池分配成本，
主线程 CPU 时间 = 墙钟的 100.0%** ⇒ 主机算不过来，GPU 有 58~70% 的时间没有内核可跑。

纯 `cuLaunchKernel`（预建参数模板）只要 **4.39 µs**，所以"发射"本身不是问题 ——
**是每次算子调用外面那层 Python 记账**。

## 2. 证据（4090 / 12 层 / E=4 / d_ff=3328 / vocab 96000 / seq512 / batch1 / `--opt int8gpu`）

### 2.1 分层微基准（各 2 万次循环取均值）

| 层 | µs/次 | ×4038 折算 |
| --- | --- | --- |
| A 纯 `cuLaunchKernel`（预建 args） | **4.39** | 17.7 ms ← 驱动地板 |
| B `rt.launch`（预建 args，含 `_activate`/`_fn`/模板写值） | 6.49 | 26.2 ms |
| C `rt.launch`（真实调用点形态） | 7.35 | 29.7 ms |
| D `rt.empty` 池**命中** | 6.48 | 29.4 ms（4539 次） |
| E `rt.add_` 完整算子 | 10.79 | 7.4 ms |
| F `rt.mul_bcast` 完整算子 | **41.4** | 23.8 ms（576 次） |
| G `rt.d2h(标量)`（唯一隐式同步） | 13.4 | 仅 26 次/步 |
| H `rt.sync()` | 0.96 | 仅 2 次/步 |

### 2.2 否证「同步导致空闲」

* `cudaDeviceSynchronize` **2 次/步**、标量 D2H **26 次/步**、`empty_cache` **0 次/步**
* 主线程 CPU 时间 / 墙钟 = **100.0%**（关掉 vram 采样线程后逐位相等）
* ⇒ 消除同步的收益上限 ≈ **0.35 ms/步（0.15%）**

### 2.3 每步分解（稳态 12 步）

| 项 | 次数/步 | 耗时 |
| --- | --- | --- |
| `rt.launch` | 4038 | ~48 ms |
| `rt._alloc` | 4539 | ~25 ms |
| `rt.free` | 4539 | ~14.5 ms |
| Tensor/autograd 对象 + 广播形状计算 | — | ~85 ms |
| **GPU 真实计算** | | **~82 ms（32%）** |

### 2.4 层数标度（证明低效是按层摊的，不是一个固定开销）

| layers | params | step |
| --- | --- | --- |
| 3 | 358.6M | 0.0780 s |
| 6 | 522.0M | 0.1361 s |
| 12 | 848.6M | 0.2287 s |

拟合 `t(L) ≈ 27.6 ms + 16.8 ms × L`；另一路独立测量 fwd 95.0 + bwd 109.6 = **17.05 ms/层**，
固定项 clip+opt+zero_grad = **33.4 ms** —— 两条路对得上。

## 3. 为什么"换更快的卡反而更慢"

| 卡 | fp32 算力 | 理想 step | 实测 step | 差 |
| --- | --- | --- | --- | --- |
| V100 | 15.7 TFLOPS | ~100 ms | 259 ms | 2.5× |
| 4090 | 80.3 TFLOPS（TF32）| 20~30 ms | 229 ms | 8~10× |

主机侧那 ~150 ms 是**两张卡都一样**的。V100 用慢算力把它遮住，4090 遮不住。
⇒ 任何"让 GPU 算得更快"的手段（含 fp16 AMP）在新卡上都几乎无效，甚至变负。

### 3.1 附带结论：fp16 AMP 在 4090 上对**两个框架都是负优化**

| 设置 | 中位（seq512, 20 步, 交替 3 轮） |
| --- | --- |
| ORV `--amp off` | **0.2114 s** |
| ORV `--amp gemm` | 0.2989 s（+41%） |
| PyT 无 `--amp` | **0.3030 s** |
| PyT `--amp` | 0.3385 s（+12%） |

原因：AMP 多出 **995 次 `cast_f32_to_f16` 发射/步**（+25% 发射数），而 4090 上
fp16 只比 TF32 fp32 快 2×（V100 上是 8×），省下的算力抵不过多付的发射。

## 6. 长序列是当前最痛的地方

两侧同开梯度检查点（10 步）：

| seq | ORV（int8gpu+ckpt） | PyT（no-amp+ckpt） | 结论 |
| --- | --- | --- | --- |
| 1024 | **0.334 s** / 14.2 GiB | 0.497 s | ORV 快 1.49× |
| 2048 | **1.080 s** / 22.1 GiB | **0.598 s** | **ORV 慢 1.81×** |

标度：seq 翻倍时 **ORV 慢 3.2×**，PyT 只慢 1.2×。

**机理**：梯度检查点让每层前向**全部重算一遍** ⇒ 发射数近似翻倍 ⇒ 主机时间翻倍。
这是同一个根因的放大版，不是另一个 bug。**所以第 5 节的 1/2/3 项同时是长序列的解。**

## 8. 这次踩过的三个方法论坑（都别再犯）

1. **把冷启动算进稳态**：`_alloc` 平均 4862 次/步里有 3394 次发生在构建期。
   正确做法是**按步快照**（挂 `print` 钩子），否则会得出"分配器占 48%"的错误结论。
2. **单次对跑**：基线自身在 0.2298~0.2391 之间漂 ±2%，改前一次改后一次必然给出偏差数字。
   必须**交替多轮 + 中位数 + 双方极差**。
3. **把"kernel 时间"当"GPU 时间"**：用同步包裹小内核会把它膨胀 1.59×，
   之前据此得出过"transpose2d 占 76 ms"的错误结论。要用 CUDA event，且先确认 GPU 没被饿着 ——
   **GPU 饿着的时候，任何单算子计时都不可信**。

# ORV 总体设计（长期维护基线）

> 版本：对应 0.9.46。本文是**长期基线文档**，不是发布说明。
> 改动架构前先改本文，再改代码 —— 否则设计会在几十轮之后漂移得没人认得。
>
> 全文区分三类陈述，不许混：
> **【已实测】** 有可复现命令与数字；**【已实现未跨硬件验证】** 代码在、单机能跑；
> **【设计】** 只有设计，没有可用实现。

---

## 1. 定位

| 项 | 内容 |
| --- | --- |
| 是什么 | 纯 Python 写的自动微分 + 训练引擎，直接走 CUDA Driver API + cuBLAS + NVRTC，**不依赖 PyTorch** |
| 包名 | `tgai-orv`（PyPI）；`tgai_go.train`（import 路径） |
| 目标 | 替代 PyTorch 做**单卡（未来多卡）**训练，并在此之上提供可扩展的插件体系 |
| 差异化 | ① 3B MoE 全参训练在 32 GB 单卡上**能跑完**（PyTorch 在 1.997B 就 OOM）；② 插件系统；③ 未来 Vulkan 后端（主战场） |
| 不做什么 | 不做推理引擎、不做训练框架全家桶、不做模型动物园（这些都交给插件） |

### 1.1 已实测的能力边界（不要外推）

| 项 | 数字 | 说明 |
| --- | --- | --- |
| 3B MoE 全参一步（AdamW fp16 动量 + 逐层更新） | **709 ms / 峰值 24.78 GiB** | V100 32 GB，2.97B 参数 |
| 同上，Muon | 18.93 GiB 但 **62.9 s/步**（`ns_fast` 后 35.0 s） | 见 §7.3，3B 上不可用 |
| PyTorch 对照（28 层 MoE 1.997B，T=512，fp32 + 梯度检查点 + 真 AdamW） | fwd+bwd 峰值 14.96 GiB 后 **OOM（31.40 GiB 已分配）** | 这是 ORV 的核心卖点，是量出来的 |
| 速度对照（8 层，独立进程，同数学） | ORV **1.11–1.16×** 于 PyT | 但 ORV **显存占用更高**（11.36–14.19 vs 10.64–10.65 GiB） |
| 数值一致性 | 8 步 loss 1.44e-07；Qwen2.5-0.5B vs HF 6.29e-06；多项 0.00e+00 | 见 §8 |

### 1.2 验证纪律（最重要的一条）

> **"跑通了"、"看起来对"、"理论上应该" —— 三者都不算完成。**
> 只有【已实测】可以对外说"是"。拿不到硬件的项必须标【未验证】，不许暗示。

这条带来的具体后果（都必须写进对外文档）：
- A100/H100 的 bf16 加速：【未验证】，本机只有 V100。
- 7B 以上热门模型微调：【未验证】。
- 多卡 / DDP / FSDP：【未验证】，且当前无机器。
- Vulkan 后端：【未实现】。
- `ParameterGroup` 在 CUDA 上：【未实现】（原因见 §5.4）。

## 2. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│ 用户面：T.tensor / T.nn.* / T.optim.* / T.build(...)     │  ← 与 PyT 用法一致
├─────────────────────────────────────────────────────────┤
│ 插件面：plugin.op / .backend / .optimizer / .layer       │  ← 六条轴
│          .arch / .api / .kernel(DSL)                     │
├─────────────────────────────────────────────────────────┤
│ 分派层：dispatch  (op, backend, dtype, arch, caps)       │  ← 单次查表 + 缓存
│         能力模型 caps + 通配回退 backend="*"              │
├─────────────────────────────────────────────────────────┤
│ 算子层：核心算子（组合式 / numpy 反向 / 原生）             │
├─────────────────────────────────────────────────────────┤
│ 数据层：Tensor / autograd / Parameter / ParameterGroup   │
├─────────────────────────────────────────────────────────┤
│ 后端层：CUDA（已有） │ CPU │ Vulkan（待建） │ 国产卡（待接）│
└─────────────────────────────────────────────────────────┘
```

### 2.1 分层的硬约束

1. **热路径零 Python 逐元素**：Python 只做图构建与调度；计算必须在原生内核里。
2. **分派开销 ≤ 1%**：实测缓存命中 627 ns。对大 GEMM 占 0.16%（可接受），
   对小 elemwise（~15 µs）占 4.2%（超标）⇒ **小算子必须 `plugin.bind()` 静态绑定**。
3. **能力不足必须报错**，不许静默退化。
4. **后端可增减**：没有某个后端时，import 不能失败，应在用到时报清晰的错。

## 3. 插件系统（本项目最大的差异化）

### 3.1 六条轴

| 轴 | 注册 API | 副作用 | 生效时机 |
| --- | --- | --- | --- |
| ① 算子 | `plugin.op(name, fn)` / `op_numpy` / `op_c` / `op_native` | 无 | 立即 |
| ② 后端 | `plugin.backend(name, factory, caps=...)` | 有（切后端） | 需 `activate()` |
| ③ 优化器 | `plugin.optimizer(name, cls, works_inplace=...)` | 无 | 立即 |
| ④ 层 | `plugin.layer(name, cls)` | 无 | 立即 |
| ⑤ 骨架 | `plugin.arch(name, builder)` | 无 | 立即，`T.build(name, ...)` |
| ⑥ API 兼容层 | `plugin.api(name, installer)` | 有（改 `sys.modules`） | 需 `activate()` |

**为什么 ②⑥ 要显式激活**：装插件不该在用户不知情时改变进程行为。

### 3.2 四档可移植性（回答「C 插件怎么跨后端」）

**物理事实：CUDA C 不可能跑在 Vulkan 或国产卡上。** 所以不追求"一份代码全后端"，
而是分档 + 自动降级：

| 档 | 形态 | 可移植 | 速度 | 谁写 | 状态 |
| --- | --- | --- | --- | --- | --- |
| **A 组合式** | 用已有算子拼（Python） | ✅ 全后端 | 看拼法 | 任何人 | 【已实测】 |
| **B 声明式内核（DSL）** | 逐元素/归约/广播的数学描述 | ✅ ORV 生成各后端代码 | 近原生 | 任何人 | 【设计】S1 未开工 |
| **C-1 源码** | CUDA C → NVRTC 现场编译 | ❌ CUDA | 原生 | 专家 | 【已实测】V100 |
| **C-2 原生库** | 预编译 `.so`/`.dll` + C ABI / JSON 清单 | ❌ 该库的架构 | 原生 | 专家 | 【已实现】CPU 侧验证 |

**纪律**：C 档插件**必须**同时提供 A 或 B 档回退。否则它在别的后端上应当表现为
「不存在」，而不是「跑出错结果」——由分派层的 `backend="*"` + 能力检查保证。

### 3.3 C 端优先（用户明确要求）

三条原生通道，按"原生程度"：

| 通道 | 需要 Python 吗 | 说明 |
| --- | --- | --- |
| `plugin.load_manifest(json)` | **不需要** | 原生库 + JSON 描述符号与参数映射 |
| `plugin.op_c(lib, symbol)` | 一行绑定 | ctypes 调 C ABI 导出 |
| `plugin.op_native(source, entry)` | 一行绑定 | ORV 内置 NVRTC 现场编译 |

**纠正一个误解**：`.py` 从来不是热路径，只在加载时执行一次。原来的限制是
"实现也只能是 Python"；现在实现可以是原生的，Python 只是可选外壳。

**安全声明（不许含糊）**：加载原生库 = 执行任意机器码。ORV 不做沙箱、不校验来源。

### 3.4 优化器能力契约（`works_inplace`）

出式更新 `p.data = p.data - ...` 会把 `.data` 换成新数组，**断开共享存储的视图**。
所以：
- 只有声明 `works_inplace=True` 的优化器能用于 `ParameterGroup`；
- 由 `plugin.require_inplace()` 在**注册/构造阶段**拒绝，而不是等训练跑歪；
- `group.assert_optimizer_ok(opt)` 额外检查优化器没拿到视图。

这条是真实的（有测试**故意**执行出式赋值并断言 `np.shares_memory` 变 false）。

## 4. 插件 DSL（插件语言）—— 尚未开工

### 4.1 要解决什么

让**一份描述**适配全后端：ORV 自己把它降到各后端的语言并编译。

### 4.2 形态（不做完整语言）

只覆盖**逐元素 + 归约 + 广播**，这就吃掉自定义算子的绝大多数（激活、norm、loss、fused epilogue）。

```python
@plugin.kernel("my_silu")
def my_silu(x, y):
    return y == x / (1.0 + exp(-x))        # == 表示"写回哪个缓冲"，不是比较

@plugin.kernel("my_rmsnorm")
def my_rmsnorm(x, w, y, eps):
    ms = mean(x * x, axis=-1, keepdim=True)
    return y == x / sqrt(ms + eps) * w
```

注册时**静态检查**：形状能否广播、类型是否一致、有没有用不支持的原语。
错在注册阶段报，不是编译出跑错的代码。

### 4.3 代码生成路径

| 后端 | 生成 | 编译 | 本机可验证 |
| --- | --- | --- | --- |
| CUDA | CUDA C | NVRTC（已具备） | ✅ |
| CPU | C | 系统编译器；不可用时回退 numpy | ✅ |
| Vulkan | GLSL compute → SPIR-V | glslangValidator | ❌ |
| 国产卡 / 自定义卡 | **由该后端插件决定**（OpenCL C / SYCL / 厂商语言） | 厂商工具链 | ❌ |

**关键**：新后端**不改 DSL**，只实现「IR → 本后端源码」的生成器。这是把"加后端"成本压下来的地方。

### 4.4 分阶段（S1 不做完不谈 S2）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **S1** | 三档契约 + 静态检查 + B 档**只支持逐元素** | 同一 DSL 在 CPU 与 CUDA 数值一致 ≤1e-6，有 pytest |
| S2 | 归约 + 广播 + 类型提升 | 覆盖 norm/loss 类算子 |
| S3 | 性能：向量化、循环展开、fp16 | 达手写原生的 70%+ |
| S4 | Vulkan 生成器 | 与 CUDA 数值一致 |
| S5 | 第三方后端生成器接口文档化 + 参考实现 | 别人能照着接 |

## 5. 数据层

### 5.1 Tensor 与 autograd

`Tensor` 持有 CPU（numpy）或 CUDA（`GpuBuf`）数据，`_parents` 构成 DAG，
每个算子注册自己的反向闭包。已与 PyT 对齐的关键语义见 §8。

### 5.2 已知坑（写下来避免重复踩）

| 坑 | 事实 |
| --- | --- |
| `min` / `max` 被遮蔽 | 模块内 `min`/`max` 是张量 API（`_api_min`/`_api_max`），做标量比较必须用 `_builtin_min` / `_builtin_max` |
| `sum` 的参数名 | 是 `axis=`，不是 `dim=` |
| `T.cat` 的参数名 | 是 `dim=`，不是 `axis=` |
| `cuda.py` 的加载方式 | 被 `exec` 进私有命名空间：`tgai_go.train.cuda` 是 `_CudaAPI` 实例，`sys.modules` 里没有这个模块 |
| CPU `.grad` 是 numpy；CUDA `.data` 是 None | 用 `to_numpy()` |

### 5.3 逐层立即更新（3B 能跑的关键）

层 i-1 的反向不需要层 i 的权重（`dL/dx_i` 已算出），所以可以逐层算完就更新、
立刻释放梯度。与统一更新的差异是 **fp32 BLAS 求和顺序**造成的 ~2e-06，
**不是逐位相同** —— 文档与测试都按这个口径写，不许说成"完全一致"。

### 5.4 共享存储参数（`ParameterGroup`）

| 平台 | 状态 | 原因 |
| --- | --- | --- |
| CPU | 【已实现】 | numpy 切片天然共享 |
| CUDA | 【未实现】 | `GpuBuf` 支持共享 `ptr` 的视图，但**没有 offset 字段**；偏移视图要伪造 `ptr+offset`，会触碰所有按 ptr 索引的逻辑（缓存失效、提交标记）。明确报错，不静默出错 |

**为什么它重要**：MoE 专家权重若连续存 `[G, N, K]`，一次 `SgemmStridedBatched` 能算完全部专家。
实测反向：需要按调用重排权重时，V2.7 慢 1.30×、256 专家慢 **2.22×** —— 因为小 M 的专家 GEMM 是
**权重带宽受限**（4 FLOP/byte，V100 的算力/带宽比约 17）。所以只有"从不需要重排"才有收益，
上限 1.02–1.39×，且只在极多专家配置下明显。

## 6. 后端抽象

### 6.1 一个后端必须提供什么（Vulkan 的实现清单）

| 能力 | 说明 | 必需 |
| --- | --- | --- |
| 设备初始化 / 上下文 | 选设备、建队列/流 | ✅ |
| 缓冲分配与释放 | 对齐、复用池 | ✅ |
| H2D / D2H / D2D | 同步语义要明确 | ✅ |
| 内核编译 | 源码或 SPIR-V | ✅ |
| 内核启动 | grid/block 映射到该后端概念 | ✅ |
| 同步 / 事件计时 | 性能测量要用它，不能用墙钟 | ✅ |
| 能力声明 `caps` | `subgroup_ops`、`shared_memory`、`async_copy`、`max_workgroup` 等 | ✅ |
| BLAS 等价（GEMM） | 可先自己写，再考虑接厂商库 | ✅ |
| 归约原语 | softmax / norm / topk 需要 | ✅ |

### 6.2 Vulkan 的关键映射

| CUDA 概念 | Vulkan 概念 | 注意 |
| --- | --- | --- |
| kernel | compute pipeline + descriptor set | 描述符绑定要预先规划 |
| block / grid | workgroup / dispatch | `maxComputeWorkGroupSize` 因设备而异，必须查 |
| shared memory | workgroup storage（`shared`） | 上限小（常见 32–64 KB） |
| warp / shuffle | **subgroup 操作**（需扩展） | 能力可能缺失，必须有回退路径 |
| `cp.async` | **无直接等价** | `caps["async_copy"]=False`，插件走回退 |
| cuBLAS | 无 | GEMM 要自己写 tiled 内核，或接第三方 |
| CUDA Graph | 无直接等价 | 捕获/重放的收益在 Vulkan 上要重新评估 |

**结论**：Vulkan 不是"CUDA 换个 API"，GEMM 与归约这两块要从头写。
这决定了 Phase C 的工作量必须按**月**计，不能按天估。

### 6.3 后端接入纪律

1. 新后端**不改** DSL、不改插件 → 只实现「IR → 本后端源码」的生成器 + 后端接口；
2. 能力不足的实现**注册时就声明**，分派负责拒绝；
3. 每个用能力优化的插件**必须**有不依赖该能力的回退路径。

## 7. 多卡（未来必须支持，当前无硬件）

### 7.1 现在的事实

**【未验证】当前一行多卡代码都没有。** 本机单卡，云上环境也不可控。
所以本节的定位是**架构预留**，不是"已支持"。

### 7.2 必须提前留的接口（不实现，但别堵死）

| 预留点 | 为什么现在就要留 |
| --- | --- |
| 后端接口带"设备"概念 | 现在 `_CudaAPI` 是单例；多卡需要 per-device 上下文。**不能假设全局单例** |
| 通信原语抽象（all-reduce / all-to-all / broadcast） | 单卡时空实现，多卡时换成 NCCL/RCCL/自写 |
| 数据并行 | 梯度 all-reduce，最简单，优先 |
| **专家并行（EP）** | MoE 的真实需求，需要 all-to-all 路由；`top-k` 跨设备是难点 |
| 分片（FSDP 类） | 显存不够时的必需品；与逐层更新策略耦合 |
| `ParameterGroup` 的跨设备视图 | 分片后参数在多个设备上，视图语义要重新定义 |

### 7.3 已知的、必须在多卡前解决的问题

- **Muon 在 3B 上不可用**（35 s/步）。它的大头是 FLOP（21.6 TFLOP/步，V100 下限已 1.4 s），
  不是启动开销 —— 按形状分组批量做**实测零收益**（35018 vs 34993 ms）。所以 Muon 适合 <1B，
  3B 请用 AdamW。
- **容量因子在 CPU/CUDA 上丢弃的 token 集合不同**（两边都遵守 cap，但 compact 顺序不同）。
  多卡 EP 下必须统一，否则设备间会算错。修法：按门控权重排序后再截断（需排序内核，未做）。

## 8. 数值一致性与测试

### 8.1 已实测的一致性数字

| 对照 | 相对差 |
| --- | --- |
| 8 步训练 loss（vs PyTorch） | 1.44e-07 |
| Qwen2.5-0.5B 前向 logits（vs HF） | 6.29e-06 |
| gather / CUDA Graph / fused fp16 AdamW | 0.00e+00 |
| LayerNorm | 4.38e-08 |
| conv | 2.39e-07 |
| CausalSelfAttention | 5.02e-08 |
| MoE 共享专家（0.9.37） | 6.09e-07 |
| aux-loss-free（0.9.38） | 5.04e-07；bias 归零后与无 bias **0.00e+00** |
| Z-loss（0.9.39） | **0.00e+00**（逐位相同） |
| 原生内核插件 axpy（0.9.46） | 4.39e-08（n=1000）/ 6.94e-08（n=1M） |

### 8.2 测试的结构性约定

| 约定 | 原因 |
| --- | --- |
| 每个 `raise` 消息必须含「修法」 | 有门禁测试用 AST 扫源码强制；用户看到错要能自己修 |
| 源码禁止 BOM 与 CRLF | 有门禁测试；BOM 会让 Python 报 invalid non-printable character |
| 容差不能压在噪声地板上 | 曾因此出现两条 flaky 测试；改为 3e-5 与"按量级缩放"的判据后连跑 5 次全绿 |
| 性能数字必须用 CUDA event | Windows `time.time()` 只有 ~15.6 ms 粒度 |
| 测量前必须预热 ≥3 次、输出缓冲预分配 | 我三次测同一个量得到 6.11 / 6.42 / 4.18 ms，前两次都是把分配算进了循环 |

### 10.1 当前技术债清单

| 债 | 影响 | 处理建议 |
| --- | --- | --- |
| `ParameterGroup` 不支持 CUDA | 分组 GEMM 的收益拿不到 | 给 `GpuBuf` 加 offset 字段 + 复查所有按 ptr 索引的逻辑 |
| 容量因子 CPU/CUDA 丢弃集合不同 | 多卡 EP 下会算错 | 按门控权重排序后截断（需排序内核） |
| Muon 3B 不可用 | 3B 只能用 AdamW | 接受；或换 A100/H100 后重测 |
| `op_native` 仅 CUDA | 其它后端用不了自定义源码 | 由 DSL 的 B 档覆盖 |
| 分组 GEMM 的 `cublasSgemmGroupedBatched` 不可用 | 只能走 strided 或逐专家 | 已归档为否定结论（rc=7，连 handle 都被拒，该库符号布局与文档不符） |
| DSL 未开工 | 插件跨后端仍受限 | 按 §4.4 分阶段 |
| 多卡零代码 | 未来要补大块 | 先留接口，见 §7.2 |
| Vulkan 零代码 | 主战场还没开始 | 见 §6.1 清单，按"先通后快"推进 |

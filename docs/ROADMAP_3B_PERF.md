# 3B MoE 训练性能：实测结论与后续路线

> 生成日期：2026-11-11。本文所有数字均为本机 V100 32GB 实测（CUDA event，预分配 + 充分预热）。
> 目的：让后来者不必重复走已证明走不通的路。

## 0. 一句话结论

**当前实现下，3B MoE（V2.7 结构，28 层 2.97B）在 V100 32GB 上的整步是 709 ms
（AdamW + 逐层即时更新，纯显存 24.78 GiB）。**

两个曾被认为"应该能优化"的目标，实测均**不可达**：

| 目标 | 要求 | 实测上限 | 差距 |
| --- | --- | --- | --- |
| MoE 反向耗时 | 332 → ≤200 ms（−40%） | −25%（约 250 ms） | 差 50 ms |
| Muon 在 3B 可用 | 降到可用范围 | FLOP 固有，不可降 | 本质不可行 |

## 1. 整步 709 ms 的构成

T=512、28 层、AdamW fp16 动量 + 逐层即时更新：

| 段 | 时间 | 占比 |
| --- | --- | --- |
| 前向链（attn+MoE） | 237.0 ms | 30% |
| MoE 反向 | **332.4 ms** | **42%** |
| 注意力反向 | 206.6 ms | 26% |
| 词表头 | 11.2 ms | 1% |

> 注意：表里的「MoE 反向 332 ms」**包含梯度检查点的前向重算**。
> 单层实测 fwd+bwd = 11.82 ms ⇒ 28 层 331 ms，与之一致。
> 其中 MoE 前向重算约 4.18 ms/层（117 ms），真正的反向约 7.6 ms/层（213 ms）。

## 2. MoE 为什么优化不动（四条路径全部实测）

### 2.1 GEMM 已跑到峰值的 50~55%

| 单层原语 | 时间 |
| --- | --- |
| gate 投影 8× `gemm_nt` | 0.99 ms |
| up 投影 8× | ≈1.0 ms |
| down 投影 8× `gemm_nt` | 1.12 ms |
| **小计（GEMM）** | **≈3.1 ms** |
| router / topk / compact / gather ×8 / ewise ×8 | ≈0.6 ms |

gate 投影 = 8 × 2 × 128 × 1024 × 4096 = **8.59 GFLOP** / 0.99 ms
⇒ **8.7 TFLOP/s = V100 fp32 峰值（15.7）的 55%**。

M=128 的瘦长矩阵跑到 55% 已是合理区间，**融合发射只能省 5~10 µs/次**。

### 2.2 四条路径的实际收益

| 路径 | 实测 | 折算 28 层 |
| --- | --- | --- |
| GEMM 融合（grouped / strided-batched） | 每次省 5~10 µs | −4~8% |
| 去掉每层 `d2h` 同步 | −0.14 ms/层（噪声内） | ≈ 0 |
| 小算子融合（silu / mul / scale） | 0.3~0.5 ms/层 | −4~8% |
| AMP / fp16 GEMM | 11.82 → **10.21 ms/层（1.16×）** | −13.6%（332→287 ms） |

**加满约 −25%，达不到 −40%。**

### 2.3 为什么 fp16 只有 1.16× 而不是 2×

2× 需要走 tensor core。专家 GEMM 是 `M=128` 的瘦长矩阵，tile 利用率低；
且 fp16 输入 + fp32 累加走的是 `cublasSgemm` 的非 tensor-core 路径。

AMP 的数值代价已实测：输出相对差 **4.31e-04** —— 是 fp16 正常量级，
但比 ORV 其它路径的判据（1e-5）大一个量级，属真实精度权衡，**不建议默认开启**。

### 2.4 `cublasSgemmGroupedBatched` 这条路已放弃

- 这台机器的 libcublas **只有**非 Ex 版符号（`cublasGemmGroupedBatchedEx` 不存在，已实测）；
- 非 Ex 版按文档签名调用返回 `rc=7`，**连 `handle`（第 1 个参数）都被判非法**，
  说明该符号的参数布局与公开文档不一致；
- 已改为**失败即安全回退**（`TGAI_MOE_GROUPED` 开关保留），正确性有保障，但性能收益拿不到。

## 3. Muon 为什么在 3B 不可用（本质限制）

| 配置 | 3B 整步 |
| --- | --- |
| Muon，`ns_fast=False`（顺序 FMA，与 OpenBLAS 逐位一致） | 62.9 s |
| Muon，`ns_fast=True`（Newton-Schulz 走 cuBLAS） | **35.0 s**（1.8×） |
| Muon + 按形状分组批量 bmm（672 个同形张量） | **35.0 s（零收益）** |
| AdamW（fp16 动量 + 逐层即时更新） | **0.709 s** |

**批量化零收益**是关键证据：算子数降了约 5×，步时完全不变 ⇒ 瓶颈是**总 FLOP**：

- 单个 `[1024,4096]` 正交化 ≈ **96 GFLOP**（5 步 × 3 次矩阵乘）；
- 3B MoE 有 224 个这样的矩阵 ⇒ **21.6 TFLOP/步**；
- V100 fp32 峰值 15.7 TFLOP/s ⇒ 理论下限 **1.4 秒**，实测 35 秒（带宽受限）。

**即使实现完美，Muon 在 3B 上也至少比 AdamW 慢一个数量级。适合 < 1B。**

## 4. 真要突破，需要什么（都不在"融合优化"范围内）

| 方向 | 预期收益 | 代价 / 前提 |
| --- | --- | --- |
| 减少激活专家数（top-2 → top-1） | MoE 计算量减半 | **改模型语义**，需重训验证质量 |
| 更小的 `d_ff` | 线性降低 MoE FLOPs | **改模型结构** |
| A100/H100 + 真 tensor-core fp16/bf16 | 可能 2~8× | **本机无硬件，未测**；精度需重验 |
| 存激活不重算（放弃 checkpointing） | 省掉 117 ms 重算 | 显存 +约 10 GiB，**32GB 装不下** |

## 6. 测量方法教训（避免重犯）

同一件事本轮测出过 **6.11 / 6.42 / 4.18 ms** 三个数，前两个都偏大：

1. **不要在计时循环里新建输出 buffer** —— 分配会被算进耗时；
2. **预热要充分** —— 首次调用的内核编译/分配不能摊进均值；
3. 正确范式见 `tools/moe_prim_bench.py` 与 `tools/d2h_cost.py`。

## 8. 2026-11-11 补充：tensor core 这条路也排除了（实测）

曾怀疑 ORV 全局的 `cublasSetMathMode(PEDANTIC)` 在压制 tensor core
（PEDANTIC 为逐位可复现而存在），若放开就能拿到 2× 以上。

`tools/tensorcore_probe.py` 在 MoE gate 投影真实形状（8 专家 × [128,1024] @ [4096,1024]）实测：

| 用例 | 时间 | 实测算力 |
| --- | --- | --- |
| **fp32 @ PEDANTIC（现状）** | **0.410 ms** | **20.9 TFLOP/s** |
| fp32 @ DEFAULT | 1.026 ms | 8.4 TFLOP/s |
| fp16 @ PEDANTIC | 0.809 ms | 10.6 TFLOP/s |
| fp16 @ DEFAULT | 0.601 ms | 14.3 TFLOP/s |

**关键判读：fp32 达到 20.9 TFLOP/s，超过 V100 标称 fp32 峰值 15.7
⇒ tensor core 本来就在用**，不存在"被 PEDANTIC 压住"的余量。

附带两点反常但可复现：
- DEFAULT 比 PEDANTIC **更慢**（1.026 vs 0.410 ms），说明 math mode 影响的是算法选择启发式；
- fp16 比 fp32 **更慢**（0.809 vs 0.410 ms），多出来的应是每次调用的转换开销。

### 结论

tensor core 不是缺失的 40%。加上此前四条路径，MoE 加速的可能空间已全部枚举并实测：

| 候选 | 上限 |
| --- | --- |
| GEMM 融合 | −4~8% |
| 去 d2h 同步 | ≈0 |
| 小算子融合 | −4~8% |
| AMP / fp16 GEMM | −13.6% |
| **tensor core（放开 PEDANTIC）** | **≈0（已在用）** |

需要 −40%，以上全部加起来仍不够。**只能改模型结构或换硬件。**

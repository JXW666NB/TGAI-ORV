# 如何超越 PyTorch（不是追平）

> 判据统一用 `docs/REFERENCE_V21E_2026-11-12.md` 的基准：
> **V100 全尺寸 v2.1e（434M，fp16+检查点，B=8/S=2048）= 5,667 tok/s / 10.28 GB**。
> 任何"超越"的主张都必须在这套协议下给出数字。

## 1. 现状：一赢一输，别混着说

| 维度 | ORV vs PyTorch | 证据 |
| --- | --- | --- |
| 单步速度（fp32）| **赢 2.58×** | `BENCHMARK_H2H`: dense 16.55 vs 42.73 ms |
| 单步速度（MoE fp32）| **赢 1.68×** | 83.0 vs 139.4 ms |
| fp16 加速比 | **输**：1.11× vs 2.17× | 本轮消融：5,667 vs 2,612 tok/s |
| 显存 | **输 1.2–1.9×** | h2h 六组一致；检查点修复后仍有差距 |
| 大模型能不能装下 | **赢**（有条件）| 3B MoE 24.78 GiB；PyT 1.997B 就 OOM（31.40 GiB）|
| 检查点 | **刚追平** | 0.9.53：20 层 606M 从 31.29 GiB 降到 7.56 GiB |

**一句话**：ORV 现在是「更快、更胖、能把更大的模型塞进去」。**胖是当前最明显的短板。**

## 2. 超越只能来自「控制整栈」这一件事

PyTorch 是通用框架，它的结构性代价是**每条算子边界都要落到 HBM**：
一个 `Linear → SiLU → Mul` 序列在 eager 下是 3 次 kernel 启动 + 2 次全量写回/读取。
`torch.compile` 想解决它，但编译慢、覆盖面窄、行为随版本漂移。

**ORV 能在源码层做整图优化，这是唯一别的引擎拿不到的优势。** 四条具体路径：

### A. 全图融合 / 大内核（最大杠杆）

| 做什么 | 收益来源 |
| --- | --- |
| **MLP 融合**：`gate/up/silu/mul/down` 串成一个 kernel，中间量留寄存器/共享内存 | 消灭 3 次 `[B*S,FF]` 往返。B=8/S=2048/FF=5120 时单个中间量 84 MB × 3 × 2(读写) ≈ **500 MB 流量/层** |
| **RoPE + QKV + SDPA 融合** | Q/K 的旋转不需要独立往返 |
| **残差 + RMSNorm 融合** | 每层省一次 `[B*S,D]` 往返（21 MB）|
| **megakernel（远期）**：整层甚至多层一个 kernel | 理论上把 HBM 流量降到只读参数 + 读写激活 |

**判据**：同协议下 tok/s 超过 5,667；且 `B=8` 峰值不高于 10.28 GB。

### B. 显存：三种 offload + 选择性检查点

| 手段 | 为什么 ORV 能做得好 |
| --- | --- |
| **选择性检查点**：只对"贵"的层（大 FF、MoE）做检查点，其余正常存 | 通用框架只能整段开关；ORV 可以按层给策略 |
| **激活 offload 到 pinned 主机内存** | 有 `pin` + 异步拷贝基础设施；代价是 PCIe 带宽 |
| **优化器状态 offload / 低精度** | 3B 时 AdamW 状态占 3.2 GiB（fp32）⇒ 8-bit 或主机存放能直接砍 |

**判据**：`B=8` 峰值 **低于** 10.28 GB，同时 tok/s 不低于 5,667。

### C. 零启动开销：CUDA Graph 默认开

| 事实 | 数据 |
| --- | --- |
| ORV 的 dispatch 开销实测 | **627 ns/次** |
| 一层的算子数 | 约 12–20 次 ⇒ 约 10 µs/层启动 |
| 20 层 ⇒ | 约 0.2 ms/步 —— 在 B=8（约 2.9 ms/步）下占 **7%** |

单看不大，但**小模型/小 batch/RL rollout** 场景（步时百微秒级）下会变成主要成本。
PyTorch 也能用 CUDA Graph，但要用户自己包、且对动态形状不友好。**ORV 可以做成默认。**

**判据**：小形状（B=1/S=512/d=512）步时比 PyTorch **快 ≥2×**。

### D. 可验证数值（**我认为最有信心、也最没人做的一条**）

PyTorch 的 AMP 是"尽力而为"：fp16 累加误差没有上界，不保证逐位复现。
ORV 已经有两个别人没有的基础：

| 已有能力 | 现状 |
| --- | --- |
| **精度门槛** | fp16 只在 `m*n ≥ 262144 且 k ≤ K` 时启用，且有实测误差记录（3e-4 → 2e-2）|
| **确定性归约** | `deterministic=True` 时走无原子归约，同一输入两次运行**逐位相同** |

**超越 = 把它变成承诺**：给出「本配置下 fp16 误差上界」并在超界时**自动回退 fp32**，
以及**默认逐位可复现**。这两件事 PyTorch 都没做（要用户自己配 flag，且不保证）。

**判据**：同一 seed 两次训练 loss 逐位相同；fp16 与 fp32 的 loss 差可报告且不超阈值。

### E. 按架构代际自调（配合「覆盖每一代 N 卡」的计划）

不同代的差异不只是 Tensor Core：L2 大小、共享内存/SM、fp16 吞吐比、是否支持 TMA。
ORV 控制 kernel 参数 ⇒ 可以为每代存一套调优表，用户无感。

**判据**：同一份代码在 sm_60/70/80/89 上**都不低于**该卡上 PyTorch 的 1.0×。

## 3. 顺序建议

| 优先级 | 做什么 | 为什么 |
| --- | --- | --- |
| **1** | **B 显存**（选择性检查点 + 优化器状态）| 这是当前唯一"输"的维度，且不修就会被 16GB 卡挡住 |
| **2** | **A MLP 融合** | 收益最大且最容易量（一层一个 kernel）|
| **3** | **D 可验证数值** | 投入小、差异化最独特，且是**质量**优势不是速度优势 |
| **4** | **C CUDA Graph 默认开** | 对 RL/小模型价值高，对大模型有限 |
| **5** | E 代际调优表 | 需要多卡硬件，等租机 |

## 4. 不要做的事

| 不做 | 理由 |
| --- | --- |
| 追求"通用 API 全覆盖" | PyTorch 有 2000+ 算子，追不完；ORV 的定位是训练够用 |
| 和 torch.compile 拼自动融合覆盖面 | 它编译整图，我们只做训练常用pattern，反而能做得更彻底 |
| 声称"显存更省" | 当前实测是**更费**；除非 B 项做完并有数字 |
| 用 host-staged 多卡去拼 NVLink 方案 | PCIe 差一个数量级（见 `MULTIVENDOR_ROADMAP.md`）|

# TGAI V3 训练吞吐终极对比（2026-11-17，V100 32 GB 实测）

> 全部是**真实训练步**：ORV 走真语料（`packed512\s512` / `packed_1024`），
> PyTorch 走 `tools/v3_pyt_train.py`（随机 token，形状与实际训练相同）。
> 配置统一：V3-1.5B ＝ 24 层 / d=1024 / d_ff=3328 / E=4+1 共享 / top_k=2 / vocab=96000 / csa=4 / n_q=16。

## 一、最快吞吐：ORV **987 tok/s**（seq512 / bf16 动量）

| 框架 | 配置 | 逐步耗时（稳态）| 中位 | **吞吐** |
|---|---|---|---:|---:|
| **ORV** | seq512 / bf16 动量 | 0.494, 0.483, 0.519, 0.528, 0.542 | **0.519 s** | **987 tok/s** |
| ORV | seq1024 / m8v16 | 1.178, 1.221, 1.193, 1.192 | 1.193 s | 858 tok/s |
| PyTorch | seq512 / fp32 | 1.20, 1.12, 1.03, 1.02 | 1.07 s | 478 tok/s |
| PyTorch | seq512 / **fp16 amp** | 1.12, 1.05, 0.95, 0.96 | 1.00 s | 512 tok/s |
| PyTorch | seq1024 / fp32 | 1.34, 1.36, 1.35, 1.57 | 1.36 s | 753 tok/s |

## 二、逐项对比

| 场景 | ORV | PyTorch（最优）| ORV 优势 |
|---|---:|---:|---:|
| **seq512** | **0.519 s** | 1.00 s（fp16 amp）| **1.93×** |
| seq512（对 fp32）| 0.519 s | 1.07 s | 2.06× |
| **seq1024** | 1.193 s | 1.36 s | **1.14×** |
| 峰值吞吐 | **987 tok/s** | 753 tok/s | **1.31×** |

**关键发现：ORV 的优势随 seq 增长而收窄**（512 时 1.93×，1024 时只剩 1.14×）。
原因：seq 越长，注意力部分的 GPU 计算占比越高，而我们赢的那部分（CPU 派发开销）
相对被稀释。**ORV 的强项是短序列/多步**，PyTorch 的强项是长序列的 GPU 利用率。

## 三、PyTorch 的 fp16 确实有效（但我们无效，原因不同）

PyTorch `--amp`：1.07 → 1.00 s（**−7%**）。
ORV 开 fp16 GEMM：**更慢**（20 层 0.783 vs 0.647），因为瓶颈在 CPU 派发而非 GEMM。
⇒ 同一个技术，在两种执行模型下结论相反 —— 这不是实现好坏，是瓶颈位置不同。

## 四、顺带查出的真 bug：`--batch > 1` 不可用

```
CudaError: reshape (2, 1024, 1024) -> (1024, 1024) 元素个数 2097152 != 1048576
```

`v3_pretrain` 的 CSA 注意力路径在 batch>1 时形状不对（把 batch 维吞掉了）。
**这意味着现在只能用 batch=1 + 梯度累积**，无法靠加大 batch 摊薄每步的 CPU 开销 ——
而摊薄恰恰是提升吞吐最直接的手段（CPU 开销是 per-step，不是 per-token）。

修好后预期：batch=2 时 tok/s 有望接近 1.6–1.8k（每步 CPU 开销不变、token 数翻倍）。

## 五、结论

1. **当前最快：ORV 987 tok/s（1.5B / seq512 / bf16 动量 / m8v16 亦可）**
2. 对 PyTorch：seq512 快 **1.93×**，seq1024 只快 **1.14×**
3. **下一步提吞吐最有效的不是优化内核，而是修好 `--batch`**（让 CPU 开销摊薄），
   其次是 CUDA Graph（上限约 17%）。

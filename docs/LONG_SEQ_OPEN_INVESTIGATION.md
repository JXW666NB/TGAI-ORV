## 最终结果（同口径：预热 1 次 + 3 次中位数，极差 ≤0.9%）

V100 / 12 层 MoE / vocab 96000 / 20 步 / ckpt 关 / AMP 开 / batch=1：

| seq | ORV | PyTorch | 结论 | 显存（ORV / PyT）|
| --- | --- | --- | --- | --- |
| 512 | **0.231 s** | 0.313 s | **ORV 快 1.35×** | **12.0** / 16.5 GiB |
| 2048 | **0.398 s** | 0.412 s | **ORV 快 1.04×** | 27.3 / **22.9** GiB |

## 长序列落后的真因（按发现顺序，前两个是我自己造成的）

1. **显存池 cap 低于峰值 live**（真问题，影响 seq2048 约 **−19%**）
   旧规则 `cap = 0.6×总显存` = 19.1 GiB，而峰值 live **23.7 GiB** ⇒ 池每步 trim 再申请。
   子代理 CUDA-event 实测：**1225 次 alloc + 1333 次 free + 138 次 trim/步，GPU 空转 130 ms**。
   修法：`cap = 总显存 − max(4 GiB, 15%)`（32 GiB → 27.1 GiB）。代价是显存占用上升。

2. **我自己引入的 clip 回归**（把 seq512 拖慢 88%）
   `sumsq_multi_slots`/`scale_multi` 的 grid 写成 `(张量数,1,1)`，**每个张量只有 1 个 block**，
   98.3M 的梯度实测只有 **26 GB/s**（同形状 1024 block 是 706 GB/s）⇒ clip 从 11.7 ms 涨到 **285.9 ms**。
   修法：>1M 元素走旧的逐张量路径；真实规模（2×98.3M）重验：9.16 ms、相对误差 9.25e-08。

3. **剩下的差距不在 kernel，在 GPU 空转**
   两侧 kernel 时间几乎相同（ORV 367 vs PyT 353 ms/步），差的是空转：
   **ORV 130 ms（26%）vs PyT 46 ms**。空转来源：每步 26 次阻塞式 D2H（主机阻塞 108.6 ms，其中
   MoE 路由 12 次）+ 驱动层 alloc/free。

## 三条方法学教训（这才是本文最该被记住的部分）

1. **不要用「调用前后各 sync」给单 kernel 计时** —— 探针开销会把小 kernel 放大几十倍。
   我曾据此把 `transpose2d` 量成 76 ms/步（实际端到端中性）、把 MoE 分发量成 169 ms/步。
   正解：CUDA event（成对 record，步末批量读）。
2. **性能验证必须用真实规模** —— 我曾用最大 5 万元素的梯度"验证"clip 快 30.6×，
   而真实 98.3M 张量上它慢了 24×。玩具尺寸只能证明"没崩"。
3. **稳态必须预热** —— 冷启动单次比预热后慢 20~100%。seq2048 同一配置冷启动测到过
   0.542/0.753/0.899，预热后稳定在 0.398 s。**协议不一致时，A/B 会得出完全相反的结论。**

## 仍未解决

- **3-D 批量 GEMM 走 fp32**：`bmm → sgemm_strided_batched` 只有 fp32 一条路（9.9 TFLOPS vs fp16 的 64.9）。
  11% 的 FLOPs 吃掉 **45% 的 GEMM 时间**；接进 AMP fp16 预计 **−55~60 ms**。（正在做方案）
- **MoE 路由每步 12 次阻塞 D2H**（主机阻塞 108.6 ms），改设备端 dispatch 预计 −40~56 ms。

# ORV 长序列落后 PyTorch：排查记录（求助版）

> 硬件：Tesla V100-PCIE-32GB（驱动 580.76.05，torch 2.6.0+cu124，ORV 1.0.2）
> 被测模型：V3 MoE 12 层（d=1024 / d_ff=3328 / E=4+1 共享 / top_k=2 / vocab 96000）
> 口径：**20 步稳态**，两侧都**关梯度检查点**、都**开 AMP**、batch=1、同一份数据
> 所有数字均为实测，脚本在 `lab/rent/` 下，可复现

---

## 1. 现象

| seq | ORV | PyTorch | 谁快 | 显存（ORV / PyT）|
| --- | --- | --- | --- | --- |
| 512 | **0.239 s**（2,140 tok/s）| 0.311 s（1,647 tok/s）| ORV **1.30×** | 12.6 / 16.5 GiB |
| 1024 | **0.278 s**（3,685 tok/s）| 0.330 s（3,105 tok/s）| ORV **1.19×** | 15.7 / 17.8 GiB |
| **2048** | 0.696 s（2,943 tok/s）| **0.407 s**（5,032 tok/s）| **PyTorch 1.71×** | 23.7 / 22.9 GiB |

**短序列我们赢，长序列我们输 1.7 倍。** 本文要回答：为什么会这样，以及差距到底在"哪个端"。

---

## 2. 逐阶段拆解（关键表）

| 阶段 | seq512 ORV / PyT | seq2048 ORV / PyT | 4× token 后 ORV 增长 |
| --- | --- | --- | --- |
| forward | 0.086 / 0.080 s | **0.353 / 0.105 s** | **4.1×**（PyT 只 1.3×）|
| backward | 0.121 / 0.122 s | 0.306 / 0.205 s | 2.5× |
| optimizer | **0.0338** / 0.0863 s | **0.0338** / 0.0841 s | 0（不随 seq 变）|
| 合计 | **0.239** / 0.315 s | 0.693 / **0.403 s** | 2.9× |

**读法**：
* seq512 时我们全部优势来自**优化器**（0.0338 vs 0.0863，省 0.052 s）；算子和反向基本打平
* seq2048 输在 **forward 涨了 4.1×**（对方只涨 1.3×），backward 也慢 1.5×

forward 内部再拆（ORV 侧，挂 `csa_forward` 计时）：

| | seq512 | seq2048 | 增长 |
| --- | --- | --- | --- |
| 注意力 | 0.036 s | 0.106 s | 3.0×（接近线性，正常）|
| 非注意力"其余" | 0.051 s | **0.247 s** | **4.9×**（占 seq2048 forward 的 70%）|

---

## 3. 成本结构：固定成本 vs 每 token 成本

用 batch 扫描解 `t = c + a·N`（seq512，batch=1 vs 2）：

* **固定成本 c = 0.206 s/步**（与 token 数无关）= seq512 步时的 **86%**
* 边际成本 a = **6.47e-05 s/token**

若边际成本不变，seq2048 应为 `0.206 + 2048×6.47e-05 = 0.339 s`，**实测 0.690 s**。
反推 seq2048 的边际成本 = **2.36e-04 s/token ⇒ 是 seq512 的 3.65 倍**。

**结论**：短序列赢在固定成本小（Py 端），长序列输在**每 token 成本涨 3.65 倍**。
所以"长序列问题"不是派发开销，是**每 token 的 GPU 侧成本**。

---

## 4. 单 kernel 微基准：我们的 kernel 并不慢

同形状（M=2048, K=1024, N=3328）对比：

| 指标 | ORV | PyTorch | 差距 |
| --- | --- | --- | --- |
| fp16 GEMM（tensor core）| **61.4 TFLOPS** | 65.7 TFLOPS | **仅 6.5%** |
| fp32 GEMM | — | 10.7 TFLOPS | — |
| 逐元素 add（2 MB 工作集）| 337 GB/s | **588 GB/s** | 我们慢（发射开销占比高）|
| 逐元素 add（8 MB 工作集）| **722 GB/s** | 689 GB/s | 我们略优 |

⚠️ 微基准**必须带同步**：不加同步会测出 672 TFLOPS 这种荒谬数字（异步调用的发射耗时）。

**结论**：单个 kernel 的峰值效率我们与 PyTorch 持平甚至略优 ⇒ **"对方 kernel 写得更快"不成立**。

---

## 5. 计数：问题在"遍数/发射数"

`ctypes` 单次发射固定开销实测约 **10 µs**（2 MB add 实测 18.7 µs，带宽下限 8.7 µs）。
每步发射数（seq2048，5 步平均）：

| kernel | 每步次数 | 说明 |
| --- | --- | --- |
| `cast_f32_to_f16` | **929** | AMP 权重影子重铸；每步 h2d 上传 **5.57 GiB / 20 步 ≈ 299 MB/步** |
| `sumsq_partial` + `sumsq_final` | **642** | 梯度裁剪**按参数逐个**算范数（321 参数 × 2）|
| `ewise_scale_v4` / `ewise_add` / `mul_bcast8` / `fused_add_ip_v4` | 各 350–380 | 逐元素链，**每个算子一趟 (T,d) 访存** |
| **合计** | **5,283 / 步**（前向 2,876 + 反向 2,407）| × 10 µs ≈ **0.053 s/步** |

发射数**与 seq 无关**（512 与 2048 几乎相同），所以：
* 它不是长序列落后的原因（只占 2048 步时的 7.6%）
* 但它是**短序列固定成本**的主体（占 512 步时的 22%）

## 6. 已被实测排除的假设（不要再走这些路）

| 假设 | 实验 | 结果 |
| --- | --- | --- |
| 注意力主导长序列 | 挂 `csa_forward` 计时 | 仅占 11.7–19.7%，且占比随 seq **下降** |
| 分块注意力没触发 | 强制 `TG_CSA_ATTN_CQ=512/256` | 0.868→0.959/0.981 s，**更慢**（分块是拿速度换显存）|
| head/loss（T×vocab）是元凶 | 2×2：seq{512,2048}×vocab{4096,96000} | T 正比部分仅 **0.074 s = 7.9%** |
| 激活精度/带宽 | `TG_BF16_ACT=1` | 步时 **+3.8%/+5.2%**，内存仅 −1.7%/−6.0% |
| 每层一次主机往返 | 计数 sync | 只有 **2 次/步**，与层数无关 |
| 专家计算量太大 | `top_k=1`（专家计算减半）| forward **反而更慢**（0.352→0.384 s）|
| 我们 kernel 比 cuBLAS 慢 | 同形状微基准 | fp16 GEMM 只差 6.5%，带宽略优 |

## 7. 当前最可能的方向（待证）

`forward` 的"其余" 0.247 s（seq2048）里，按 FLOPs 估算 MoE 的 GEMM 只需 ~16–35 ms，
**差了一个数量级** ⇒ 时间不在 GEMM，而在：

1. **MoE 的分发/置换**：scatter / index_gather / permute / cat_place / transpose2d 等
   每层几十个 token 级小 kernel，每个都是一趟 DRAM 往返（工作集 8 MB > L2 6 MB）
2. **专家 GEMM 的行数变小**：2048 token × top_k 2 / 4 专家 ≈ 1024 行/专家，
   加上 padding，cuBLAS 在小 M 上效率会显著低于基准的 61 TFLOPS（**未实测**）
3. **逐元素链无法融合**：`silu / mul / scale / add` 各一趟

## 10. 一句话总结

**我们的单个 kernel 不比 PyTorch 慢（GEMM 差 6.5%、带宽还更优）；
长序列的差距来自"每 token 成本涨 3.65 倍"，指向 MoE 分发与逐元素多趟访存，而不是算力或派发次数。**
下一步需要 kernel 级时间线来确认，而不是继续做消融。

## 11. 关键消融：把路由整个去掉（E=1）——2026-11-19 补充

| 配置 | seq512 步时（fwd / attn / rest）| seq2048 步时（fwd / attn / rest）| 参数 |
| --- | --- | --- | --- |
| E=4, top_k=2 | 0.240（0.087 / 0.035 / 0.052）| 0.693（0.354 / 0.106 / **0.248**）| 849M |
| E=4, top_k=1 | 0.227（0.080 / 0.036 / 0.044）| 0.634（0.383 / 0.095 / 0.288）| 849M |
| **E=1（无路由）** | **0.145**（0.035 / 0.035 / **0.000**）| **0.347**（0.173 / 0.078 / **0.095**）| 481M |

**去掉路由与专家：seq2048 步时 0.693 → 0.347（−50%），"其余" 0.248 → 0.095（−62%）。**

但边际成本（每 token）暴露出更深的问题：

| | seq512 | seq2048 | 边际成本 |
| --- | --- | --- | --- |
| ORV E=4 | 0.240 | 0.693 | **2.36e-04 s/token** |
| ORV E=1 | 0.145 | 0.347 | **1.31e-04 s/token** |
| PyTorch | 0.315 | 0.416 | **6.6e-05 s/token** |

**即使完全去掉 MoE，我们的每 token 成本仍是 PyTorch 的 2 倍；带 MoE 是 3.6 倍。**
⇒ 长序列差距是两半：**一半来自 MoE 分发/专家，一半来自更底层的每 token 效率**（逐元素多趟访存）。
所以"只优化 MoE"最多追回一半。

## 12. 上传量的归属（一个必须说清的乌龙）

`h2d` 计数显示 20 步共 5.97 GiB。逐调用点追踪后发现：
**其中约 786 MB 是模型构建时的一次性上传**（`emb` 96,000×1,024×4 = 393 MB + `head` 393 MB），
被我错误地按步数摊了。扣掉后**每步约 260 MB** 仍待解释。

更强的探针把另一处归给 `clone()`（约 505 MB），但 `clone` 内部走的是 **D2D**、不该有 h2d，
说明该栈归属不可信。**因此"每步上传 260 MB"目前不能断定为 bug**，需要 CUDA 事件级计时才能确认。

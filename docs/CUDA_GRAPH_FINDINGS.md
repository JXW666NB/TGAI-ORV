# CUDA Graph 训练路径：能跑，但**已经没有加速**（负结果记录）

## 1. 结论（2026-11-03，V100 / Qwen2.5-0.5B / B=4·S=512）

| 项 | 数值 |
| --- | --- |
| 图节点数 | 2151（fp32）/ 2515（fp16） |
| 图内 前向+反向 重放 | **238.9 ms**（fp16） vs 逐算子 **241.5 ms** ⇒ **1.01×** |
| 图内 前向+反向 重放 | 587.6 ms（fp32） vs 逐算子 594.3 ms ⇒ 1.01× |
| 梯度数值 | 重放 vs 逐算子：fp32 相对 5e-8；fp16 相对 1.3e-10 |

**负结果**：Graph 曾经量到 1.23×（fp32，748→605）和 1.71×（fp16，437→256）。
那是**优化前**的数据。这轮回头重测时，其他优化（分配器真实空闲显存判断、
fused AdamW 290→1、CE 合并访问、rope_half）已经把「发射间隙」这条收益吃掉了，
于是 Graph 只剩 1.00~1.01×。

⇒ **结论：在当前代码上，CUDA Graph 不再是值得投入的优化方向。**
（保留代码是它仍能作为"发射开销上限"的测量工具。）

## 2. 为什么当初以为它能救

之前 fp16 逐算子 437 ms，其中 GPU kernel 约 255 ms，其余 180+ ms 是每步几百次
kernel 发射的间隙 —— 图能把间隙消掉。但后来发现那些间隙里很大一部分是
**分配器每次未命中都做一次整设备同步**（硬编码 12.2 GiB 判据导致），
修掉后间隙本身就没了。

## 3. 实现里踩到的两个真坑（代码保留，后人别再踩）

1. **优化器不能放进图里**：AdamW 的偏差校正 `1-b^t` 是随步数变的标量，
   被刻进 kernel 参数后要靠 `cuGraphExecKernelNodeSetParams` 改写。
   实测改写**不干净**：单步重放与逐算子的参数差 1.7e-05，而该步更新量只有 1.3e-05
   —— 等于步长错了几倍。最终把优化器放在**图外**（fused AdamW 只有 1 个 kernel，30 ms）。
2. **`zero_grad` 必须在图里**：放在图外会把梯度缓冲换掉，导致重放的写落不到当前梯度上
   （现象：重放后梯度全是 0，参数完全不动，差异恰好等于整步更新量）。

## 4. 当前权威性能（同机同配置，3 次取平均）

| 配置 | 完整一步 |
| --- | --- |
| 我们 fp32 | **749.5 ms** |
| 我们 fp16（`rt.fp16_gemm=True`） | **441.9 ms** |
| PyTorch fp32 | 609.8 ms |
| PyTorch AMP | **219.5 ms** |

⇒ 对 torch fp32 快 1.38×；对 **torch AMP 仍慢 2.01×**。
差距来自 torch AMP 把**激活也存 fp16**（我们只把 GEMM 的输入换成 fp16）。
这才是下一步该动的地方，不是 Graph。

## 5. `graph_train.GraphStep` 用法（仍可用）

```python
from tgai_go.train.graph_train import GraphStep
gs = GraphStep(model, opt, ids_shape=(4, 512), tgt_shape=(2048,), vocab=151936,
               fp16_gemm=True)
gs.capture()                     # 捕获 前向+反向
gs.step(ids_np, tgt_np)          # 原地改宿主数据 + 重放 + 图外优化器
```

限制：形状固定；图里不能有 D2H（`clip>0` 或打印 loss 会触发）；参数地址必须稳定。

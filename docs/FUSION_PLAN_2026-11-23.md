# 算子融合路线图（2026-11-23）

> 依据：`docs/HOSTHOTSPOTS_2026-11-23.md` 的差量 cProfile 归因（12 层/seq512/batch1，V100）
> 现状：每步 **3071 次内核发射**、**3890 次显存分配**，host 端 CPU ≈ 0.20 s（vs 墙钟 0.2156 s）
> 已做的开关级优化（1.0.22）：`TG_POOL_FAST` −1.4%、`TG_LAUNCH_TMPL2` −0.9%，合计 −2.2%
> 结论：开关级收益已榨干，下面是**结构性**方向。

## 2. 候选融合项（按"收益/风险"排序）

### F1 广播乘反向融合（**进行中**，子智能体 `fuse-bcast`）

* 现状：`prod = mul_bcast(g, other)` → `src = unbroadcast(prod)` → `_acc(grads, src)` = **3 个 kernel**
* 中间缓冲 `out_shape`（512×1024 fp32 = 2 MB）/次，约 200 次/步 ⇒ **≈800 MB/步**的写+读流量
* 做法：新 NVRTC 内核 `mul_bcast_sum` 一次算出 `unbroadcast(g*other)`；可再门控把 `_acc` 也融进去
* 预期：发射 −200~400 次/步，流量 −0.8 GB/步 ⇒ **墙钟 −2%~−4%**
* 风险：累加顺序必须与 `sum_axis` 一致才能逐位；否则收窄支持形状或接受 1e-6 级差异

### F2 `zeros()` 与"零初始化"融合（低成本候选）

* 244 次 `full`/步基本都来自 `zeros()`；多数用途是"先清零再累加"
* 做法 A：把「先 zero 再第一次写」改成"第一次直接写"（需要每个消费者知道自己是首次写）
* 做法 B：池里维护一批**常驻零缓冲**（只读），需要累加时用 copy
* 预期：−100~200 次发射；风险低但改动面广（消费者逐个确认），收益中等
* 风险：语义易错（坑：某处依赖"缓冲已清零"）

### F3 梯度累加批量化（`_acc`/`add_`）

* 366 次/步，全部来自 `_acc`。反向时每个 autograd 边各自发射一次累加
* 做法 A：把同一目标缓冲的多次累加合并（需要反向遍历时按目标分组）
* 做法 B：给常用模式做"融合进生产者内核"（如 matmul 反向直接写 += ）
* 预期：−200~300 次发射 ⇒ −2%~−3%；**改动面大、回归风险高**（涉及所有算子合约）
* 建议：在 F1 完成后，先只对 2~3 个热点算子做 B 方案

### F4 整层融合（最大收益，工期最长）

* 典型可融合模式：`RMSNorm + RoPE + QKV`、`SiTU-GLU`(gate/up/down 三 GEMM + 逐元素)、`softmax(scale + causal mask)`
* 预期：若把每层 20~30 次发射压到 8~12 次，整体可再拿 **10~15%**
* 代价：属"新算子开发"，每个都要对拍 + 多形状覆盖；建议按周排期，不宜混在答辩前
* 前置：先有 F1 这类小融合验证"逐位一致 + 有收益"的流程

### F5 CUDA Graph（已否）

* 32 GB 装不下 1.5B（arena 需 46 GiB）；分段捕获被"路由数据相关"否掉；历史 0.5B 复测仅 1.01×
* 详见 `docs/CUDA_GRAPH_FEASIBILITY.md`、`docs/HOSTOPT_ROUND2_2026-11-23.md` §5

## 4. 验收纪律（每一项都适用）

1. `ast.parse` + 相关 pytest 子集；
2. micro parity：新 vs 旧路径 `max_abs == 0`（做不到就收窄支持形状）；
3. 端到端：`TG_DETERMINISTIC=1` 下 4 步 loss/gnorm 字符串逐位相同；
4. 性能：`_v100_hs_ovl2.py` 3 轮中位，开关 off vs on，极差须不重叠；
5. 默认关（opt-in），文档写清支持矩阵与回滚；
6. 负结果同样入档（本仓库已有 MoE_DEV +1.7% 的先例）。

## 九点六、两件**不同**的事：TG Link 与后端混用

> 2026-11-12 更正：本 agent 曾把这两件事混为一谈。**它们是两个独立方向**，
> 层级不同、技术难点不同、判据也不同。下面按用户口径定义。
>
> ⚠️ **先读 `HARDWARE_INVENTORY.md`**：当前两台机器**各只有一半能力**
> （笔记本只有 Vulkan/AMD 核显；远端只有 CUDA/V100，Vulkan 枚举不到设备），
> 所以 **TG Link 的 P2P 假设目前无法验证 —— 不是代码没写，是硬件不具备**。

### A. TG Link —— 设备**之间**的通信

> **定义（用户口径）**：利用 **Vulkan 让显卡与显卡之间 P2P**，实现**多厂商交火**。

| 项 | 内容 |
| --- | --- |
| 层级 | 设备间（跨卡、跨厂商） |
| 关键手段 | Vulkan 外部内存/信号量（`VK_KHR_external_memory` + `_fd`/`_win32`、`_semaphore`） |
| 想达成的效果 | 跨厂商卡之间**不经主机中转**直接互传 |
| 若成立的价值 | 集合通信**少一次 PCIe 跳**（host-staged 是 A→host→B 两跳，有效带宽约减半）；真 P2P 是一跳 ⇒ 带宽/延迟约 **2×** 改善，且**不占主机内存**、不牵扯 CPU |
| **别高估：即使成立也不解锁 TP** | TP 需 NVLink 级（300+ GB/s），PCIe 3.0 x16 只有 10–12 GB/s，差一个数量级 —— 同厂商也没人用 PCIe 做 TP。所以 TG Link 的收益在 **DP/PP 的效率**，不是 TP |
| 若不成立的退路 | host-staged 集合通信（0.5B fp32 梯度 ≈1 GB/步 ÷ 10–12 GB/s ≈0.1 s，占 0.8 s 步时 ≈12%）|
| 相关文档 | `MULTIVENDOR_ROADMAP.md`（**注意**：该文把 TG Link 定位为 host-staged 层，那是**退路**，不是你的原始设想） |

### B. 后端混用 —— **一个进程里**用多种后端

> **定义（用户口径）**：**一个进程里使用多种不同后端训练模型**。

| 项 | 内容 |
| --- | --- |
| 层级 | 进程内（同进程多后端实例） |
| 关键难点 | `_CudaAPI` 是进程级单例；缓冲、显存池、CUDA Graph、fp16 影子缓存都假设单后端 |
| 想达成的效果 | 一张卡同时用 CUDA 与 Vulkan；或让不同算子落在不同后端 |
| 核心纪律 | 跨后端搬运必须**显式可见、可统计**，禁止隐式搬运（否则热循环里 10–100× 静默减速）|
| 当前状态 | **未设计、未实现**（`MULTIVENDOR_ROADMAP.md` 讲的是 A 的退路，不覆盖 B） |

### 与「多设备」的区分（别再一次搞混）

「同后端、多张 NVIDIA 卡、同进程」是**多设备**，它既不是 A 也不是 B：
`dist.py` 走的是**多进程**（每 rank 一进程），所以严格说 ORV 现在连"单进程多设备"也没有。

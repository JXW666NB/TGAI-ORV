# 真 AMP（激活 bf16 存储）的差距与计划

> L3 的三项收尾里，这一项**还没开始**。这份文件把它从口号变成"改哪些内核、怎么验收"。
> 数据由 `python tools/amp_readiness.py` 现场扫出，不是估计。

## 一、现状（实测）

| 事实 | 数值/说明 |
| --- | --- |
| matmul 是否支持 bf16 | ✅ **支持**：走 cuBLAS，`CUDA_R_16BF`，由 `TG_BF16=1` 打开（默认关） |
| 手写内核总数 | **81** |
| 其中接受 bf16 参数的 | **0** |
| 结论 | "激活存 bf16" 目前在引擎里**做不到**：内核只认 `float*` |

`TG_BF16=1` 现在解决的是"**算**用 bf16"，不是"**存**用 bf16" —— 两者对显存的意义完全不同：
真正省显存的是**激活/中间张量以 bf16 驻留**，否则 fp32 副本照样占满。

## 二、缺口按类别拆开（`tools/amp_readiness.py` 输出）

| 类别 | 内核数 | 支持 bf16 | 举例 |
| --- | --- | --- | --- |
| 逐元素（加减乘/激活） | 31 | 0 | `ewise_add`、`ewise_scale`、`ewise_mul`、`ewise_exp32` |
| 归一化 | 2 | 0 | `rmsnorm_fwd`、`rmsnorm_bwd` |
| 注意力 / softmax | 10 | 0 | `softmax_lastdim`、`log_softmax_lastdim(_bwd)` |
| 交叉熵 / 损失 | 4 | 0 | `ce_fwd_rows`、`ce_bwd`、`reduce_sum` |
| 嵌入 gather/scatter | 8 | 0 | `emb_gather_fwd`、`emb_gather_bwd`、`emb_bwd_hist` |
| 矩阵乘 / 转置 | 3 | 0 | `transpose2d`、`sgemm_mode` |
| 归约 / 其它 | 23 | 0 | `sum_axis8`、`permute8`、`swap_last2` |

**第一步只需要 41 个**（逐元素 31 + 归一化 2 + 嵌入 8）—— 它们都是"读进来、算、写出去"，
逻辑简单，加 bf16 变体的风险最低。

## 三、分阶段计划（每阶段都有可验收的门）

### S1 · bf16 驻留 + fp32 累加（41 个内核）

- 逐元素/归一化/嵌入内核加 bf16 变体：**读 bf16、用 float 算、写回 bf16**；
- 验收：
  1. 与 fp32 同配置的**同一份数据、同一 seed**，100 步内 loss 相对差 ≤ 1e-3；
  2. 峰值显存相对 fp32 **下降 ≥ 25%**（激活占大头时才会到这个量级；若不到说明还有别的 fp32 副本）；
  3. `python tools/amp_readiness.py` 里 bf16 内核数 > 0。

### S2 · 注意力/softmax（10 个）

- softmax 必须 **fp32 内部累加**（bf16 下 exp 溢出风险高）；
- 验收：单层 attention 输出与 fp32 版本相对误差 ≤ 1e-2（bf16 只有 8 位尾数，不能按 1e-5 要求）。

### S3 · 交叉熵（4 个）

- `ce_fwd_rows` 的 logits 求和必须 fp32；否则长词表（151936）下误差累积明显；
- 验收：与 fp32 的 CE 值相对差 ≤ 1e-3。

### S4 · 训练闭环 + 与 PyTorch 正面对决

- `TG_AMP=1` 一键开启；master weight 保持 fp32（现有 `Parameter` 已是 fp32，不用改）；
- 验收（对 L3 的原始要求）：
  1. **同模型同数据，bf16 训练 300 步的留出集 loss 不差于 PyTorch AMP 同配置**；
  2. 显存对比表（fp32 / 我们的 bf16 / PyTorch bf16）；
  3. 步速对比表（同上）。

## 四、风险（先说清楚，别到时候误判）

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| bf16 只有 8 位尾数 | 不能用 1e-5 这类判据衡量 | 判据按类别定（见上） |
| softmax/CE 溢出 | bf16 动态范围小 | 内部 fp32 累加 + 减最大值 |
| RMSNorm 的 `1/sqrt` | bf16 下精度损失明显 | 内部 fp32，只存不算是 bf16 |
| 梯度精度 | 反向对累加误差敏感 | **梯度与 master weight 一律 fp32**，只让激活 bf16 |
| 现有 `TG_BF16` 混淆 | 它只影响 GEMM 计算 | 新开关 `TG_AMP` 管存储，两者独立 |

## 五、为什么现在不做（如实说明）

需要 GPU 实测（显存/精度/步速），而 A10 现在被 24h 长稳占用，长稳是 L3 的另一项判据，
不能为了做这一项把那一项搞脏。长稳 22:11 结束后再排期，届时先做 S1 的验收 ①（精度）。

## 六、S1 进展（2026-10-31，第一步已完成的部分）

| 项 | 状态 | 证据 |
| --- | --- | --- |
| bf16 ↔ fp32 转换（round-to-nearest-even，纯整数位运算） | ✅ 已实现 | `python/tgai_go/train/amp.py` |
| 与 torch 的 bf16 转换位级一致 | ✅ **100.0000%**（20 万个随机值，含 1e-6~1e6 量级） | `tests/test_amp_bf16.py` |
| 往返误差是否在 bf16 理论精度内 | ✅ 实测 3.85e-3 ≤ **2^-8 = 3.9e-3** | 同上 |
| bf16 内核（`ewise_add_bf16` / `ewise_scale_bf16` / `rmsnorm_bf16`） | ✅ **NVRTC 编译通过**（rc=0，PTX 489,270 B） | `tools/amp_compile_check.py` |
| GPU 上执行 / 端到端精度 / 显存收益 | ❌ 未做（长稳占用 A10） | 待 22:11 后 |

### 两个实现要点（都踩过）

1. **不能 `#include <cuda_bf16.h>`** —— 引擎内核是一整段 NVRTC 字符串，没配 `-I`，
   加了就编不过。所以 bf16 用位运算实现：bf16 就是 float32 的高 16 位。
2. **舍入必须是 RNE，不能截断** —— 截断有系统性向零偏置（`tests/test_amp_bf16.py`
   里有反证：截断的误差均值明显为负，RNE 才是对称的）。

### 一处判据纠正（写下来避免再犯）

bf16 是 **1 符号 + 8 指数 + 7 位显式尾数**，加 1 位隐含 ⇒ **8 位有效位**，
所以 RNE 的最坏相对误差是 **2^-8 ≈ 3.9e-3**，不是 2^-9。
我第一版测试按 2^-9 判，把正确实现判成了失败 —— 判据写错和实现写错一样危险。

### 编译验证为什么不占 GPU

`nvrtcCompileProgram` 只需要 libnvrtc，**不需要设备、不分配显存**。
所以长稳占卡时也能做"能不能编过"这件事，避免等真机跑训练才发现语法错。

## 8. V100 上的显存构成实测（2026-11-01）——这决定了 AMP 值多少

**配置**：Qwen2.5-0.5B（494.0 M 参数）、batch 2、seq 256、fp32 权重 + AdamW、V100-32GB。
用 `nvidia-smi` 在四个检查点采样（GiB，扣掉产线推理服务占用的 14.83）：

| 阶段 | 累计增量 | 说明 |
| --- | --- | --- |
| 权重上卡 | **+3.97** | 而 494M fp32 只需 **1.84** ⇒ 有约 2 GiB 的额外分配（见下） |
| AdamW 的 m/v | +6.02 | m+v 理论 3.69，实测多出约 0.5（fp64 中间量/缓存） |
| 跑一步（激活+反向图） | **+12.87** | 这一步的增量里激活占大头 |
| 峰值（`tools/mem_profile.py`） | **16.5 GiB** | 与上表一致（20 步采样） |

**AMP（bf16 激活存储）能省多少**：
- 激活部分 ≈ 12.87 − 6.02 = **6.85 GiB**；
- 激活改 bf16 存储 ⇒ 理论省 **≈3.4 GiB**（约峰值的 21%）；
- 权重/梯度/优化器若也走 bf16 还能再省约 1.8 GiB，但那会改变数值行为，需单独验证。

**一处浪费：修了，但只有一半效果（如实记录）**

`Qwen25.__init__` 原先先建 `T.nn.Embedding(V, D)`（0.5B 模型 = 545 MB 随机表），
下一行就把 weight 换成共享 Parameter —— 白分配。已加 `Embedding(weight=)` 修掉。

复测（同一脚本、同一配置）：

| 阶段 | 修复前 | 修复后 |
| --- | --- | --- |
| 权重上卡增量 | +3.97 GiB | **+2.56 GiB**（省 1.41 GiB） |
| 跑一步后峰值增量 | 12.87 GiB | **12.87 GiB（不变）** |

⇒ 加载期少占 1.4 GiB（对"卡刚好不够"的场景有用），但**稳态峰值没有下降**
（分配器把省下来的块复用给了后面的激活）。这条是实测推翻了原先"至少省 545 MB 峰值"的推断。

## 9. 为什么 bf16 的"计算加速"在 V100 上验不了（如实记录）

V100 是 **sm_70（Volta）**，硬件只有 fp16 Tensor Core，**没有 bf16**；
cuBLAS 的 `CUDA_R_16BF` 需要 **sm_80+**（A100/A10/4090）。

所以在这台机器上能验的是：
- ✅ bf16 的**存储**路径（存 bf16、算 fp32），任何架构都能跑；
- ✅ bf16 与 torch 的**位级一致**（已验：20 万个值 100.0000%）；
- ✅ 三个 bf16 内核的 **NVRTC 编译**（rc=0，PTX 489,270 B）；
- ❌ bf16 的**吞吐/加速比** —— 必须 sm_80+ 硬件。

结论：AMP 的"能不能省显存"可以在这类卡上验，"快多少"必须换卡。
判据里写的"bf16 正面对决 ≥ PyTorch"只能等 sm_80+ 的机器，**不拿 V100 的数据凑**。

## 10. 真正打不过的是**显存**（2026-11-01 实测，应作为下一阶段第一优先级）

### 10.1 实测

| 形状（Qwen2.5-0.5B，fp32 + AdamW） | 活张量峰值 | 结果 |
| --- | --- | --- |
| B=1 / S=256 | 8.84 GiB | 通过（0.22 s/step） |
| B=4 / S=512 | **29.92 GiB** | **OOM**（设备 31.86 GiB 仍不够） |

### 10.2 理论值是多少（自己算的）

| 组成 | 字节 |
| --- | --- |
| 权重 fp32 | 1.84 GiB |
| 梯度 fp32 | 1.84 GiB |
| AdamW m+v | 3.69 GiB |
| 激活（24 层，B=4/S=512 估） | ≈3.6 GiB |
| logits + CE 中间量（B*S*V = 4×512×151936） | ≈3.7 GiB |
| **合计** | **≈14.7 GiB** |

实测 **29.92 GiB ≈ 理论的 2 倍**。也就是说：**不是模型大，是我们自己的内存管理粗**。

### 10.3 三个最可疑的来源（按预期收益排序）

1. **词表维度的大张量没分块**：`logits`、softmax 概率、`grad_logits` 各 `B*S*V*4` 字节，
   B=4/S=512 时每个 1.24 GB，三份就 3.7 GB。改成**按 token 分块的 CE**
   （一次只算 chunk 大小的 logits）可省 2~3 GB。
2. **自动微分保存了过多中间量**：每层 q/k/v、SDPA 的注意力概率、MLP 的 g/u 全留着。
   `T.checkpoint` 已实现且能逐层用（`cfg["GRAD_CKPT"]=True`），但**只在小形状下测过**——
   在大形状下它正好是解药（每层重算换显存）。
3. **分配器缓存只增不减**：`_pool_cached_bytes` 实测 4.22 GiB 常驻。

### 10.4 结论

> bf16（AMP）是在"已经很省"的基础上再省一半；
> 而我们现在的问题是**先多花了一倍**。所以顺序应该是：
> **① 分块 CE + ② 大形状下打开检查点 + ③ 池子回收** → 再谈 bf16。

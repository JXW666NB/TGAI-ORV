# 【已定案】数据并行下各 rank 的 gnorm 不一致

**结论（2026-11-21 15:15，2×4090 实测）**：**不是** gnorm 的计算问题，也不是浮点舍入。
真正的根因是 —— **「反向即归约」(`dp_overlap`) 路径根本没有做真正的梯度归约**：
它报 `comm=0.00ms`、`pending_zeroed=True`（看起来完全正常），但普通 `all_reduce_grads`
一次都没被调用，于是数据并行静默退化成「各卡用自己的本地梯度」。

## 决定性证据（同配置、同数据、同 4 步，唯一变量 `TG_DP_OVERLAP`）

| 配置 | 普通 `all_reduce_grads` 调用 | `[dp-ov] comm` | rank0 gnorm | rank1 gnorm | 逐位相同 |
| --- | --- | --- | --- | --- | --- |
| `TG_DP_OVERLAP=0` | 每步 1 次（共 4 次）| 无 | 10.740522953 / 9.803510496 / 9.168341559 / 9.538912535 | **完全相同** | ✅ |
| 默认（重叠开）| **0 次** | **0.00 ms** | 13.999368381 / 13.162478461 / 13.079501682 / 13.260794219 | 14.150760353 / 13.255153014 / 12.628965454 / 13.081686576 | ❌ 相对差 1e-2 |
| 默认（**修完后**）| 每步 1 次 | 无 | 10.741 / 9.804 / 9.168 / 9.539 | 同上 | ✅ |

两组的 gnorm **量级都不同**（10.7 vs 14.0）——"归约过的梯度范数"和"没归约的本地梯度范数"
本来就该不同，这正是最直接的旁证。

## 处置（已落盘）

1. **`v3_pretrain._overlap_enabled()`：改默认关（opt-in）**。
   只有显式 `TG_DP_OVERLAP=1` 才走重叠路径；其余一切情况（含未设置）都走普通的
   「反向结束后一次性 all_reduce」。10 条测试钉住这个默认值。
2. 端到端验证：**不设任何环境变量**跑 2 rank × 4 步 ⇒ 两 rank gnorm 逐位相同，
   且与"显式 `TG_DP_OVERLAP=0`"完全一致（10.741/9.804/9.168/9.539）。
3. `bf16 + 重叠` 更早被 `bf16grad` 实测为 gnorm 偏大 4.6×，已在 `begin_overlap()` 里
   对低精度直接返回 None + WARN —— 与本文是**同一处缺陷的不同表现**。

## 还剩什么

* 重叠路径本身**仍然是坏的**，只是现在默认不走。要修它，先加一条"归约必须真的发生"
  的自检（例如 `comm_ms <= 0.5` 且 `world > 1` 时直接 raise），再谈性能。
* `docs/DP_OVERLAP_2026-11-21.md` 里那些"重叠把 seq512 从 0.84× 提到 1.10×"的数字
  **需要重新审视**：如果当时归约没有真的发生，那"速度提升"就是假的（少做了工作当然快）。

**第 3 次**（加 `--dp 2`）：两 rank 都 rc=0，
```
rank0: 13.997000782  13.193862899  13.099180566  13.227820493

step0 |Δ|=1.372e-01 相对 9.80e-03   ← 注意这是 step0
```

**step0 就已经差 1%**。而 step0 的权重是同一份（同 seed + `broadcast`），
梯度归约之后两个 rank 拿到的是**同一个平均值** ⇒ gnorm 必须相同。
差 1% 恰好是"**两个 rank 各自的本地梯度范数**"的量级 ⇒ **最可能是归约根本没发生**，

## 为什么这算 bug

`python/tgai_go/train/v3_pretrain.py:1625` 的注释写得很明确：

> ★ 必须在裁剪**之前**归约：否则 gnorm 只是本 rank 的范数

也就是说归约发生在 `clip_grad_norm_` 之前，**归约之后两个 rank 的梯度缓冲应当逐位相同**
⇒ gnorm 必须逐位相同。现在不同，说明两个 rank 归约出来的梯度**不是同一个数**。

`--zero 2` 自己是逐位一致的（0/20），可见问题不在"分片数学"，而在
**`dist.all_reduce_grads` 的 host 路径**（`--zero 1` 复用它，所以一起出错）。

## 我怀疑的三条（**都还没验证**，按可能性排序）

1. **d2h 之前没有设备同步**。host 路径是「GPU 内打包 → 分块 d2h → 共享内存」。
   如果打包内核与 d2h 之间缺一次同步（或两者不在同一条流上），
   某个 rank 可能把**还没写完**的梯度发出去 ⇒
   rank0 看到 `g0 + g1(略旧)`、rank1 看到 `g1 + g0(略旧)` ⇒ 两边和不同。
   这与观测到的 **6e-6 量级**吻合（只差最后几个 bit）。
2. **本地梯度本身不对称**。MoE 反向用 `atomicAdd`，rank0 与 rank1 的**本地**梯度
   在最后几位就不同。这对"求和"不致命（`a+b` 可交换），但会放大任何同步问题的后果。
3. **分块边界 + 中途 barrier** 让某些块在某个 rank 上读到上一块的数据。
   （打包缓冲是复用的，`pack` 在 d2h 之后又被当作对端数据的落点。）

## 怎么验证（下次有 GPU 时，≤10 分钟）

1. 2-rank `--zero 0`、4 步、`TG_DP_TIMING=1`，把**两个 rank 的 gnorm 与 `pack`/`d2h` 各阶段耗时**一起打出来
2. 在 d2h 之前插一次 `rt.sync()`（环境变量开关），再跑同样 4 步：
   - **如果 gnorm 变逐位相同 ⇒ 就是第 1 条**（缺同步）
   - 如果仍不同 ⇒ 转为查第 3 条（分块/chunk 设 1 块试一次）
3. 对照组：`TG_DP_GRAD_DTYPE=bf16`（bf16grad 的路径）与 `--zero 2`（zero2 的路径）
   都不经过这段 host 打包，若它们逐位一致，就把范围锁死在 host 打包路径

## 影响面（诚实评估）

* 影响：**同一个训练里，两张卡看到的"梯度范数"不完全一样**。裁剪阈值因此有一点点差异
  （相对 6e-6），对收敛的实际影响极小，但**"各 rank 逐位一致"这条性质被破坏了**，
  而它是查其他 bug 的基准线（这一轮已经靠它抓到过两次真问题）。
* 不影响：单卡、`--zero 2`、NCCL 后端路径（待确认）。

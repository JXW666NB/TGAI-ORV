# ORV 现状与生态参与指南

> 面向**想帮忙的人**。目的：让你在 10 分钟内知道「现在已经有什么 / 缺什么 / 我能干什么」。
> 数字来自 `docs/CAPABILITY_AUDIT.md`（脚本从源码与测试直接扫描，可复核）。
> 本文所有陈述带状态标记：**【已验证】/【已实现未验证】/【未实现】**。

---

## 1. ORV 是什么

纯 Python 写的自动微分 + 训练引擎，**不依赖 PyTorch**，直接走 CUDA Driver API + cuBLAS + NVRTC。
包名 `tgai-orv`，import 路径 `tgai_go.train`。

**和 PyTorch 的关系**：ORV 从 TGAI GO（推理引擎）长出来，GO 可以理解为只保留推理的精简版 ORV。

**已经确定的差异化**（有实测，不是宣传词）：

| 项 | 数字 |
| --- | --- |
| 3B MoE（2.97B）全参一步 | **709 ms / 峰值 24.78 GiB**（V100 32GB）|
| 同条件下 PyTorch | 在 1.997B 就 **OOM**（31.40 GiB 已分配）|
| 数值一致性 | 8 步 loss 1.44e-07；Qwen2.5-0.5B vs HF 6.29e-06 |
| 可复现训练 | 两次训练逐位一致，代价约 1%（PyT 结构上做不到）|

## 3. 想帮忙，从哪下手（按门槛排序）

### 门槛低：写算子插件（不用碰核心）

```python
from tgai_go.train import plugin
import tgai_go.train as T

@plugin.op("softplus")            # 组合式：autograd 自动，不用写反向
def softplus(x):
    return (x.exp() + 1.0).log()
```

**适合**：科研函数（fft/svd/特殊函数）、图形学算子、自家模型的私有算子。
**参考**：`docs/PLUGINS.md`；规范见 `docs/PLUGIN_CHARTER.md` §4。

### 门槛中：写 C 端算子插件（要性能）

四条通道，从"完全不写 Python"到"一行绑定"：

| 通道 | 需要 Python | 适合 |
| --- | --- | --- |
| `plugin.load_manifest(json)` | ❌ 完全不需要 | 已用 nvcc 编好库 |
| `plugin.op_c(lib, symbol)` | 一行 | 有现成 `.so` |
| `plugin.op_native(src, entry)` | 一行 | 想写 CUDA C 但不想装工具链 |
| `plugin.op(fn)` | 是 | 组合已有算子 |

**参考**：`docs/PLUGIN_NATIVE.md`。**注意**：加载原生库 = 执行任意机器码，无沙箱。

### 门槛中：补后端

`backend.py` 定义了 233 个后端方法，其中训练路径常用 **79 个**，最小 dense 后端只需 **45 个**。
`missing(inst)` 会告诉你还差哪些。**参考**：`docs/BACKEND_PORTING.md`、`docs/DESIGN.md` §6。

### 门槛高：DSL 代码生成器

**参考**：`docs/PLUGIN_DSL.md`（设计）、`PLUGIN_CHARTER.md` §3（契约）。
先读宪法 §3 的三条硬要求，再动手。

### 不需要写代码的方向

- **在更多硬件上跑一遍并报告**：A100/H100、AMD、老 Pascal 卡、国产卡 —— 目前只有 V100 的实测数据
- **双卡验证**：按 `DP_2GPU_RUNBOOK.md` 跑，报加速比
- **热门模型迁移尝试**：7B 以上模型目前【未验证】
- **文档纠错**：发现文档与代码不一致就提 issue，这个项目文档很多，必然有漂移

## 4. 参与前必须知道的五条纪律

1. **不把"跑通了"当"验证了"**。必须给出可复现命令与数字。
2. **不把"未验证"写成"已支持"**。拿不到硬件的项就标【未验证】。
3. **错误信息必须写清「哪个对象 / 什么条件 / 怎么修」**。有 AST 门禁测试强制检查。
4. **热路径不许有 Python 逐元素**。能下沉到原生就下沉（宪法 §4.1）。
5. **插件不得改变核心数值语义**（dtype 提升、累加顺序、边界行为）。更快可以，更准/更省事地不同不行。

## 5. 后端混用（用户想法 · 只有设计）

### 5.1 目标

一张卡同时支持 CUDA 与 Vulkan；或两张异构卡（N 卡 + A 卡）。
让每个后端做自己擅长的事：例如 **V100 算反向，GT730 跑脏活**。

### 5.2 必须先有的地基（现在没有）

| 缺什么 | 为什么必须有 |
| --- | --- |
| **设备描述符** `(backend, device_index)` 挂在每个 buffer 上 | 现在后端是全局单例（`_CudaAPI`），一进程只能一个后端 |
| **显式跨后端搬运** `copy_to(dst)` | 零拷贝（同卡 CUDA-Vulkan interop）/ 同厂 P2P / 主机中转，三级 |
| **按设备分派** | 一个算子的输入在不同设备上时，要么切分、要么**报错** |

### 5.3 三条硬约束（比功能更重要）

1. **隐式跨后端拷贝是头号杀手。** 框架一旦"体贴地"帮你搬数据，用户会在热循环里
   得到 10~100× 的静默减速且看不出来。⇒ **搬运必须在代码里显式可见，且可统计。**
2. **异构卡之间没有 P2P。** NVIDIA ↔ AMD 必须主机中转。所以"两张异构卡"只能做
   **流水线并行**，做不了张量并行。
3. **不同厂商数值不同。** fp32 累加顺序、FMA、归约实现都不一样。混用后同一次训练
   里不同层的舍入方式不同，**可复现性会变差**，必须记录"这层跑在哪个后端"。

### 5.4 关于「自动防 OOM」

用户想法：某张卡显存快炸时，立刻调度到别的卡。

**技术上可行，但要小心**：显存压力是**运行时才知道**的，而搬数据的代价可以远大于收益。
所以合理形态是：

- **训练前**：用 `doctor.py` 算出"这张卡能训多大模型"（静态规划）
- **训练中**：只在**明确的边界**（层结束、优化器步）做迁移，不在 kernel 中途
- **必须有日志**：每次迁移记一行"第 N 层从 dev0 迁到 dev1，代价 X ms"

### 5.5 建议的落地顺序

1. 设备描述符 + 显式 `copy_to` + **拒绝隐式跨设备**（正确性优先，哪怕只能主机中转）
2. 同卡 CUDA-Vulkan interop 零拷贝（性能）
3. 异构流水线（场景最窄，最后做）
4. 自动防 OOM 调度（依赖 1、2 都稳了才谈）

**注意**：第 1 步是**多卡的前置条件** —— 多卡本质就是"多个 device"。
所以做多卡接口预留时顺便就把混用的地基打了。

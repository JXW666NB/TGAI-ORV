> 2026-11-13。本文只记录**实测**；估算单独标注。目标是对比 ORV 与 PyTorch 的显存/速度/loss，
> **同口径、同参数，不为让谁跑通而便宜任何一方**。

**拿旧标记语料训练 = 在测格式不匹配，不是在测性能。**

## 2. 全参训练的显存账（按 2.999B 精确算，不含激活）

| 方案 | 权重 | 梯度 | Adam m | Adam v | 合计 |
| --- | --- | --- | --- | --- | --- |
| fp32 全套（两家默认）| 11.18 | 11.18 | 11.18 | 11.18 | **44.7 GiB** ✗ |
| fp32 权重/梯度 + fp16 状态 | 11.18 | 11.18 | 5.59 | 5.59 | **33.5 GiB** ✗ |
| **fp16/bf16 权重+梯度+状态** | 5.59 | 5.59 | 5.59 | 5.59 | **22.35 GiB** ✓ |

32 GB 卡（可用 31.86 GiB）只有**第三种**放得下，且还要留激活。

## 3. 实测结果（这是本文最硬的部分）

### PyTorch 2.6.0+cu124：**全参不可行**（三档全 OOM）

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 16.00 MiB.
GPU 0 has a total capacity of 31.86 GiB ... 31.32 GiB is allocated by PyTorch
  File "torch/optim/adamw.py", line 175, in _init_group
    state["exp_avg_sq"] = torch.zeros_like(...)
```

**死点很关键**：模型与梯度都建成了（31.32 GiB 已分配），崩在为动量/二阶矩分配 **fp32** 状态那一步。
seq 512 / 1024 / 2048 **全部同样失败** ⇒ 不是序列长度问题，是优化器状态本身放不下。

### ORV 0.9.62（pip 安装）：**默认配置同样不可行**

```python
def make_optimizers(self, lr=1e-5, **kw):
    return [T.optim.AdamW(self.params_of(i), lr=lr, **kw) for i in range(self.NL)]
```

`V27Trainer` 默认用 **fp32 AdamW**，且参数以 fp32 存放 ⇒ 44.7 GiB，三档同样 OOM。
**换成 `Fp16MomAdamW` 也只能到 33.5 GiB，仍放不下** —— 因为权重与梯度还是 fp32。

## 4. 结论：两家都撞墙，但墙的性质不同

| | 撞墙原因 | 能否改 |
| --- | --- | --- |
| PyTorch | 原生 `AdamW` 只有 fp32 状态 | 只能外挂（bnb 8-bit / DeepSpeed / 手写），不是原生能力 |
| ORV | `V27Trainer` 目前 fp32 参数 + fp32 AdamW | **能改**：把权重/梯度/状态降到 fp16 即 22.35 GiB |

所以"打 PyTorch 屁股"这一条，**胜负不在跑分，在能否起跑**：PyTorch 原生到不了 22.35 GiB 这条线；
ORV 差一次训练器改动。这也正是"还需要优化什么"的第一条答案。

## 5. 同口径口径（下一阶段必须遵守）

| 项 | ORV | PyTorch |
| --- | --- | --- |
| 权重 / 梯度 / Adam 状态 | fp16（或 bf16）| 同左 |
| 主权重（fp32 master）| **无** | **无** |
| 优化器 | `Fp16MomAdamW` | **手写**同精度 AdamW（不用 `torch.optim.AdamW`）|
| logits / CE | fp32 | fp32 |
| 激活检查点 | 开 | 开 |
| batch / seq / lr / steps / 数据 | 1 / {512,1024,2048} / 1e-5 / 10 / 同一份 `.npy` | 相同 |

**任何一侧改精度，另一侧必须同步改**；某一档只在一侧 OOM 不允许调参过关，必须报"该档不对称失败"。

## 6. 还缺什么（未完成）

### 6.0 一个被实测推翻的前提（重要，先看这条）

我原以为"给 `V27Trainer` 加 `param_dtype='fp16'` 就能把权重降到半精度"。**实测不成立**：

```
TypeError: CUDA cat 目前只支持 float32，收到 float16。
修法：本引擎张量统一 float32；需要低精度请用 rt.fp16_gemm，而不是改 dtype
```

**ORV 的张量语义就是 float32**，fp16 只存在于 GEMM 内部（`rt.fp16_gemm`）。参数一旦按 fp16 存，
`cat` / matmul / 反向这些算子直接拒收。所以：

* 0.9.63 加的开关**在 0.9.64 里改成早失败**（`NotImplementedError` + 修法），
  不让用户撞到深层 `cat` 崩；
* **"把权重存成 fp16"不是加开关能解决的**，它要求核心算子支持半精度张量存储 —— 一个后端工程。

### 6.1 由此得到的真实边界

| 引擎 | 全参 2.999B 在 32 GB V100 | 依据 |
| --- | --- | --- |
| PyTorch 原生 | **不可行** | fp32 优化器状态 39.11 GiB，实测 OOM 于 `AdamW._init_group` |
| ORV 0.9.62/0.9.63 | **不可行** | 张量统一 fp32 ⇒ 权重 11.18 + 梯度 11.18 + fp16 动量 11.18 = **33.5 GiB**，仍超 31.86 |

**结论：在当前两家引擎上，2.999B 全参训练都放不进 32 GB V100。** 这不是调参问题，是存储语义问题。

### 6.2 还需要优化什么（这就是答案）

1. **让核心算子支持 fp16/BF16 张量存储**（cat / matmul / norm / 反向 / 优化器缓冲）。
   这是唯一能把 33.5 GiB 压到 22.35 GiB 的路径；只改优化器或只改 GEMM 都不够。
2. 在此之前可行的省显存手段（都不改变"全参"性质，但要么慢、要么改并行方式）：
   梯度检查点（省激活）、优化器状态分片/offload（省状态）、更小 batch。
3. PyTorch 侧要跟上同一口径，同样得外挂（bnb 8-bit / DeepSpeed），**不是原生能力**。

### 6.3 仍未完成

* 三档的**显存 / 每步耗时 / tok·s⁻¹ / 逐 step loss** 目前**一个有效数字都没有**；
* 语料与两侧权重对齐已完成（见 §1），可直接在具备 ≥34 GB 显存的卡上复跑；
* **别引用任何"ORV 比 PyTorch 快 N 倍"的说法** —— 没有任何数据支撑。

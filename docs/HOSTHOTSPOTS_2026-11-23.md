# ORV 稳态每步 host 时间花在哪（V100 差量 cProfile）

> 实测 2026-11-23　｜　V100-PCIE-32GB（TCC）｜　ORV **1.0.21**　｜　12 层 / d=1024 / E=4 / d_ff=3328 / vocab=96000 / batch=1 / seq512 / `--amp off`
> 方法：`cProfile` 分别跑 **4 步** 与 **20 步**，两份 profile **逐函数相减 ÷ 16**，
> 得到"稳态每步"热点（一次性初始化被消掉）。
> 交叉校验：同配置墙钟/步 **0.2204 s**、CPU/步 **0.2586 s**、GPU 利用率 **23.0%**。

---

## 1. ORV 稳态每步热点（self time，profile 有膨胀，比例可信）

| 热点 | self/步 | 次数/步 | 单次代价 | 归属 |
| --- | ---: | ---: | ---: | --- |
| `d2h`（设备→主机回读）| **0.0501 s** | **26** | **1.9 ms** | 标量回读（loss/gnorm/lr/timing）|
| `launch` | **0.0426 s** | **3071** | 13.9 µs | 每次算子发射 |
| `sync`（全局同步）| **0.0224 s** | 2 | 11 ms | 每步 2 次强制同步 |
| `_sgemm` | 0.0152 s | 578 | 26 µs | 小 GEMM 发射 |
| 池分配族（`_alloc`/`_pool_release`/`empty`/`_pool_take`/`_pool_checkout`/`free`）| **0.0438 s** | 3890 | ~11 µs | 显存池记账 |
| Tensor 对象（`__init__`/`__del__`/`_cuda`）| **0.0223 s** | 4680 | ~5 µs | 包装对象创建/析构 |
| `_bmm_op` | 0.0098 s | 357 | 27 µs | 批量矩阵乘 |
| launch 参数生成 `genexpr`(cuda.py:5751) | 0.0048 s | **39274** | 0.12 µs | 每次发射拼参数 |
| `getattr` / `dict.get` | 0.0122 s | 58k / 30k | — | Python 属性查找 |
| **合计（列出的）** | **≈0.24 s/步** | | | 占实测 0.259 s 的绝大部分 |

### 三个直接的"离谱点"

1. **每步 26 次 D2H**：单次 1.9 ms（含隐式同步等待）⇒ 0.05 s/步，**占 host 时间 19%**。
2. **每步 3071 次 launch**、单次 13.9 µs；而 `docs/DISPATCH_BOUND.md` 实测纯 `cuLaunchKernel` 只要 **4.39 µs**
   ⇒ 每次多花约 9.5 µs 在 Python 记账/参数拼装上（`genexpr` 每步被调 **39274 次**）。
3. **每步 2 次全局 `sync()`**（各 11 ms）+ **每步 3890 次池取/还 + 4680 次 Tensor 包装**
   ⇒ 纯记账开销 ≈ 0.066 s/步（占 26%）。

## 3. 结论：利用率低不是"0 日 BUG"，是这个规模下的 launch-bound

* 我们和 PyTorch **都是**每步要发几千个短 kernel、并且每步做若干次同步/回读；
  GPU 在 host 记账期间无活可干 ⇒ 利用率只有 23%（ORV）/ 33%（PyT）。
* 证据：seq 512→2048 时两边利用率同步上升（ORV 23%→45.7%，PyT 33%→58%），
  因为 kernel 变长、host 占比下降 —— 典型的 launch-bound 曲线。
* batch 扫描（ORV，seq512）：batch 1→4，`cpu/wall` 仍是 1.02~1.05，利用率 15%→32.5%，
  `wall/1k tok` 0.382→0.325 s ⇒ 加密 batch 只能摊薄部分固定开销，host 仍是瓶颈。
* 所以：**优化方向是砍 host 开销，不是换卡、也不是先磨 kernel。**

## 4. 可落地的修复项（按收益/风险排序）

| # | 动作 | 预期收益/步 | 风险 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | **合并/降低 D2H**：loss、grad-norm、lr、timing 等标量改为「每 N 步一次」或「打包成一条 d2h」 | **~0.04–0.045 s** | 低 | 26 → 2 次即可 |
| 2 | **去掉每步 2 次全局 `sync()`**：只在记录/存档边界同步 | **~0.02 s** | 低 | 需确认没有隐藏依赖 |
| 3 | **launch 快路径**：预建参数模板（避免每次拼 39k 次 genexpr），把 13.9 µs 拉回 ~4.4 µs | **~0.025–0.03 s** | 中 | `TG_LAUNCH_FAST` 开关已存在，需验证是否覆盖全部算子 |
| 4 | **显存池/对象复用**：Tensor 包装对象缓存、减少 empty/free 往返、池记账合并 | **~0.02–0.03 s** | 中 | 3890 次/步 → 目标 <1000 |
| 5 | **CUDA Graph**（把 3071 次发射压成一次图执行）| 潜力最大（~0.15 s+） | 高 | 见 `CUDA_GRAPH_FEASIBILITY.md`；训练动态形状/池地址是难点 |
| 6 | 减少逐参数 Python 算子（对齐 PyTorch 的 clip/norm 批处理）| ~0.005 s | 低 | 我们这方面已比 PyT 少 |

> 1–4 合计可望把每步 host 从 **0.26 s 降到 ~0.15 s**（≈1.7×），GPU 利用率随之抬升；
> 到那时才会真正进入"kernel 质量决定墙钟"的区间——那时 P100（0.78×）那类问题才变成主矛盾。

## 6. 局限

* cProfile 会膨胀耗时（本页比例可信、绝对值不可直接引用）；真实绝对值以
  `docs/HOSTSHARE_V100_2026-11-23.md` 的 Job 对象测量为准。
* 只有 V100 / Windows(TCC) / 单一配置；未做 4090/5090/P100 对照。
* `1.9 ms/次 d2h` 含隐式同步等待，不能全归为拷贝成本。
* 未逐个验证第 4 节修复项的实际收益（均为按结构推算）。

## 7. 修复尝试与实测（2026-11-23 当天）

### 7.1 `TG_LAUNCH_FAST`：**默认本来就是开启的**，关闭才是回退路径

代码里 `cuda.py`（M8 段）明确写「默认开」，`TG_LAUNCH_FAST=0` 才退回旧通用路径。
所以下面这组 5 轮中位，测的其实是「**关掉它要付多少代价**」，
而不是「开启能赚多少」——历史所有基线数字（≈0.22 s/步）**已经含这个优化**。

| seq | `TG_LAUNCH_FAST=0`（关闭=回退）| `TG_LAUNCH_FAST=1`（默认）| 差异 |
| --- | ---: | ---: | --- |
| 512 | 0.2691 s（5 轮中位，0.2403~0.3117）| **0.2234 s**（0.2209~0.2275）| **默认快 17%**，极差完全不重叠 |
| 2048 | 0.7241 s（0.7201~0.7561）| 0.7185 s（0.6896~0.7628）| ±1%，无差别 |

* 与 launch-bound 模型一致：短序列（GPU 利用率 25%）收益大，长序列（50%）消失。
* **正确性**：`TG_DETERMINISTIC=1` 下关/开两配置逐 step loss **逐位完全一致**，且各自可复现。
* 结论：**无需任何默认值改动**；该开关请勿在生产环境设为 0。

### 7.1b 与 PyTorch 的对照（同配置，多次稳定）

| 侧 | seq512 | seq2048 |
| --- | ---: | ---: |
| ORV（默认）| **0.2234 s** | 0.7185 s |
| PyTorch（eager，无 amp）| 0.384 s | 0.858 s |
| 加速比 | **1.72×** | 1.19× |

### 7.2 每步 `sync()` 关闭（本次新增开关 `TG_STEP_SYNC=0`）

* 单轮实测：`TG_STEP_SYNC=1` 0.2464 s vs `=0` 0.2485 s ⇒ **无可测收益**。
  原因：GPU 本来就大半空闲，`sync()` 等待时间接近 0，其成本只是几十 µs 的调用；
  cProfile 里 11 ms/次是**采样膨胀**，据此判断会误判。
* 因此该开关**默认保持开启**（`TG_STEP_SYNC` 缺省=1，行为与 1.0.21 一致），
  仅在需要测"纯发射吞吐"时关掉；关掉后日志 `sec/tok_s` 变成发射时间，不可当真实步时。

### 7.3 修正一处此前的误判

§1 表格里的 `sync 0.0224 s/步`（2 次 × 11 ms）是 cProfile 膨胀值；
真实成本接近 0（见 7.2）。**d2h 与 launch 的占比仍然成立**（有独立 A/B 支撑）。

### 7.4 剩余最大的可优化项

1. **MoE 路由的 D2H**：每步 24 次 `to_numpy()` 来自 `route_topk`(15) 与反向 `bw`(15)——
   因为专家分派是**主机侧**驱动的，必须把 top-k 下标读回主机。要消掉需要改成设备端分派
   （`moe_permute` 类内核），属于架构级改动，风险高、收益大（每步最多 ~0.05 s）。
2. **显存池 / Tensor 包装对象**：3890 次取还 + 4680 次对象创建/析构 ≈ 0.04~0.06 s/步，
   可通过对象缓存与池记账合并削减。
3. **CUDA Graph**：把 3071 次发射压成一次图执行，但训练侧动态形状/池地址是难点。

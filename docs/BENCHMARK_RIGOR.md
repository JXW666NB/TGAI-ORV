# 性能测量口径纠正（2026-11-03）——此前「快 1.38×」是错的

## 1. 错在哪

之前的基准脚本在**每一步内部**都读了一次 loss：

```python
loss = cross_entropy(...)
ls.backward(); opt.step(); opt.zero_grad()
loss_val = float(loss.to_numpy())     # ← 这里：D2H + 整设备同步
```

`.to_numpy()` 会把 loss 从显存拉回主机，**强制同步**，把异步流水线打断。
它把每一步的「最后一个 kernel 到提交完成」之间的空隙也算成了计算时间，
于是**虚增约 10~15%** 的步时；在 kernel 数多、单步短的情况下更明显。

## 2. 正确口径

循环内**不读任何设备标量**，只在整段循环后 `sync()` 一次：

```python
for _ in range(N):
    step()            # 全程异步
rt.sync()             # 只在这里同步
```

## 3. 纠正后的数字（V100 / Qwen2.5-0.5B / B=4·S=512 / 6 步平均）

| 配置 | 本次（无内联同步） | 旧（有内联同步） | 差异 |
| --- | --- | --- | --- |
| 我们 fp32 | **683.9 ms** | 749.5 ms | −8.7% |
| 我们 fp16 | **389.3 ms** | 441.9 ms | −11.9% |
| PyTorch fp32 | **621.0 ms** | 609.8 ms | +1.8% |
| PyTorch AMP | **219.5 ms** | 219.5 ms | 0% |

> PyTorch 那两项本来就没在循环里读 loss，所以几乎不变（这也验证了「是口径问题，不是机器变快」）。

## 4. 结论（以此为准）

| 对比 | 事实 |
| --- | --- |
| 我们 fp32 vs torch fp32 | **我们慢 1.10×**（683.9 vs 621.0） |
| 我们 fp16 vs torch AMP | **我们慢 1.77×**（389.3 vs 219.5） |
| 我们 fp16 vs torch fp32 | **我们快 1.60×**（389.3 vs 621.0） |

**此前文档/CHANGELOG 里「对 PyTorch fp32 快 1.25×~1.38×」的说法作废**，
那是拿我们「含内联同步」的数字去比 torch「无内联同步」的数字，属于口径不一致。

## 5. 纪律修订

今后基准一律：
1. 循环内**不读设备标量**（loss / 梯度范数 / 任何 `.to_numpy()`）；
2. 需要监控 loss 时，单独跑「带同步」的版本，并**明确标注**它不代表吞吐；
3. 与被测对手（PyTorch）**用同一段测量代码**，两边口径必须一致；
4. 报告里写清 `N 步 / 是否含同步 / 是否包含数据加载`。

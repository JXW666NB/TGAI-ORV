# BUG：ORV vs PyTorch 的加速比归因错误（真正的变量是 host 端开销占比）

> **状态：OPEN（核心论断已于 2026-11-23 在 V100 上实测确认，见 §3.4）**　｜　登记日期 2026-11-23　｜　严重度：高（影响所有对外性能声明）
> 发现方式：外部评审意见 + 我们自己的五组实测数据自洽性复盘

---

## 1. 一句话

我们一直把「ORV 比 PyTorch 快 1.47×~1.59×」归因为**「纯 C 实现所以更快」**。
**这个归因是错的。**

语言本身不会让 GPU 算得更快。真正的变量是：
> **每步总耗时里，host（CPU）端开销占多大比例。**

`PyTorch eager` 每次调用 kernel 前都有 Python 调度、算子分发、内存分配、`launch` 这些固定成本；
`ORV` 的 host 端是纯 C，这部分成本小。所以：

* **GPU 越快 → 每个 kernel 越短 → host 开销占比越高 → 我们的优势越大**（launch-bound）；
* **序列越长 → kernel 越长 → 进入计算/带宽瓶颈 → 两边趋同**；
* **卡越慢（P100）→ host 开销占比极小 → 优势消失 → 退回比 kernel 质量 → 我们输**。

这三条，我们的实测数据**全部吻合**。

## 3. 证据

### 3.1 五组实测（同一模型、同协议、同步数）

| 场景 | ORV / PyTorch | 用本 BUG 的框架解释 |
| --- | ---: | --- |
| RTX 5090 · seq512 | **1.59×** | 卡最快，kernel 极短，launch-bound 最严重 → 优势最大 |
| RTX 4090 · seq512 | **1.47×** | 同样 launch-bound，略低 |
| Tesla V100 · seq512 | **1.42×** | 卡较慢，但 seq512 kernel 仍短，host 占比仍可观 |
| Tesla V100 · seq2048 | **1.08×** | 序列变长 → kernel 变长 → 进入计算/带宽瓶颈 → 趋同 |
| Tesla P100 · seq2048 | **0.78×** | 卡最慢 + 无 Tensor Core + 我们没编 sm_60 → host 优势归零，kernel 质量劣势暴露 |

### 3.2 4090 ≈ V100 倍率接近，也能解释

两张卡显存带宽几乎一样（V100 ≈ 900 GB/s，4090 ≈ 1 TB/s）。
若负载主要卡带宽（decode 阶段），两者表现接近是**必然**；5090 ≈ 1.8 TB/s，所以拉到 1.59×。
⇒ 应**按带宽而不是按卡代际**解读我们的数据。

### 3.3 仓库内既有证据（本来就指向同一结论，但没被串起来）

* `docs/DISPATCH_BOUND.md`（2026-11-20，4090 实测）：
  **一步 4038 次内核发射、每次约 59 µs 主机成本、主线程 CPU 时间 = 墙钟 100%、GPU 有 58~70% 时间没内核可跑**
  ⇒ **ORV 自己就是派发受限**。这条恰恰说明：我们赢 PyTorch 不是因为 kernel 强，
  而是因为**双方的 host 开销差距**；而且我们自己的 host 开销仍然很大（所以只赢 1.47×，不是 3×）。
* `docs/P100_WHY_SLOWER.md`（2026-11-21）：P100 慢 22% 已分解到"低显存注意力内核质量"，
  与 3.1 的最后一行一致。
* `docs/CUDA_GRAPH_FEASIBILITY.md` / `CUDA_GRAPH_FINDINGS.md`：降低 host 开销的可行手段已在评估。

### 3.4 V100 实测（2026-11-23，`docs/HOSTSHARE_V100_2026-11-23.md`）

| 侧 | seq | 墙钟/步 | CPU/步 | cpu/wall | GPU 利用率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ORV | 512 | **0.2545 s** | **0.2836 s** | 1.114 | 22.3 % |
| PyTorch | 512 | 0.3807 s | 0.4227 s | 1.110 | 32.5 % |
| ORV | 2048 | **0.7298 s** | **0.8109 s** | 1.111 | 45.7 % |
| PyTorch | 2048 | 0.8673 s | 0.9477 s | 1.093 | 58.2 % |

两条几乎重合的比值证明本 BUG 的核心论断：

* seq512：CPU 比 **1.49**，墙钟比 **1.50**
* seq2048：CPU 比 **1.17**，墙钟比 **1.19**

⇒ **两边都 host 受限（cpu/wall≈1.10、GPU 利用率仅 22–58%），加速比≈host CPU 开销之比。**
同时 ORV 的 GPU 忙时也更少（seq512 粗估约 1/2.2），但当前不构成墙钟瓶颈。

## 4. 影响面

1. **对外表述**：不能说"纯 C 所以 GPU 更快"；应说"我们把 host 端开销压到更低，因此在 launch-bound 区间占优"。
2. **优化优先级被误导**：如果把赢的原因当成 kernel 质量，就会去堆 kernel 优化；
   但 `DISPATCH_BOUND.md` 显示真正的天花板是 **host 端每步 4038 次发射 × ~59 µs**。
   ⇒ 降 host 开销（CUDA Graph / 参数模板 / 减少算子数 / 融合）收益**远大于**继续磨 kernel。
3. **P100 结论不能外推**：P100 上 0.78× 是 kernel 质量与硬件特性（无 TC）问题，与"引擎架构落后"无关。
4. **不要再用"跨卡代际"叙事**，改用"带宽 + launch-bound 程度"。

# P100 公平复测清单（2026-11-21）

> 起因：第一份 P100 报告（`docs/P100_MEASURED_2026-11-21.md`）用的是
> **fp32 + LOWMEM=1** 的默认配置，而 ORV 有一批"降显存/提速"的开关在报告里**一个都没出现**。
> 所以那份结论**可能是对的，但还不能断定是"引擎设计差距"还是"配置没开"**。
> 这份清单把差异量化出来：跑 5 组，答案就清楚了。

---

## 0. 先明确：P100 上什么能救、什么不能救

| 目标 | P100 上能否救 | 原因 |
| --- | --- | --- |
| **速度超过 PyTorch** | ❌ 基本不能 | P100 是 Pascal（cc=6.0），**没有 Tensor Core**。ORV 的速度优势来自 fp16/bf16 tensor-core GEMM 与融合内核，这张卡上这些路径不存在 |
| **显存降下来** | ✅ 很可能能 | 显存超支来自**激活用 fp32 存**（每样本 +0.65~0.87 GB，随 batch 线性）。bf16 存激活/梯度重算都是纯存储优化，**不需要 Tensor Core** |

所以复测的目标是：**把显存差距关掉，看速度是否至少持平**。这才是公平比较。

---

## 1. 跑之前：先做一次显存归因（最重要，只读）

你第一份报告只给了峰值，没给"峰值里都是什么"。这一条决定了后面所有优化值不值得做：

```python
import os
os.environ["TG_POOL_DEBUG"] = "1"
# …… 建模型 + 跑 1 个 step（就你现在 bench 里的那套）……
print(rt.pool_stats())         # 总量 / 峰值 / 碎片
rt.pool_dump_live(top=20)      # 最大的 20 个"还活着"的块（按字节）
```

我们要的是 `pool_dump_live` 的输出：它会指名道姓地告诉我们超支的是
**注意力分数**、**MoE dispatch 缓冲**，还是**某层激活的 fp32 副本**。
**在没有这份输出之前做的任何"显存优化"都是猜。**

## 2. 五组配置（同机、同骨架、S=2048、分进程跑）

每组都用 `--impl orv` / `--impl torch` 分开进程（你已知这条，继续遵守）。
`B=2` 与 `B=4` 各跑一遍，记 s/step、tok/s、峰值。

| # | 配置 | 关键命令 | 期望 |
| --- | --- | --- | --- |
| **A** | 你的基线（复现） | `python bench_v3exp2.py --impl orv` | 复现 8.43 / 10.14 GB |
| **B** | + bf16 激活存储 | `TG_BF16_ACT=1 python bench_v3exp2.py --impl orv`<br>或 `… --bf16-act`（1.0.20+ 的 CLI） | 峰值明显下降（理想 −30%~50%）；速度略降 |
| **C** | + 梯度重算（全开） | `… --grad-ckpt`（等价 `TG_GRAD_CKPT=1`） | 峰值再降；速度降 10~25% |
| **D** | + 部分重算（中间档，新增） | `… --grad-ckpt --grad-ckpt-layers 4` | 在 B/C 之间取平衡，用来找"显存刚好够"的点 |
| **E** | PyTorch 侧也开混合精度（**公平性**） | `torch.autocast`/`amp` 下跑一次 | 如果 PyT 也开 AMP，它的显存/速度都会变 —— 否则两边不是同一条件 |

> ⚠️ **B 组有个已知陷阱**（`bf16_act_store` 的文档写明了）：这是"全有或全无"的优化 ——
> 只有**消费方在反向内部才读缓冲**的算子才受益；如果某个算子在**前向就抓住了 fp32 缓冲**，
> 压缩后那份 fp32 仍被攥着，**内存反而涨约 50%**。
> 所以 B 组必须同时看 `pool_stats()` 的峰值：**涨了就说明这个开关在当前骨架不适用**，
> 不要硬用。这也是为什么必须先做第 1 步归因。

## 3. ORV 里还有哪些"没被用上"的开关（第一份报告里都没出现）

这些都已存在并可独立 A/B（`T.help` 可查）：

| 开关 | 作用 | 备注 |
| --- | --- | --- |
| `TG_BF16_ACT` / `--bf16-act` | 激活存 bf16 | 见上，需实测确认峰值真降 |
| `TG_FP16=1` / `--fp16-gemm` | GEMM 走 fp16 | **P100 上 fp16 只有 fp32 的 1/2 速率且无 TC**，这组在 P100 上大概率**不划算**，仅作对照 |
| `--amp` / `--policy` | 精度策略（AMP/fp16） | 与 PyT 的 autocast 对手方 |
| `TG_GRAD_CKPT` / `--grad-ckpt`、`--grad-ckpt-layers N` | 梯度重算（显存⇄算力） | 本次新增档位 |
| `--ce-chunk` / `TG_CE_CHUNK` | head+CE 分块 | 词表 32779 时 logits 很大，这项对显存有直接帮助 |
| `--chunk` | 数据/分块相关 | 见 `--help` |
| `--opt-state fp16/bf16`、`--muon-fp16-mom` | 优化器状态低精度 | AdamW 的 m/v 省一半 |
| `TG_MOE_MERGED`（默认开） | MoE 合并内核 | 关掉一定更慢，别关 |
| `TG_SDPA_LOWMEM` | SDPA 低显存路径 | 你报告的 `LOWMEM=1` 若指的就是它，需要说明作用在哪个算子 |
| `TG_POOL_DEBUG` + `pool_dump_live` | 显存归因 | 第 1 步用 |
| `--place` / `T.DUO()` | 多卡放置/一键多卡 | P100 单卡用不上 |

## 4. 我们要的结论（明确到可判定）

跑完请给这 5 个数（B=2 与 B=4 各一套）：

1. A 组峰值（复现，应与 8.43 / 10.14 一致）
2. **B 组峰值**（bf16 激活）：是否下降？降多少？
3. C 组峰值与 s/step
4. D 组峰值与 s/step（找"显存刚好够 B=4"的档位）
5. E 组（PyT 开 AMP）的峰值与 s/step

判定：

* 若 **B 组峰值降 ≥20% 且速度只降 ≤5%** ⇒ 说明第一份报告的显存劣势**主要是配置**，
  我们会把 bf16 激活做成该骨架的推荐项；
* 若 **B 组峰值不降甚至上涨** ⇒ 说明当前骨架没有收益（文档已写明这个失败模式），
  那这个劣势就是**设计层面**的，需要改代码（MoE dispatch 缓冲复用/注意力物化），
  我们会按第 1 步的 `pool_dump_live` 定位后动手；
* **速度**：P100 上不期待超过 PyTorch，**打平即可**；打不平就维持"P100 不推荐用 ORV 训练"的结论。

---

## 5. 一句话

**你的怀疑方向是对的**：第一份报告的对比是"PyTorch 默认 vs ORV 默认"，而 ORV 默认
并没有打开它自己那套降显存开关。但**即使全开，P100 也赢不了速度** —— 这张卡没有 Tensor Core。
所以我们真正要验证的是"**显存差距能不能靠配置消掉**"，这对用户才是实际的（16 GB 卡能开多大 batch）。

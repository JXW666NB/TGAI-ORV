# TGAI-ORV 在 P100 上的训练可用性评估

> 评估对象：`TGAI-ORV-main`（v0.9.49，PyTorch-free 训练引擎）
> 硬件：Tesla P100-PCIE-16GB（sm_60，无 Tensor Core）
> 系统：Windows 10，Python 3.13，机器上只装了 PyTorch（cu118），无系统 CUDA Toolkit
> 基准模型：自研 aaAI v2.1e（20 层 / d=1280 / MoE 36 专家 top-6 / 434M 参数）
> 结论时间：2026-11-12

---

## 0. 一句话结论

**P100 上 ORV 能跑，但“提速 + 降显存”两个目标都没有拿到证据：**
fp16 只覆盖前向 GEMM（反向仍是 fp32），P100 又没有 Tensor Core；
而 ORV 的梯度检查点显存回收弱于 PyTorch，v2.1e 同规模（B=8, S=2048）直接 OOM。
另外 v2.1e 的 MoE / RoPE / 分段注意力在 ORV 里都没有对应实现，迁移等于重写。

---

## 1. 接入过程：两个必须先解决的问题

### 1.1 NVRTC 找不到 builtins（**首装即失败**）

```
CudaError: NVRTC 编译失败 arch=compute_60
nvrtc: error: failed to open nvrtc-builtins64_118.dll.
```

- 机器上 `nvrtc64_112_0.dll` / `nvrtc-builtins64_118.dll` 都在 `torch/lib` 下，
  但进程的 DLL 搜索路径里没有它
- **规避方式**（需要用户自己知道才行）：

```python
import os
os.environ["PATH"] = r"D:\st\venv\Lib\site-packages\torch\lib;" + os.environ["PATH"]
os.add_dll_directory(r"D:\st\venv\Lib\site-packages\torch\lib")
```

- 建议：加载器启动时自动扫描 `torch/lib`、`site-packages/nvidia/*/lib`，
  并在失败时把“请把哪个目录加进 PATH”直接写进报错

### 1.2 P100（sm_60）本身是支持的

```
NVRTC 能编译 arch=compute_60，张量/模型/AdamW 可正常创建与训练
```

## 2. 速度与显存实测

### 2.1 PyTorch 基线（v2.1e 同形状，可信）

```
配置：20 层 / d=1280 / FFN=5120 / 10 头 / B=8 / S=2048
      fp16 autocast + 每层梯度检查点 + AdamW
结果：7,728 ms/step   2,120 tok/s   峰值显存 14.18 GB   393M 参数
对照：v2.1e 真实训练约 1,600 tok/s（含 MoE 与更复杂结构）
```

### 2.2 ORV

```
fp32、同形状、未开梯度检查点：直接 OOM（15.9GB 卡不够）
开启 checkpoint 后：仍然 OOM
   —— ORV 的 checkpoint 对激活的释放不如 torch 彻底（同一形状 torch 能跑）
降到 B=2 才能继续，但与 v2.1e 的真实配置已不可比，故未采信其速度数字
```

### 2.3 fp16 机制（关键差异）

```
ORV：rt.fp16_gemm = True 只把**前向 GEMM** 换成 fp16（fp32 累加），
     反向仍然走 fp32 的 sgemm/gemm_tn
     官方注释：V100 上 mlp 4.33x / lm_head 5.21x（靠 Tensor Core）
P100：没有 Tensor Core，fp16 只有 2:1 FMA 吞吐，且只作用于前向
     → 端到端提升远小于 V100 的 4x，乐观估计 ≤1.3x
对照：我们 v2.1e 现在是 torch fp16 autocast（前反向都能 fp16）
      → 在 P100 上，ORV 的“fp16 路线”反而比 torch 窄
```

## 3. 迁移 v2.1e 的缺口（逐项核对过代码）

| v2.1e 组件 | ORV 现状 | 结论 |
|---|---|---|
| RoPE（cos/sin 预计算表） | Tensor 没有 `cos/sin`（只有 exp/log） | 需 numpy 预生成再传入，或加内核 |
| **MoEFFN**：36 专家 top-6、无锚点、Loss-Free Balancing 偏置 | 有 `nn.MoE`，但 top-k 与均衡方式不同 | **必须重写这一层** |
| 分块 CE（避免 [B,T,V] 物化，省 2GB+） | `functional.linear_cross_entropy`（同思路） | 可替换，需改接口 |
| 按文档切段的因果注意力（bool mask） | `scaled_dot_product_attention` 参数约定与 torch 不同 | 重写；照 torch 调用会报 5 维 broadcast |
| 梯度检查点 | 有，但显存回收弱 | v2.1e 的 B8/S2048 在 ORV 上跑不动 |
| 分段注意力 + 文档打包 | 无 | 需自己实现 |

## 4. 建议（按优先级）

```
P0  首装体验：自动定位 nvrtc/cublas（torch/lib、nvidia/*/lib），失败时给出可执行的修复命令
P0  梯度检查点：显存回收要达到 PyTorch 水平，否则 16GB 卡跑不了 400M 级模型
P1  SDPA 与 torch 参数约定对齐（或提供 torch 兼容层）
P1  Tensor 补 cos/sin（否则 RoPE 类模型迁移成本高）
P2  在 P100 上给出实测：fp32 GEMM 相对 cuBLAS 的倍数（同一 cuBLAS 下差距应来自融合与 kernel 数）
P2  P100 上 fp16 只做前向这件事，需要在文档里明确，避免“有 fp16 就能快”的误解
```

---

## 5. 如果要继续合作评估

```
建议改用 dense 小模型（≤300M、B≤2、S=1024）作为双方共同的基准：
  · 形状简单，不涉及 MoE/RoPE，能纯粹比较 GEMM 与算子融合
  · 在 P100 上 torch fp32 / ORV fp32 / ORV fp16 三方对照
  · 这样得到的倍数才是“框架本身的效率”，与具体模型结构解耦
```

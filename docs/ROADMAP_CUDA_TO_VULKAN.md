# 从 CUDA 收尾到 Vulkan 开工：开发计划

> 2026-11-12 制定。**范围**：CUDA 后端「可交付」还差什么，以及为什么 Vulkan 必须排在它后面。
> 本文只列**已经实测过的问题**，不列想象出来的需求。每条都带可测判据。

## 0. 为什么不是直接开 Vulkan

`MULTIVENDOR_ROADMAP.md` §6 的原话：先把 CUDA 做成"可交付"，Vulkan 才有一个**能对拍的正确性基准**。

补一条今天新增的理由：**Vulkan 训练后端目前是 0 个内核**，而 CUDA 侧的每个融合核都可以当它的
参照实现。先开 Vulkan = 没有参照物地造轮子。

---

## 1. 现状盘点（只写有证据的）

### 已经能交付的部分

| 项 | 证据 |
| --- | --- |
| 单步数值正确 | 8 步 loss 1.44e-07；Qwen2.5-0.5B vs HF 6.29e-06 |
| 单步性能 | dense fp32 16.55 ms vs PyT 42.73 ms（2.58×）；MoE fp32 83.0 vs 139.4（1.68×）|
| 3B MoE 能训完一步 | 709 ms / 峰值 24.78 GiB（V100 32GB），PyT 在同规模 OOM |
| 验证工具齐备 | `tools/accept.py`、15 个 `align_*.py`、`conv_cuda_parity.py`、`pytorch_loss_curve.py` |
| 测试套件 | 665 passed / 37 skipped |

### 还没解决的部分（本次实测或用户反馈）

| # | 问题 | 证据 |
| --- | --- | --- |
| 1 | **长跑收敛未证** | 只有「20 步 loss 偏差 1.59e-05」；**没有 500–2000 步的对照** |
| 2 | **显存比 PyT 多 1.2–1.9×** | 本次 h2h 实测；检查点修复后仍 1.75–1.85× |
| 3 | **`getitem` 不支持数组索引** | 写 benchmark 时连撞 3 次（ndarray / Tensor 索引均报错）|
| 4 | **7B 规模未测** | README 明写 0.5B 是已验证上限 |
| 5 | **分布式未真机验证** | `dist.py` 代码在、2 进程 CPU 验过、**从未上双卡** |
| 6 | **社区无法自助验证** | 没有一键自检 + 结果回流路径 |

## 2. 工作包 A：质量验证（最高优先）

**为什么最高**：这是你定的三个判据之一（质量对等），而且是最弱的一环。
单步对齐只能证明"算对了"，证明不了"训得动"。

| 项 | 内容 |
| --- | --- |
| 做什么 | 同语料、同 seed、同结构，ORV 与 PyTorch 各跑 **1000 步**，比 loss 曲线 |
| 已有工具 | `tools/pytorch_loss_curve.py`、`tools/conv_cuda_parity.py` |
| 判据 | ① 1000 步无发散；② 末段 loss 相对偏差 ≤5%；③ 曲线最大偏离步与幅度要报出来 |
| 交付 | `docs/CONVERGENCE_1000.md`（含命令、两份 loss 序列、图）|
| 依赖 | 无（V100 即可）|

**要用真实语料，不能只用随机 token。** 随机 token 上 loss 只能降到 ln(V)，掩盖不了问题也暴露不了问题。

---

## 3. 工作包 B：显存（决定能训多大）

**为什么重要**：它直接决定"能替别人训多大的模型"。当前 1.8× 的差距会把 7B 挡在 32GB 之外。

| 项 | 内容 |
| --- | --- |
| 已知 | 检查点修复后 dense 0.602 GiB vs PyT 0.325（1.85×）；剩余约 0.28 GiB 未归因 |
| 下一步 | **逐张量归因**：每步采样池里 live 缓冲的 (size, 分配点)，按占用排序，找出那 0.28 GiB 是谁 |
| 判据 | dense + 检查点场景，与 PyT 的比值 **≤1.3×**；并且能解释剩余差距的来源 |
| 可能的来源（待验）| ① 残差流每层一份（PyT 也是，应可比）② `_FP16_SHADOWS` ③ 池的碎片化 ④ logits `[B*S, V]` 物化 |
| 依赖 | 无 |

**注意**：`docs/GAP_VS_PYTORCH.md` §7 列过四个方向（SDPA 低显存、融合核接线、词表单份、视图零拷贝），
但那是 11-02 的清单，其中部分已接线。**先做归因，再选方向**，不要照旧清单盲改。

---

## 4. 工作包 C：API 完备性（降低迁移摩擦）

**为什么重要**：这是"社区能不能用"的门槛。我今天写一个 benchmark 就撞了三次。

| 缺口 | 现状 | 判据 |
| --- | --- | --- |
| `getitem` 数组索引 | `x[idx]`（idx 为 ndarray/Tensor）直接抛 `NotImplementedError` | 支持 int 列表/ndarray/Tensor 索引，与 numpy 语义一致 |
| `max(dim=)` 不返回索引 | 已在 README 披露 | 可接受（用 `argmax`），但要确认 `argmax` 覆盖常见用法 |
| `permute` 真拷贝 | 已在 README 披露 | 暂无要求，保持披露即可 |

**为什么把 `getitem` 排进来**：embedding 查表和 gather-based CE 是最常见的两种写法，
用户第一次写就会撞。绕过去要改用 `nn.Embedding` —— 能work，但会让人以为"这库不支持索引"。

## 5. 工作包 D：真实规模

| 项 | 内容 |
| --- | --- |
| 做什么 | 一个 **7B 级别**模型在 32GB 上跑通一步，报显存与步时 |
| 判据 | 跑通 + 数字入文档；跑不通就明确写"32GB 不够，需要 N GB" |
| 依赖 | **B（显存）**：不降显存，7B 很可能放不下 |
| 备注 | 若 7B 放不下，退一步做 4B 并写清边界 —— 边界本身也是交付物 |

---

## 6. 工作包 E：分布式（你点名的那项）

| 项 | 内容 |
| --- | --- |
| 现状 | `dist.py` 是**进程级** DP（每 rank 一进程、共享内存 all-reduce），**2 进程 CPU 验过** |
| 缺 | ① 真双卡从未跑过；② 无 `device` 感知的梯度交换；③ 无 pinned/异步 |
| 判据 | 2×V100 上：**加速比 ≥1.3×**，且梯度与单卡一致（相对差 ≤1e-5）|
| 硬件 | **租 Linux 双卡机**（40 元级）。**必须 Linux** —— Windows 上 V100 处 TCC，Vulkan/CUDA 二选一 |
| 依赖 | 无（可并行于 A/B/C）|

**这一步同时是 TG Link 的 tier-3 基础**：host-staged all-reduce 与厂商无关，先把同厂商跑通，
跨厂商只是换一个 backend 实例。

## 7. 工作包 F：社区自助验证（不占 GPU，可并行）

| 项 | 内容 |
| --- | --- |
| 做什么 | ① `accept.py` 收敛成**一条命令**出结论；② 一键探针（见 §8）；③ 结果回流模板 |
| 判据 | 一个没用过 ORV 的人，照 README 能跑完并贴出结构化结果 |
| 为什么现在做 | 群友已经在测了（P100 报告就是成果）。**没有回流模板，好数据会散在聊天记录里** |

---

## 8. 工作包 G：TG Link 探针（T1）

只做**静态层**，不碰 P2P 实测。

| 项 | 内容 |
| --- | --- |
| 输出 | 设备清单（按 **PCI BDF** 配 CUDA↔Vulkan，不用索引）+ 每对设备的句柄类型交集 + **阻塞原因**（`TCC_MODE` / `NO_ICD` / `NO_VULKAN_LOADER` / `HANDLE_INTERSECT_EMPTY`）|
| 判据 | 在笔记本与远端都能跑出有意义输出（配对为空也算）|
| 不做 | 不做导出/导入实测（需要同机 ≥2 Vulkan 设备，当前没有）|
| 价值 | 让群友一句话交数据：「你有没有同时装 A 卡和 N 卡的机器」|

---

## 9. 顺序与依赖

```
A 质量验证(1000步)  ──┐
B 显存归因 ───────────┼─→ D 7B 规模
C getitem/API ────────┘
E 分布式(租Linux双卡) ── 独立，可并行
F 社区自助            ── 独立，不占 GPU
G TG Link 探针        ── 独立，不占 GPU
```

**建议迭代顺序**：
1. **B 显存归因**（先测，不猜；它决定 D 能不能做）
2. **A 长跑 1000 步**（最弱判据，越早暴露问题越好）
3. **C `getitem`**（小改动，直接降迁移摩擦）
4. **F + G**（不占 GPU，与上面并行）
5. **E 分布式**（等租机）
6. **D 7B**（等 B 的结论）

---

## 10. 明确「不做」的清单

| 不做 | 理由 |
| --- | --- |
| Vulkan 训练后端 | 没有 CUDA 参照物；且 roadmap 排序如此 |
| TG Link 的 P2P 实测 | 需要同机 ≥2 Vulkan 设备，当前没有；等社区数据或 Linux 租机 |
| 后端混用（进程内多后端） | 要拆 `_CudaAPI` 单例，且被"Vulkan 训练后端为零"卡住 |
| 自动防 OOM 的动态迁移 | 运行时事务，代价可能大于收益；改为「准入控制 + 步边界重试」|
| 细粒度算子级多卡分配 | 每次搬运走 PCIe，必然亏（单次 84 MB 往返就 17 ms）|

## 11. 需要拍板的决策项

| # | 决策 | 现状 | 影响 |
| --- | --- | --- | --- |
| 1 | `_FP16_MAX_K` 默认值 | 默认 `1<<30`（不限制），但注释记录长 K 会让梯度误差恶化到 2e-2 | 影响所有开 `TG_FP16=1` 的用户精度 |
| 2 | 多卡目标形态优先级 | DP / PP / TG Link 未定序 | 决定 E 之后接什么 |
| 3 | 7B 是否硬性目标 | README 只承诺 0.5B | 决定 B 要做到多紧 |
| 4 | 确定性承诺范围 | 「两次训练逐位一致」是卖点，但跨不同传输 tier 会破 | 需在文档定性：同机同配置才保证，还是全局保证 |

> 口径：V100 32GB，8 层 / d=512 / 8 专家 / top_k=2 / 1 个共享专家 / 8 头（d_k=64）/ seq 2048 / batch 1 / fp32，

> **PyTorch 基准：4,633 MiB / 0.507 s**（`tools/v3_pyt_train.py --n_heads 8 --top_k 2`）

## 2. 目标 1「空间换速度」：速度要秒杀 PyT

**差距**：现在只是持平（0.53 vs 0.507）。要"秒杀"得进 0.30 s 级。

**唯一可行杠杆：CUDA Graph**。引擎自带 `graph_train.GraphStep`，作者实测 437~489 ms → 256 ms（**1.71×**）。
按此推算 0.53 s → 约 0.31 s，达到目标。显存不变（9.3 GB，约为 PyT 的 2 倍，符合"空间可以输"）。

**硬阻塞**：捕获期间任何 D2H 都会写 `_graph_poison`，`graph_end` 直接失败。当前 D2H 来源：
1. `v3_moe.route_topk` 的 `idx_buf.to_numpy()`（每层 1 次）
2. 检查点边界的 `to_numpy()`（若开检查点；本档不开，可避开）
3. 每步 `loss.to_numpy()` 打日志（可挪到图外）

⇒ **只需清掉第 1 项**。运行时有 `moe_compact` / `moe_gather_rows` / `moe_scatter_rows` 可在设备侧压实，
但这正是 `docs/PLAN_MOE_GROUPED_FIX.md` 里 rc=7 未解决的那条路。

## 3. 目标 2「显存远少于 PyT」：当前 0.86×，做不到"好几倍"

**必须先说清一个下限**：237 M 参数在 fp32 下
```
权重 904 MiB + 梯度 904 MiB + Adam m/v 1,808 MiB ≈ 2,616 MiB
```
再加词表嵌入/头的梯度、临时量，**实际地板约 3,300~3,800 MiB**。
PyT 是 4,633 MiB ⇒ **即使激活为零，最多也只能到 0.7~0.8×**，不可能"少好几倍"。

**要做到 0.5× 以内，唯一出路是压优化器状态**：
| 方案 | 省下 | 代价 |
| --- | --- | --- |
| Adam m/v 存 fp16（主权重仍 fp32）| ~904 MiB | 需要 fp16→fp32 转换核；收敛性需实测（业界常用）|
| 8-bit Adam | ~1,580 MiB | 量化误差，需分组 scale |
| 梯度检查点 + 梯度累积 fp16 | 再省几百 MiB | 与上面叠加 |

⇒ 目标 2 需要**新功能**（低精度优化器状态），不是调参能到的。建议先做 fp16 动量：
预计 3,980 → ~3,100 MiB（**0.67×**），速度不变。

## 4. 目标 3「两个都要赢」：现在 0.99× 显存 / 2.0× 慢

要同时赢，得在 4,000 MiB 以内做到 ≤0.50 s。当前最接近的是"物化 + 检查点"（4,593 / 1.00 s）。

三条并行路径：
1. **检查点结构改造**：现在每层重算整层；若只对注意力做检查点（MoE 不重算），可省一半重算时间
2. **融合 RoPE**（`T.fused_rope` 已存在）：每步省 2.1 GiB 流量、304 次发射
3. **清 D2H + CUDA Graph**（同目标 1）：对"物化 + 检查点"档同样有效

## 5. 关于原生内核（lowmem）的结论

单算子实测（S=1024，d_k=64）：**0.014 s**，比物化（0.017）快、比块化（0.053）快 3.8×，且数值正确（2.33e-09）。
但在整模型 S=2048 下反而是 2.88 s（比物化的 0.53 慢 5×）。

⇒ **该内核在当前调用方式下不适用**（可能是我方 permute/布局带来额外开销，或内核在 S=2048 的 grid 配置不佳）。
先用 nsys/事件计时确认再决定是否投入；**不要仅凭单算子数据就切默认路径**（这里踩过一次）。

## 8. 2026-11-14 傍晚：一步的部件分解与三个否定结论

### 8.1 一步到底花在哪（8 层、seq2048、8 头、top2，同步打点）

| 部件 | 时间 | 占比 |
| --- | --- | --- |
| **反向（整步）** | **0.318 s** | **74.4%** |
| MoE 分派（前向，含 2 槽）| 0.049 s | 11.5% |
| 注意力（前向）| 0.035 s | 8.1% |
| 共享专家 | 0.012 s | 2.9% |
| Adam | 0.007 s | 1.6% |
| 其余（norm/残差/嵌入/头/CE）| 0.006 s | 1.4% |
| **一步合计** | **0.428 s** | — |

**结论：之前一直在优化前向注意力，方向偏了 —— 反向占 74%。**

### 8.2 发射次数不是瓶颈

累计每步约 **2,400 次内核 + 1,200 次 cuBLAS**，按 10 µs/次也只有 ~36 ms（占 8%）。
⇒ CUDA Graph 的收益上限只有个位数百分比，**不是 1.71×**（引擎那个 1.71× 是别的负载形状）。

### 8.3 显存地板：目标②必须压优化器状态

按层数外推（块化+检查点、seq2048）：

| 层数 | 峰值 | 每层增量 |
| --- | --- | --- |
| 1 | 865 MiB | — |
| 2 | 1,311 MiB | +446 |
| 4 | 2,204 MiB | +446 |
| 8 | 3,987 MiB | +446 |

每层 446 MiB 里约 **366 MiB 是权重+梯度+Adam**（压不掉），约 80 MiB 是激活。
⇒ **激活归零时地板 ≈ 3,350 MiB**，高于目标②的 3,200 ⇒ **不做优化器状态压缩就不可能达标**。
fp16 动量预计省 ~800 MiB → 约 3,187 MiB，刚好达标。

### 8.4 fp16 GEMM 实测无收益（否定结论）

`TG_FP16=1`（引擎自带，门槛 输出≥26 万元素，我们的 GEMM 基本都满足）：

| | 步时 | loss |
| --- | --- | --- |
| fp32 | 0.49 s | 8.4202 |
| **fp16 GEMM** | **0.50 s** | 8.4202 |

⇒ 数值可用，但**没有提速**：转换/落盘开销吃掉了张量核收益，且反向的小 GEMM 本来就不是算力受限。

### 8.5 因此目标①的现实路径

0.428 s 的一步里，反向 0.318 s 主要由**每层 24 个 M=256 的小 GEMM**（MoE，2 槽 × 8 专家 × 3）构成。
fp32 下这些小 GEMM 的利用率只有个位数百分比。

**唯一有数量级空间的做法**：把 MoE 的小 GEMM 合并成 **1 次 batched/strided 调用**
（按专家打包 + 定长容量），顺带把两个槽合成一趟。这是 `docs/PLAN_MOE_GROUPED_FIX.md` 未完成的那条路。

## 9. 2026-11-14 夜：bf16 动量与选择性检查点（目标②的显存轴已达标）

### 10.1 为什么必须是 bf16，不是 fp16

引擎自带 fp16 动量 Adam（`adamw_update_multi_f16` + `Fp16MomAdamW`）。**实测不能用**：

| 步 | fp32 动量 loss | fp16 动量 loss |
| --- | --- | --- |
| 0 | 8.4093 | 8.4092 |
| 1 | 8.4202 | 8.4221 |
| 2 | 8.4362 | 10.1713 |
| 3 | — | 29.1893 |
| 4 | — | 246.2503 |
| 5 | — | **552.9841** |

**根因**：fp16 最小正规数 6.1e-5，而二阶动量 v 训练早期常在 1e-8 量级 ⇒ **下溢为 0**，
`denom = sqrt(0) + eps = eps`，步长被放大几个数量级。

**修法**：新增 `adamw_update_multi_bf16`（bf16 与 fp32 同指数范围，下限 ~1.2e-38），
`Fp16MomAdamW(state="bf16")`。6 步 loss：8.4092 → 8.4191，**稳定**。

### 12.4 因此下一步只有两个候选

1. **MoE 分派里的 gather/scatter**：`x[order]` 的反向是 `D2H + np.add.at + H2D`（子代理报告 F7），
   每次分派 4096 行 × 512 列 = 8 MB 往返；2068 估算每步十余次 → 需要实测确认
2. **每专家的 elementwise 链**（gate/up/SiTU 反向）在 (512, 2048) 上多次往返

下一轮用 CUDA event（而不是每次同步）在**一次**分派内部打点，定位这 62 ms。

## 13. 2026-11-15：把专家分派的 gather 换成设备侧 —— 单点收益最大的一改

`indexing.index_select(x, 0, order)` 的**反向直接调 `rt.scatter_add_rows`**（设备侧原子加）。

数值：前向 4.27e-07、dx 2.86e-06；整模型 loss 轨迹与改前**逐位相同**（8.4092→8.4191）。

## 15. 2026-11-15：一次失败的优化与回退（记录教训）

### 15.1 想做的事

合并路径里先 `x[tok]`（按 token 展开）再 `x[order]`（按专家排序），是**两次** gather。
理论上等于 `x[tok[order]]`，可以合成一次，省一趟 8 MB 搬运和一份中间张量。

### 15.2 错在哪

**gather 与 scatter 用的不是同一个索引**：
- gather 要 `src_tok = tok[order]`（每个排序后位置对应的**源 token 号**）
- 散回原位要 `order`（每个排序后位置在**原布局里的位置**）

第一版把 `tok[order]` 同时用作两个用途，实测前向差 **0.921**、dx 差 **3.97**。
补上"门控也要按同一置换重排"后仍差 0.608 —— 说明还有第二处不一致。

### 15.3 处置：**回退**

按"稳定性第一"，直接回退到已验收的 `4bdfa0a`（设备 gather 版本），
重新对拍恢复 **4.27e-07 / 2.86e-06**。

**教训**：这类"多个索引互换"的改动，必须在**同一个探针里同时验证前向与梯度**，
并且**改完立刻跑**；这次我先提交再验证，多花了两轮。

### 15.4 回退后的稳定成绩（本轮确认）

## 16. 2026-11-15：gc 频率是个真瓶颈；折叠求和是中性的

### 16.1 每层 `gc.collect()` 是隐藏开销

`layer` 检查点路径原来**每层**都 `gc.collect() + empty_cache()`。Python 大堆一次 gc 约 20–40 ms，
8 层就是 0.2–0.3 s/步。改成每 4 层一次（可用 `TGAI_GC_EVERY` 调）：

| 配置 | 改前 | 改后 |
| --- | --- | --- |
| 块化 + 整层重算 @1024 | 1.09 | **1.04** |
| 块化 + 重算 MoE @1024 | 0.70 | **0.61** |
| 块化 + 重算 MoE @768 | — | 0.65 |

再放宽到每 8/16 层无进一步收益（1.04 不变），说明剩余时间不在 gc。

### 16.2 把 k 路求和折进 scatter：**中性**

合并路径原先是 `scatter_add(..., n_rows=N·k)` 再 `reshape(N,k,d).sum(axis=1)`。
改成**直接按 token 号 scatter 到 N 行**，原子加天然完成 k 路求和，省掉一次 reshape+sum。
数值保持（4.27e-07 / 2.86e-06），但整步**没有可测变化**（0.40→0.41，噪声内）。

⇒ 说明那一步本来就不贵；**不再把它当优化项**。

## 17. 2026-11-15：峰值到底由什么组成（逐阶段追踪）

### 17.1 追踪（块化 + 整层重算 + bf16 + tile1024）

| 阶段 | live |
| --- | --- |

### 17.2 结论：峰值 = 权重/Adam + **逐层累积的梯度** + 层内临时量

- 权重 891 MiB + bf16 Adam 446 MiB ≈ 1,337 MiB（压不动，除非改精度）
- 反向过程中梯度逐层累积：2,146 → 2,919，约 **110 MiB/层**（fp32 梯度）
- 层内临时量约 340 MiB

**因此"再省 58 MiB"不能靠省激活**（激活只剩几百 MiB），
最有杠杆的是**梯度精度**：把累计的 773 MiB 梯度存 bf16 可省约 386 MiB。
但这要求 `_acc` 分配 bf16 梯度缓冲，且融合 Adam 直接读 bf16 —— 属于引擎级改动，
按"稳定性第一"不能在这一步仓促做。

## 19. 2026-11-15：CUDA Graph 实测被路由的 D2H 挡住了（决定性的负面结果）

### 19.1 引擎里确实有 CUDA Graph

`graph_train.py` 提供 `GraphStep`：捕获**前向+反向**（优化器刻意留在图外，
因为 AdamW 的偏差校正是按步数算的标量，实测改写图参数会差 1.7e-05）。
捕获期用一块独立 arena 做 bump 分配，重放走 `graph_launch()`。

### 19.2 实测

| 项目 | 结果 |
| --- | --- |
| 逐算子（同一探针，无打印/无同步）| **0.354–0.359 s/步** |
| 捕获 | **失败**：`cuStreamSynchronize 失败 rc=900 operation not permitted when stream is capturing` |

### 19.3 根因：`route_topk` 每层一次 D2H

`v3_moe.route_topk` 里有：

```python
eids = np.asarray(idx_buf.to_numpy() ... )   # ← 每层一次设备→主机拷贝
```

D2H 必须同步，而**捕获期间不允许同步**，所以整步无法成图。

⇒ **要吃到 CUDA Graph 的 1.71×，必须先让路由与分派全程留在设备上。**
这也正是目标里"清掉路由每层的 `to_numpy`"那一条 —— 此前一直没做，现在有了硬证据说明它是前置条件。

### 19.4 下一步的两条具体路线

1. **设备侧排序**：把 `argsort(eids)` 换成设备上的 CUB radix sort（引擎还没有导出该入口，需要新增绑定）
2. **免排序的按容量稠密分派**：对每个专家用 mask 收集该专家的行（8 次带 mask 的 gather），
   M 补齐到容量上限，一次 strided-batched GEMM —— 完全不需要排序，天然可捕获

路线 2 与 PyTorch 的 `_grouped_mm` 兜底思路一致（它也是主机循环），但**没有 D2H**，
同时也把"每专家一次 Python 循环"的开销摊薄。我倾向先做路线 2。

## 20. 2026-11-15：设备侧 permute 内核已落地并验数（CUDA Graph 的地基）

### 20.1 为什么做

路由的 `to_numpy()` 每层一次 D2H → 捕获期间不许同步 → 整步无法成图（rc=900）。
要吃到 CUDA Graph 的 1.71×，必须让**路由与分派全程留在设备上**。

### 20.2 新增内核（`cuda.py`）

| 内核 | 作用 |
| --- | --- |
| `moe_permute` | 按专家把 (row, slot) 对写进容量 C 的槽位；`atomicAdd` 领号；空槽 `rowid = -1` |
| `moe_unpermute` | 把槽位输出写回原 (row, slot) 位置（每槽唯一，无需原子） |
| `moe_permute_bwd` | `dx` 原子加（同一 row 的两个 slot 会撞），`dgate` 每槽一个 block 归约 |

配套启动器：`rt.moe_permute / moe_unpermute / moe_permute_bwd`。

### 20.3 验数（`tools/probe_moe_permute.py`，N=2048/k=2/d=512/E=8/C=768）

| 检查项 | 结果 |
| --- | --- |
| counts（每专家对计数）| **完全一致** `[516,495,516,497,521,488,527,536]` |
| rowid 集合 | **一致** |
| gate | **一致**（逐位）|
| xp（收集的激活）| **0.000e+00** |
| unpermute（散回）| **0.000e+00** |
| 反向 dx | **0.000e+00** |
| 反向 dgate | 1.19e-06（浮点归约顺序，符合预期）|

### 20.4 一个静默的坑（值得记住）

`rt.h2d(arr, dtype=np.float32)` 的 **dtype 默认是 float32**，会把 int64 静默转成 float32。
第一版探针就踩了：内核按 `long long` 读，4096 个 pair 只有 **32** 个被处理，
而 xp/unpermute/dx 的"差"仍显示 0（因为对齐的槽位本来就没写）。
**教训**：设备索引数组必须显式 `dtype=np.int64`；并且**只差 0 不能证明对**，
必须同时检查 counts（覆盖度）—— 这是本次才补上的一项断言。

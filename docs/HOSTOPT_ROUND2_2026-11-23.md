## 2. `TG_POOL_FAST`（默认关，建议按需开）

**改了什么**：`cuda.py` 把「稳态池命中」这条直线（`empty → _alloc → _pool_take → _pool_checkout → GpuBuf.__init__ → _pool_token_of`）内联成顺序代码，
并给 `GpuBuf` 增加 `token=` 直传；`__del__` 等价直线化（释放时机不变）。
**非稳态场景一律回退旧实现**（显式 `free`、arena、`TG_LAUNCH_FAST=0` 的 event 链、OOM 兜底、捕获、未命中）。

| 项 | 数据 |
| --- | --- |
| 单圈 `empty+del` 微基准（V100，纯主机）| 3.01 µs → **1.90~1.92 µs（−36.5%）** |
| 每步分配/归还次数 | ≈3890 次（≈launch 次数 3071）|
| 理论收益 | ≈4.3 ms/步 |
| **实测端到端** | **−1.4%（0.2200 → 0.2169），区间不重叠** |
| 数值正确性（确定性 4 步）| 与安装版 loss/gnorm **逐位相同** |

> 口径纠正：`HOSTHOTSPOTS_2026-11-23.md` 里"池/Tensor 包装 0.02–0.03 s/步"是 cProfile 膨胀值；
> 该族真实成本约 **11.7 ms/步**，本改动拿走约 1/3，其余是 `_pool_live` 建删与对象生命周期的硬成本。

## 3. `TG_MOE_DEV`（默认关，负结果留档）

**改了什么**：`v3_moe.py` 新增设备端路由句柄 `DeviceRouteIdx` 与 `moe_dispatch_dev`
（`moe_compact` → 一次 `off` D2H → 逐专家 `moe_gather_rows → grouped GEMM → SiTU-GLU → 门控 → moe_scatter_rows_add`），
反向只接"累加器"层，GEMM/SiTU-GLU/dW 复用旧 Tensor 算子。

### 3.1 它确实做到了设计目标

| 项 | 旧 | 新 |
| --- | ---: | ---: |
| D2H 次数/步 | **26** | **14**（−12）|
| D2H 主机阻塞 ms/步 | ~90.3 | **~22.5**（−68）|
| 每步 CPU（另一组干净 A/B）| 0.223 s | **0.176 s**（−21%）|

### 3.2 但墙钟没变好，反而略慢

| 配置 | 稳态 s/步 |
| --- | ---: |
| 基线 | 0.2200 |
| `TG_MOE_DEV=1` | **0.2238（+1.7%）** |

**原因**：省下的 68 ms 主机阻塞里，大部分本来被 GPU 队列**遮住**（GPU 空闲时才有价值）；
而设备端分派新增了 `moe_compact` + 每专家 `gather/scatter` 等内核与串行段，在这套形状下成本更高。
⇒ 这不是实现错误，而是**该形状下不值得**。留作"CPU 严重受限 / GPU 更闲"场景的可选路径。

### 3.3 正确性（做得很干净，值得保留）

* 生产 MoE 形状（N=512,k=2,d=1024,d_ff=3328,E=4）：输出/gates/s_all/eids/d(hn)/d(router)/12 个专家矩阵梯度 **24/24 项逐位相同（max_abs=0）**；含空专家与 70/20/10/0 极端分布。
* 12 层 4 步训练：每步 loss、gnorm **Δ=0**，训练结束**全部参数 sha256 相同**，重复 4 次一致。
* 默认路径（不设变量）：与安装版 4 步 loss/gnorm/参数 sha256 全同，D2H 同为 26/步。
* 已知边界：`k≥3` 时求和顺序变化可能带来末位差异（生产 k=2 不受影响）。

## 5. CUDA Graph：按证据结案（不做）

* 机制可用：`lab/prof/graph_smoke.py` 重放**逐位一致**，CPU 派发 0.063 → 0.004 ms（14.4×）。
* 但 32 GB 装不下 1.5B：arena 是 bump-only，捕获期必须容纳"整步分配总和"**≈28 GiB**，加参数/优化器 18 GiB ⇒ **46 GiB**。
* 分段捕获也不成立：V3 路由数据相关，每步专家索引与各专家 token 数都在变。
* 当年 0.5B 复测只剩 **1.01×**（发射间隙已被其他优化吃掉），见 `docs/CUDA_GRAPH_FINDINGS.md`。

### 5.1 对照组：PyTorch 能不能训 1.5B？（能）

实测（同一张 V100-32GB，`v3_pyt_train.py`，24 层 / d=1024 / E=4 / d_ff=3328 / seq512 / batch1）：

| 配置 | 参数量 | 结果 |
| --- | ---: | --- |
| fp32，无梯度检查点 | 1,383,233,554 | **跑通，1.14–1.20 s/步，无 OOM** |
| fp16 AMP + 梯度检查点 | 同上 | 跑通，1.23 s/步 |

⇒ PyTorch 显存上做得下，理论上也能捕获图（其图池按**峰值**而非总和计）；但该规模下 PyTorch 是 GPU-bound（1.2 s/步），图的收益按历史实测应在 1.0× 量级。
**我们没做 Graph 不吃亏**：ORV 是 arena 机制装不下，PyTorch 装得下也几乎不加速。

## 6. 本轮结论

1. 采纳 `TG_POOL_FAST`（**opt-in**，−1.4%，正确性逐位一致）；
2. `TG_MOE_DEV` 保留代码、**默认关**，负结果入档（CPU −21% 但墙钟 +1.7%）；
3. `TG_LAUNCH_FAST` 维持默认开（关闭代价 −17%）；
4. CUDA Graph 不做（显存 + 历史 1.01× 双重证据）；
5. 剩余真正的大头仍是**减少 kernel/分配数量**本身（融合），而不是搬主机开销 —— 每步 3071 次发射 × ≈3890 次分配是结构性成本。

## 9. 第三项微优化：`TG_LAUNCH_TMPL2`（默认关）

**问题**：`launch()` 每次都重建键 `(name, tuple(t[1] for t in args))`，
差量 profile 里对应 **39,274 次 genexpr/步** —— 是最大的单一 Python 热点之一。

**做法**：按 **kernel 名** 直取参数模板（同时缓存已解析的 `fn`），省掉键的元组分配与哈希。
安全守卫：① 参数个数一致 ② 逐个 `参数类型 is 模板类型`；任一不满足就**不写值**、落回按类型键控的旧路径
（两条路径使用各自独立的模板对象，互不污染）。门控 `TG_LAUNCH_TMPL2=1`。

| 配置 | 稳态 s/步（3 轮中位）| 极差 | 相对 |
| --- | ---: | --- | ---: |
| `=0` | 0.2204 | 0.2198 ~ 0.2208 | — |
| **`=1`** | **0.2184** | 0.2184 ~ 0.2191 | **−0.9%**（区间不重叠）|

确定性 4 步：loss/gnorm 与关闭时**逐位相同**。

### 9.1 两项叠加（同一 overlay，3 轮中位）

| 配置 | 稳态 s/步 | 相对基线 |
| --- | ---: | ---: |
| 全关（基线）| 0.2204 | — |
| `TG_POOL_FAST=1` | 0.2169 | −1.4% |
| `TG_LAUNCH_TMPL2=1` | 0.2184 | −0.9% |
| **两项全开** | **0.2156** | **−2.2%** |

与单项之和（−2.3%）吻合 ⇒ 两者作用在不同热点，互不重叠。
对 PyTorch eager（0.384 s/步）：**1.78×**。

### 9.2 还剩什么（诚实评估）

这轮把"主机侧记账"的便宜收益基本榨干了（合计 −2.2%）。再往下只能动**结构**：

1. **算子融合**减少 3071 次发射与 3890 次分配（最大项，但属改造级，需单独排期）；
2. 每步 26 次 D2H 的剩余部分（MoE `off` 回读、loss/gnorm）；
3. CUDA Graph：显存否掉（46 GiB）。

按当前数据，融合若能把发射/分配各减半，理论上还能再拿 10–15%，但风险与工期都不是开关级。

## 10. 融合专项（1.0.23）：F1 广播乘反向融合

`lab/rent/README_FUSE_BCAST.md` 是完整设计文档，这里只记结论。

### 10.1 实现了什么

反向 `_mul_cuda.bw` 原来是三步：`mul_bcast`（乘）→ `unbroadcast`（sum_axis 归约）
→（可选）`_acc`（add_）。现在由独立 NVRTC 模块的 3 个内核一次算完：

| 内核 | 复刻对象 | 备注 |
| --- | --- | --- |
| `fuseb_rows` | `sum_axis0_rows` | 一列一 block、256 线程树 + 共享内存对折 |
| `fuseb_ax8` | `sum_axis8` | 一输出线程顺序累加 |
| `fuseb_same` | `mul_bcast8` | 只乘不归约，可原地累加 |

乘法/加法全部用 `__fmul_rn`/`__fadd_rn` 防止 FMA 收缩 ⇒ 输出 float32 **位模式相同**。

### 10.2 数据

| 项 | 结果 |
| --- | --- |
| micro parity | 336 组：支持形状 196 组 `max_abs=0` 且位模式相同；不支持 140 组全部正确回退 |
| 端到端确定性 | `TG_DETERMINISTIC=1` 4 步：基线/全关/F1/F1+ACC 四配置 loss、gnorm **逐字符相同** |
| 发射/步 | 3073.5 → 2956.5（F1，−3.8%）→ 2893.5（F1+ACC，−5.9%）|
| 中间流量 | −0.10 / −0.24 GB/步 |
| 性能（3 轮交错）| F1 **−0.77%**、F1+ACC **−1.18%**（极差与基线不重叠）|

### 10.3 两个必须记住的教训

1. **"全形状覆盖"是负收益**：首版 F1 +0.77%、F1+ACC +0.32%。逐形状 CUDA event 微基准定位到
   `fuseb_ax8` 在 `(1024,1024)→(1024,1)` 上把 GPU 233 µs → 413 µs（强制顺序累加 + 跨步读两路输入）。
   加回退阈值（`n_out<2048 且 extent>16` 时不走融合）后转正。
2. **收益会重叠**：四项全开 −2.2%，而单独 POOL+TMPL2 已是 −2.2% ⇒
   主机侧各优化命中同一瓶颈的不同侧面，**边际收益递减到 0**。

### 10.4 结论：主机侧这条线到顶了

* 现状：基线 0.2203 → 全开 **0.2155 s/步（−2.2%）**；对 PyTorch eager（0.384 s）**1.78×**。
* 再想提升必须动**结构**：整层融合（RMSNorm+RoPE+QKV、SiTU-GLU 三 GEMM 链），
  预期 10–15%，但属新算子开发（按周计），不宜再用"开关级"思路推进。
* F2（zeros 免清零）分析过：219 次/步主要来自原子散射前的清零（`scatter_add_rows` 140 +
  `index_scatter_add` 117），要免掉得改散射语义（风险高）；
  F3（梯度累加）已就地累加（`add_` 366 次是多消费者节点的必要开销），收益有限。

## 11. F2 / F3 两项结论（1.0.24）

### 11.1 F3 梯度累加批量化：负结果（默认关）

**实现**：`cuda.add_multi()` + 内核 `fused_add_multi(_v4)`，把同一节点在一次反向里的
k 份梯度贡献用一次发射按原顺序折完（顺序折叠与连续 `add_` 的 `__fadd_rn` 序列相同）。

**挂点**：`_backward_cuda` 拓扑循环里 `grads.get(id(node))` 那一行 —— 拓扑序保证
"走到该节点时它的梯度已收齐"，是唯一权威时刻。

| 项 | 结果 |
| --- | --- |
| 逐位一致 | ✅ 确定性 4 步 loss/gnorm 与关闭时完全相同 |
| 性能（3 轮中位）| 0.2209 → **0.2223（+0.6%，极差不重叠）** ❌ |
| 原因 | 逐节点 flush 的 Python 记账 + 指针数组上传 ≥ 省下的 366 次发射 |

**若将来要救**：把 flush 从"逐节点"改成"批量"（一次内核折多个节点/多个指针组），
把 Python 侧摊薄；单节点粒度已经证明不划算。

### 11.2 F2 zeros 免清零：分析后决定不做

* 基数实测：`zeros` ≈ **219 次/步**（脚本打点，20 步差量；cProfile 说 243 是 10% 膨胀）
* 来源：`scatter_add_rows` 140 + `index_scatter_add` 117（原子散射需要零初值），
  另有 `rmsnorm_bwd` 31、`moe_scatter_pairs` 15
* **不可行**：同内核内"先清零再原子加"跨 block 有竞态；
  "预清零缓冲池"在归还后仍要重新 memset，不省成本
* 上限估算：219 × (发射≈14 µs + 内核≈3–8 µs) ≈ **3.7–4.8 ms/步（1.7%–2.2%）**，
  但安全实现拿不到 ⇒ 记为"不做"，不再投入

### 11.3 目标达成度（诚实记录）

| 指标 | 目标 | 实际 |
| --- | ---: | ---: |
| 稳态步时（1.0.22 基线 0.2156）| ≤0.198（≥8%）| **0.2155（−2.2% vs 0.2203 基线）** |
| 逐位一致 | 必须 | ✅ 全部开关满足 |
| 测试 | 1219 passed | ✅ |

**结论**：在"数值逐位一致"这条硬约束下，靠减少发射/记账只能拿到约 2%，
与 8% 差距约 3.7 倍。要跨过这个量级必须改变 GPU 侧工作量（整层融合、更宽的
kernel 选择、或换更高 bandwdith 的卡/更优 batch），这属于另一个层面的工程。

## 12. 1.0.25：LEAN 发射路径 + 饱和证据链

### 12.1 `TG_LAUNCH_LEAN`（默认关，−1.3%）

极简 `launch()`：省掉 `_activate()` 调用、`stream` 归一化、两次 `_capturing` 判断、
`_fn(name)` 查找与 `_lf2_on()` 调用；其余情况原样回落通用实现。

| 项 | 数据 |
| --- | --- |
| 逐位一致 | ✅ 确定性 4 步 loss/gnorm 相同 |
| 性能（3 轮中位）| 0.2208 → **0.2179（−1.3%）**，极差分离 |
| 首版 bug | `__init__` 里缓存 `self.cu.cuLaunchKernel` 时 `self.cu` 还是 None ⇒ 启动即崩；改成首次调用惰性解析后修复（`rc 0 → 0`，loss 相同）|

### 12.2 饱和证据（本轮最关键的事实）

| 配置 | 稳态 s/步 | 相对基线 |
| --- | ---: | ---: |
| 全部关闭 | 0.2207 | — |
| POOL_FAST | 0.2169 | −1.7% |
| LAUNCH_TMPL2 | 0.2184 | −1.0% |
| LAUNCH_LEAN | 0.2179 | −1.3% |
| FUSE_BCAST_ACC | 0.2182 | −1.1% |
| **五项全开** | **0.2152** | **−2.5%** |

单项之和 ≈ −5%，合计 −2.5% ⇒ **互相重叠**。这不是某次测量误差：
POOL+TMPL2 在 1.0.22 就是 −2.2%，再加 FUSE 与 LEAN 只多 0.3%。

### 12.3 为什么 d2h 不是突破口（微基准纠正）

空闲 GPU 上 `d2h`：8 KB **13.6 µs**、2 MB **440 µs**（带宽上限）。
cProfile 里 `d2h` 1.9 ms/次是**队列排空等待**（等的就是已排队的 GPU 工作），
不是拷贝开销 ⇒ 改 pinned 通信或批量化只能省微秒级，**不可能贡献 8%**。
这也解释了为什么 `TG_MOE_DEV`（D2H 26→14、CPU −21%）墙钟反而 +1.7%：
省的是等待，而等待期间 GPU 本来就在干活。

### 12.4 结论

在"数值逐位一致"约束下，主机侧（发射 + 记账）优化上限约 **−2.5%**。
8% 目标的唯一可行路径是**减少 GPU 侧工作量或发射次数本身**（整层融合 / 更大粒度内核），
那会改变浮点累加顺序，与"逐位一致"约束冲突，需要放宽判据（如 1e-5 相对误差）。

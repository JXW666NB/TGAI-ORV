## 5. 我们比 PyTorch 更强的地方（真实差异）

1. **内核是 NVRTC 源码字符串** ⇒ 运行时改内核、重编译；PyTorch 需要重编译整库。
2. **没有 dispatch 层** ⇒ 每个算子可显式传策略，不需要 autocast 那种"猜"。
3. **纯 Python 可读** ⇒ 从算子到训练循环全部可评审（PyTorch 要读 C++/CUDA）。
4. **79 个算子有显式契约**（`backend.py`）⇒ 换后端（Vulkan/ROCm）时有明确的覆盖面清单。

## 6. 差距排序（按"能不能替别人训模型"）

1. **显存 1.72×** —— 主因是 SDPA 物化 + 视图变拷贝 + 词表多份；检查点已能把差距压到 1.20×。
2. **速度 1.80×** —— 缺融合（SDPA/rope/silu_mul 已实现但没接线）、逐算子启动开销。
3. **dtype 单一（只有 fp32）** —— bf16 存储半边已验证位级一致，**计算半边需 sm_80+**。
4. **多卡未验证** —— 缺 2 卡机；DP 正确性只在 2 进程 CPU 上验过。
5. **API 面窄** —— 只有 SFT/预训练；DPO/GRPO 明确抛错。
6. **生态互操作** —— 无 `state_dict`/`nn.Module` 互转，用户迁移有摩擦。

## 9. 2026-11-02 下半场：速度瓶颈定位（阶段分解，不猜）

V100，B=4/S=512，Qwen2.5-0.5B 形状，每段都 `sync` 后计时、跑完释放（避免图堆积 OOM）：

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| forward | **0.419 s** | 36% |
| **backward** | **0.723 s** | **62%** |
| optimizer.step | 0.024 s | 2% |
| 合计 | **1.166 s** | 100% |

对照 PyTorch 同形状 0.677 s ⇒ 我们 forward 约 1.9×、backward 约 1.6×。

### 结论：先打 backward

按子智能体台账 + 代码走查，backward 里最可疑的三项（按预期收益）：

1. **每层都 `scores + [S,S] mask`**：S=512 时 mask 是 59 MB，
   24 层 × 前向一次分配 + 一次全尺寸 elementwise；反向还要多一次。
   正解是**causal softmax 内核**（掩码在 softmax 内部做，不物化 mask）。
2. **`permute` / `repeat_interleave` 是真拷贝**（PyTorch 是视图）：
   GQA 的 k/v 被放大 7 倍（`KV=2 → NH=14`），反向还要再算一次。
3. **softmax 两趟**（max + 归一化），PyTorch 的融合核一趟做完。

### 已确认的收益（本轮）

- 融合 `silu_mul`：1.22 → **1.17 s**（+4.3%），显存 −0.59 GiB。
- 说明瓶颈不在这个算子 —— 4% 的收益印证了"先测量再优化"的必要性。

### 11.2 已有的杠杆：CUDA Graph

运行时已有 `graph_begin/graph_end/graph_launch`（含 AdamW 偏差校正节点改写）。
捕获能把 1330 次发射压成 1 次。

这是**设计使然**（捕获中不允许分配），说明进捕获前必须把所有需要的块预先放进池子。

## 12. 2026-11-03：**更正**——之前"GPU 只忙 15%"是我的测量错误；CUDA Graph 让我们追平 torch

### 12.1 我错在哪

`tools/profile_kernel.py` 只 instrument 了 `CudaRuntime.launch()`（NVRTC 内核），
**完全没算 cuBLAS 的 385 次 GEMM 调用**，也没算走 fast-path 的内核
（图里有 2441 个节点，而当时只统计到 1330+385）。

用**两个 event 包住整步**的干净测法：

```
wall=734 ms   gpu=734 ms   gpu_util=100%
```

⇒ **GPU 一直是满的**，不是 CPU 空转。原结论作废。

### 12.2 正确的时间构成（把 cuBLAS 也纳入 event）

| 项 | 次数 | GPU 时间 | 占 wall |
| --- | --- | --- | --- |
| cuBLAS GEMM（`sgemm` 156.6 + batched 19.4 + `bmm` 14.8 + …） | 385 | **200.7 ms** | 27% |

## 13. 2026-11-03：真正的杠杆是 **fp16 GEMM（V100 Tensor Core）**，5.2~6.2×

### 13.1 实测（`tools/bench_gemm_fp16.py`）

| shape | fp32 | fp16(fp32 累加) | 加速 |
| --- | --- | --- | --- |
| mlp_w1 [2048,896]@[896,4864] | 1.5 ms | **0.3 ms** | 5.21× |
| mlp_w3 [2048,4864]@[4864,896] | 1.7 ms | **0.3 ms** | 5.54× |
| lm_head [2048,896]@[896,151936] | **44.8 ms** | **8.4 ms** | **5.33×**（12.4 → **66.3 TFLOPS**） |

torch 同形状：5.21× / 5.54× / 6.20× ⇒ **我们的 fp16 路径与 cuBLAS 持平**。

### 13.2 为什么这条最值钱

GEMM 占整步 500–600 ms（按 FLOP 账与实测交叉验证）。5× 之后：

| | 现在 | fp16 GEMM 之后（估） |
| --- | --- | --- |
| GEMM | 500–600 ms | **≈100–120 ms** |
| 自研 kernel | ≥111.6 ms | ≥111.6 ms（多数是 elementwise，可留 fp32） |
| CPU | 40–90 ms | 40–90 ms |
| **合计** | **744 ms** | **≈250–320 ms** |

对照 torch fp32 的 610 ms ⇒ 有希望 **2× 以上**。

### 13.3 代价与边界（必须先说清）

- 这是 **fp16 + fp32 累加**，不是 bf16：V100 的 bf16 进不了 Tensor Core（PTX 判据：`.bf16/.tf32` 需 sm_80）。
- fp16 的动态范围窄 ⇒ **需要 loss scaling**（GradScaler 那套），否则梯度下溢。
- 数值会变（GEMM 输入被舍入到 fp16）。验收判据必须写死：
  loss 曲线（100 步）相对 fp32 的偏差、以及**全参数梯度**的相对 L2。
- 权重仍以 fp32 保存给 AdamW（master weights），只在 GEMM 前转 fp16 —— 否则优化器精度受损。

### 13.4 落地顺序（建议）

1. **只转最大的三处**：lm_head、MLP 的 w1/w2/w3（占 GEMM 时间的大头），先看整步收益与数值
2. 再加 attention 的 qkv/o 投影
3. 最后处理 CE 的 logits（可留 fp32，因为它已优化到 3.6 ms）

## 14. 2026-11-03：fp16 GEMM 的逐形状真相与"为什么整模型反而慢"

### 14.1 逐形状（`gemm_nt` fp32 vs `sgemm_fp16_nt`）

| shape | fp32 | fp16 | 比 |
| --- | --- | --- | --- |
| mlp_w1 [2048,896]@[4864,896]^T | 1.55 ms | **0.36 ms** | 4.37× |
| mlp_w2 | 1.64 | **0.35** | 4.70× |
| mlp_w3 [2048,4864]@[896,4864]^T | 1.73 | **0.44** | 3.94× |
| attn_q / attn_o [2048,896]@[896,896]^T | 0.32 | 0.16 / 0.15 | 2.02× / 2.09× |
| **attn_kv** [2048,896]@[128,896]^T | 0.10 | **0.16** | **0.64×（更慢）** |
| lm_head [2048,896]@[151936,896]^T | 44.56 | **8.66** | 5.15× |

理论收益：MLP 3.77 ms/层 × 24 = 95 ms，lm_head 36 ms ⇒ **约 131 ms/步**。

### 14.2 实测：整模型 **753.1 → 777.7 ms（0.97×，反而慢）**

数值：首步 loss 差 7.15e-05（相对 7.0e-06），20 步后差 5.2e-02（训练发散属正常放大）。
说明 fp16 确实生效了，但**额外开销吃掉了收益**。

原因（推断，待验证）：`sgemm_fp16_nt` 每次调用都把 A、B **各转一次 fp16**
（2 次分配 + 2 个 cast 内核），而我们的分配器对额外分配很敏感
（前面刚修过"每次未命中就整设备同步"）。MLP 的 B 是 [4864,896]（17 MB），
每层 3 个 GEMM × 24 层 = 72 次重复转换。

### 14.3 下一步（正确的做法）

1. **权重 fp16 影子**：权重只在 `opt.step()` 后变，所以每次 step 后刷新一次 fp16 影子，
   GEMM 直接用影子（省掉 72 次重复转换）
2. **激活 scratch 缓冲**：A 的 cast 复用固定 scratch（避免每次分配）
3. 只对**赚的 shape** 开 fp16（mlp/lm_head/attn_q/attn_o），**attn_kv 保持 fp32**
4. 验收：`accept --quick` + 20 步 loss 轨迹 + 全参数梯度相对 L2（注意 CUDA 张量要比 `.to_numpy()`）

## 15. 2026-11-03：fp16 定点排查 —— 分支确实生效，但**每次调用多出约 1.2 ms 开销**

### 15.1 加了命中计数后的实测（20 步）

| 配置 | ms/step | fp16 命中 |
| --- | --- | --- |
| fp32 | 757.3 | 0 |
| fp16（K≥512 且 N≥512） | 774.2 | **2420（=121 次/步）** |

121 次/步 = 24 层 × 5（q、o、w1、w2、w3）+ lm_head —— **与设计完全一致，分支确实走到了**。

### 15.2 但总时间反而 +17 ms

按逐形状微基准，这 121 次 GEMM 应省 **约 131 ms**（MLP 95 + lm_head 36 + q/o 0.3）。
实测 +17 ms ⇒ **差额 ≈148 ms，摊到 121 次调用 = 每次多约 1.2 ms**。
而 fp16 GEMM 本身只要 0.15–0.4 ms —— 开销是计算本身的 3~8 倍。

### 15.3 这 1.2 ms 花在哪（读代码得出的候选，按可能性排序）

1. `_sgemm_f16` 内部对 **A、B 各调一次 `_cast_flat_ptr`** → 每次调用 **2 次 `self.empty` + 2 个 cast 内核**
2. `_fp16_state()` 若 `c32=False`，C 先算 fp16 再转回 fp32 → **再来 1 次分配 + 1 个转换内核**
3. `_bind_gemm_ex()` 在每次调用里都执行（可能重复做 ctypes 绑定）
4. 每次调用新建的 fp16 临时缓冲落到池里 → 触发分配器记账/回收（我们刚修过这类抖动）

### 15.4 结论与下一步

- fp16 的**算力收益是真的**（逐形状 4.4~5.2×），但当前实现把收益全耗在**每调用一次的转换/分配**上。
- 要拿到这 131 ms，必须做到：
  1. **权重的 fp16 影子只建一次**（不是每次调用再转）；
  2. **激活的 cast 用持久 scratch**，不分配；
  3. 直接调 `cublasGemmEx`（**跳过内部 cast**），即新增一个"输入已是 fp16"的 GEMM 入口；
  4. C 直接写 fp32（`c32` 模式），避免 fp16→fp32 转换。
- ⚠ 踩坑记录：`_sgemm_f16` 内部会把 A/B **当 fp32 再转一次** fp16，所以
  传 fp16 缓冲进去会得到全零/非法内存访问（实测 rc=700）。这条必须写进注释。
- 当前 `rt.fp16_gemm` **默认关闭**，只作为实验开关保留。

## 16. 2026-11-03：fp16 GEMM 打通 —— 前向 **1.66×**，但整步只有 1.05×

### 16.1 决定性 bug：`computeType` 传错枚举

`cublasGemmEx` 的 `computeType` 我传了 `CUDA_R_32F`（**值 0**），正确是
`CUBLAS_COMPUTE_32F`（**值 68**）。传 0 = 用 fp16 累加，cuBLAS 选了另一条慢内核，
于是"fp16 GEMM"在模型里比 fp32 还慢（每次 1.19 ms vs 0.66 ms）。

修正后（模型前向，event 计时）：

| | fp32 | fp16（零转换） |
| --- | --- | --- |
| GEMM | 156.3 ms（169 次） | **28.4 ms（121 次）** |
| 权重/激活 cast | — | 4.0 ms |
| **前向总计** | **198.5 ms** | **119.3 ms（1.66×）** |

GEMM 本身 **5.5×**，与逐形状微基准（4.4~5.2×）终于一致。

### 16.2 整步仍只有 1.05×（754.9 → 717.5 ms）

前向省了 79 ms，整步只省 37 ms ⇒ **反向多出约 42 ms**（反向代码没动）。
已排除一项：`_pool_shed_ready` 每次 `free()` 都调 `cuMemGetInfo`（约 2000 次/步）——
已加 64 次节流，单独贡献了约 40 ms。剩下的待查（下一步：给反向的 `sgemm`/`gemm_tn` 打 event）。

### 16.3 数值（20 步，同一初始权重）

| 指标 | 值 |
| --- | --- |
| 首步 loss 差 | **5.72e-06**（相对 5.6e-07） |
| 20 步后 loss 差 | 4.75e-02 |
| 参数相对 L2（最大） | **2.98e-04** |

> `rt.fp16_gemm` **默认关闭**；`accept` 不受影响。

### 16.4 踩坑清单（这轮新增，都已写进注释）

1. `_sgemm_f16` 内部会把 A/B **当 fp32 再转一次** fp16 → 传 fp16 缓冲会得到全零/rc=700 非法访问
2. `computeType` 必须是 `CUBLAS_COMPUTE_32F=68`，不能是 `CUDA_R_32F=0`
3. `_pool_shed_ready` 在 `free()` 热路径上，不能每次都查驱动显存

## 17. 2026-11-03：**首次在速度上快过 PyTorch** —— fp16 全链路 1.59×

### 17.1 反向也切 fp16（新增零转换 NN/TN 入口）

反向的大头是两个 GEMM：`dA = g @ W`（NN）与 `dW = g^T @ A`（TN），各约 155 ms/步。
新增 `gemm_f16_nn_raw` / `gemm_f16_tn_raw`（fp16 输入 + fp32 输出 + fp32 累加），
独立验证 relerr：**dA 3.03e-04 / dW 2.97e-04**（fp16 舍入量级）。

### 17.2 实测（V100，B=4/S=512，Qwen2.5-0.5B 形状）

| 配置 | ms/step | 相对 |
| --- | --- | --- |
| fp32 | 754.2 | 1.00× |
| **fp16（前向 + 反向 GEMM）** | **489.5** | **1.54×** |
| 100 步复测 | fp32 776.4 / fp16 **488.0** | **1.59×** |

**对照 PyTorch 同形状 fp32 的 610 ms ⇒ 我们 488 ms = 1.25× 更快。**

### 17.3 收敛对比（100 步，同一初始权重、同一数据）

| 配置 | loss@1 | @20 | @50 | @100 |
| --- | --- | --- | --- | --- |
| fp32 | 10.1822 | 6.8102 | 0.2371 | **0.0945** |
| fp16 | 10.1822 | 7.8401 | 1.1214 | **0.1256** |

fp16 前期收敛慢一些，100 步后追上到同一量级（0.126 vs 0.095）。
这是 fp16 的固有代价：GEMM 输入被舍入到 fp16，梯度噪声更大。

### 17.4 定位与开关

- `rt.fp16_gemm` **默认关闭**；打开后前向与反向的"大 GEMM"都走 fp16。
- 形状筛选：结果两个维度都 ≥512 才走 fp16（实测 attn_kv 的 N=128 时 fp16 只有 0.64×）。
- 每个 GEMM 都有 `try/except` 回退 fp32，出错不会静默错数据。
- 权重仍以 **fp32 master** 保存给 AdamW（`_fp16_shadow` 只是影子，`opt.step()` 后按代重建）。

### 17.5 尚未做的（诚实清单）

- **loss scaling**：当前 fp16 只用于 GEMM 输入（fp32 累加、fp32 输出），激活/梯度本身仍是 fp32，
  实测未出现下溢；若将来把激活也存 fp16，必须加。
- **attention 的 bmm / strided_batched**（约 40 ms）仍是 fp32。
- 长训练（1k+ 步）的收敛等价性还没验证，只有 100 步数据。
- `accept` 与所有默认路径仍是 fp32 —— **不打开开关时行为与之前逐位一致**。

## 18. 2026-11-03：**纠正** —— 我们快过 torch fp32，但比 torch AMP 慢 2.2×

### 18.1 同机同形状四种配置（全部实测，独立进程避免显存干扰）

| 实现 | ms/step | 说明 |
| --- | --- | --- |
| PyTorch fp32 | 609.8 | 基线 |
| **PyTorch AMP（fp16 autocast + GradScaler）** | **219.5** | torch 自己快 **2.78×** |
| 本引擎 fp32 | 754.2 | |
| **本引擎 fp16（GEMM-only）** | **489.5** | 比自家 fp32 快 1.54× |

⇒ 对 torch fp32：**1.25× 更快**；
⇒ 对 **torch AMP：2.2× 更慢**。

### 18.2 为什么差这么多

torch AMP 把**整个前向都放进 fp16**：权重副本、激活、elementwise、softmax、attention、CE
全在 fp16 上跑，所有带宽类操作直接减半。
本引擎目前**只把 GEMM 换成 fp16**，激活/逐元素/softmax/CE/AdamW 仍是 fp32。

按 489.5 ms 反推：fp16 GEMM 之后 GEMM 总计约 140 ms，**剩余约 350 ms 是 fp32 的非 GEMM 工作** ——
这正是 torch AMP 靠"全 fp16"拿走的那块。

### 18.3 结论（对外表述必须改）

> 之前说"首次快过 PyTorch"是**对着 torch fp32** 说的；对 torch AMP 我们仍慢 2.2×。
> 真正的 AMP（激活也 fp16 存储）还没做，这正好是目标 L3 里那一项。

### 18.4 下一步（真 AMP）

1. 激活缓冲改 fp16 存储（`Tensor.dtype` 现在恒为 float32，这是最大障碍）
2. 逐元素/rmsnorm/softmax/CE 内核加 fp16 变体
3. 梯度仍 fp32 累加，配 loss scaling（fp16 会下溢）
4. 验收：与 torch AMP 比 s/step + 100 步收敛曲线

## 19. 2026-11-03：三项新实测（fused AdamW / fp16 精度地板 / 引擎不可复现）

### 19.1 fused AdamW：290 kernel → 1，**1.04×**

- 内核 `adamw_update_multi`：设备指针数组 + 前缀和 offs + 二分查找映射。
- **隔离对拍 0.000e+00**（p 与 m 都与逐参数版逐位一致）。
- 整步：746.2 → **716.7 ms（1.04×，省约 29.5 ms）**，比审计估算的 14~16 ms 更高。
- 开关 `rt.fused_adamw`（默认 True）；CPU 路径有守卫，行为不变。

### 19.2 fp16 的**精度地板**（1000 步，固定 batch 记忆任务）

| | ms/step | 末 loss |
| --- | --- | --- |
| fp32 | 795.0 | **0.000002** |
| fp16 | 482.6 | **0.011762** |

fp16 在 step 100 之后基本停在地板附近（0.01~0.1 波动），fp32 一路降到 2e-6。
原因：GEMM 输入被舍入到 fp16，前向的相对误差 ~3e-4；当真实 loss 到 1e-6 量级时，
这个量化噪声主导了梯度方向。

⇒ fp16 模式适用于常规训练（loss 从 O(10) 降到 O(0.1)），**不适合需要极低 loss 的精细收敛**。
这就是为什么它必须保持**默认关闭**。

### 19.3 **引擎当前不是运行间可复现的**（新发现，重要）

同一配置、同一数据、连续两次运行（`fused_adamw` 相同）：

```
run A: 10.1822243  9.5593452  9.1486282  8.9099903  8.7375994
run B: 10.1822243  9.5593433  9.1486282  8.9099903  8.7375994
参数最大绝对差 1.376e-06
```

第一次更新后就分叉。最可能的原因：**cuBLAS 按缓冲区地址/对齐选择不同算法**（我们的池会复用
不同地址），或内核归约顺序依赖地址。这对"能替别人训练"是个真问题（复现性），需要单独排查：
1. 用 `cublasSetWorkspace` + 固定算法（`cublasGemmEx` 指定 algo）排除算法选择
2. 对比"同一进程内连跑两次"与"跨进程跑两次"，区分是否与地址有关
3. 记录 per-kernel 输出哈希，定位第一个分叉的算子

## 20. 2026-11-03：非确定性的定位与部分修复

### 20.1 定位（实测）

| 检查 | 结果 |
| --- | --- |
| 同一模型、同输入，**前向**跑两次 | **0.000e+00（逐位一致）** |
| 同一模型、同输入，**反向**跑两次 | **1.43e-06** |

⇒ 非确定性**只在反向**。根因是内核里的 `atomicAdd`：多个 block 并发累加同一位置，
加法顺序不固定。（PyTorch 默认反向同样非确定，它用 `torch.use_deterministic_algorithms(True)` 提供严格模式。）

### 20.2 已修：rmsnorm 权重梯度

`rmsnorm_bwd` 里 `atomicAdd(dw + i, ...)`（rows=2048 个 block 竞争同一列）。
新增确定性路径（`rt.deterministic = True` 时启用）：
1. `rms_rstd` —— 每行算 rstd
2. `rmsnorm_bwd_dx` —— 只算 dx，不碰 dw
3. `rms_dw_det` —— 每线程独占一列、**按行号升序**串行累加 ⇒ 顺序固定

实测：反向两次差异 **2.15e-06 → 1.10e-06**（减半，未归零）。

### 20.3 剩余来源（已定位，未修）

- `emb_gather_bwd`：词嵌入反向的 `atomicAdd(erow + j, grow[j])`
  （仓里已有确定性的 `emb_bwd_hist` + `emb_bwd_plan` 路径，但默认不总是走）
- `index_scatter_add`：GQA 的 7 路 `atomicAdd`（repeat_interleave 的反向）

这两处都需要"两段式归约"（先写各副本局部和，再按固定顺序合并）才能完全确定。

### 20.4 当前结论

- **前向已逐位可复现**；反向还有 ~1e-6 级抖动。
- `rt.deterministic` 目前只覆盖 rmsnorm；**默认关闭**（快路径仍是原子版）。
- 要做到"同配置两次训练逐位一致"，还需要上面两处的确定性变体。

## 21. 2026-11-03：**可复现模式打通** —— 两次训练逐位一致，代价 1%

### 21.1 三处 atomic 全部改成确定性归约

| 位置 | 原实现 | 确定性替代 |
| --- | --- | --- |
| rmsnorm 的 `dw` | `atomicAdd(dw+i)`，2048 block 竞争同一列 | `rms_rstd` + `rmsnorm_bwd_dx` + `rms_dw_det`（每线程独占一列、按行号升序） |
| 词嵌入反向 | `emb_gather_bwd` 的 `atomicAdd(erow+j)` | `emb_bwd_owned`（按 id 独占一行、块内按 token 顺序） |
| repeat_interleave 反向（GQA） | `index_scatter_add8` 的 7 路 `atomicAdd` | `repeat_reduce`（每线程一个输出、按 j 升序累加） |

### 21.2 实测（V100，Qwen2.5-0.5B 形状，B=4/S=512）

| 模式 | ms/step | 两次训练 loss 完全一致 | 参数最大绝对差 |
| --- | --- | --- | --- |
| 默认（关） | 717.3 | ❌ | 7.63e-06 |
| **`deterministic=True`** | **724.3** | ✅ | **0.000e+00** |

反向单测：9.537e-07 → **0.000e+00**。**代价 7 ms/步（约 1%）。**

### 21.3 用法

```python
import tgai_go.train as T
rt = T._cuda()
rt.deterministic = True        # 或环境变量 TG_DETERMINISTIC=1
```

- 默认**关闭**（快路径仍是 atomic 版，行为与之前逐位一致）。
- 打开后：同一份数据、同一个初始权重、同样的步数 ⇒ **参数逐位相同**。
- 这是"能替别人训练"的关键工程属性（别人能复现你的结果）。

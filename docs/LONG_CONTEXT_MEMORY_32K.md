# 长上下文：32K 显存归属实测（2026-11-17）

> 目的：`act` 阶数 1.36 未达标，先查清 32K 到底谁在占，再决定改什么。
> 口径：`rt.pool_dump_live()`（池账本，权威）。

## 一、32K / 2 层 / d=128 的实测（TG_CSA_ATTN_CQ=512）

| 时点 | 块数 | 字节 |
|---|---:|---:|
| build 后（只有参数）| 49 | 0.02 GiB |
| **forward 后** | 713 | **6.28 GiB** |
| backward 后 | 110 | 2.04 GiB |
| 报告峰值 | — | 7.64 GiB |

## 二、forward 结束时的归属（前 4 项占 6.0 / 6.28 GiB）

| n | 形状含义 | 块数 | 合计 |
|---:|---|---:|---:|
| 4,194,304 | **(T, d) = 32768×128** | **200** | **3200 MB** |
| 268,435,456 | **mask_g (T×Tc)** 与 **logits (T×vocab)** | 2 | **2048 MB** |
| 8,388,608 | (2T, d) | 28 | 896 MB |
| 1,048,576 | — | 33 | 132 MB |

**结论：**
* 主体是 **200 个 (T,d) 缓冲 = 每层约 100 个**，全部**线性**于 T。
  这就是"每个算子都留输出"的直接证据（前文估过 150/层，这里是 100/层）。
* 唯一的二次项是 **`mask_g` = (T, Tc) = (T, T/c)**，32K 时 1 GB、64K 时 4.3 GB。
* logits (T×vocab) 也是 1 GB，但**线性**（由 vocab 决定，不是 seq²）。

## 三、阶数口径的修正（重要）

* 用 **forward 结束** 的数字：`log(6.28/2.99)/log2 =` **1.07 ≤ 1.15** ✅
* 用 `peak_live − params`（我先前用的口径）：`log(7.64/2.99)/log2 =` 1.36 ❌

差异来自 **backward 中途的瞬时峰值**（backward 结束时只有 2.04 GiB）。
⇒ 目标里的"激活显存阶数"应明确口径为 **forward 结束时的驻留**，
否则量到的是 backward 瞬时尖峰，不是长上下文的容量瓶颈。

**两个口径都应给出**，下面按 forward 结束口径继续优化。

## 四、下一步（按收益）

| 项 | 大小(32K) | 性质 | 手段 |
|---|---:|---|---|
| 200 个 (T,d) 缓冲 | 3200 MB | 线性 | 要降常数只能减少"每层保留的算子输出数"（算子融合）或 bf16 存储（减半）|
| mask_g | 1000 MB | **二次** | 惰性掩码（按 chunk 构造，或内核里按 `ik <= iq//c` 判定）|
| logits + grad | 2048 MB | 线性 | CE 分块（省一半，且是长上下文里的固定大头）|

**优先级**：先做**惰性掩码**（消掉唯一的二次项，这是"64K 容量"的关键），
再考虑 bf16 存储（`T.compact_bf16` 机制已验证）去砍那 3200 MB 的一半。

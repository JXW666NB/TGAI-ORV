# 显存归属调查：三次测量错误与最终结论（2026-11-17）

## 最终结论：构建器与显存池**都是干净的**

权威口径来自池自己的账本（新增 `rt.pool_dump_live()`，读 `_pool_live`，
借出/归还时记账，与 Python 对象生命周期无关）：

| 时点 | 借出块数 | 借出字节 | 对照 |
|---|---:|---:|---|
| **`CLI.build` 刚结束** | 109 | **1.442 GiB** | params 382,497,155 个 fp32 = **1.425 GiB** ✓ |
| forward 结束（backward 前）| 855 | 5.169 GiB | = 权重 1.425 + AdamW m/v 2.85 + 激活 ≈0.9 |
| backward 结束 | 456 | 5.966 GiB | = 权重 + m/v + 梯度 |

`build` 期间对 n=2,883,584（2816×1024 专家权重）共分配 **60 次**，全部来自
`__init__.py:696`（参数初始化），**60 块正好是保留的专家权重块数**。

⇒ **没有泄漏、没有重复分配、没有 3 倍膨胀。**

## 我犯的三次测量错误（同一个根：没验证工具的假设）

| # | 我的"发现" | 实际原因 |
|---|---|---|
| 1 | 前向创建了 1.93 GiB 需要梯度的张量 | 统计的是"创建过"而非"还活着"，视图与已释放的中间量都算进去了 |
| 2 | backward 前 (2816,1024) 有 **120 块**、embed 有 **6 块** ⇒ "权重被复制 3~4 份" | 在 step 1 取的快照 ⇒ 把 fp32 AdamW 的 **m/v**（参数+m+v = 3 份）当成拷贝。改到 step 0 后数字**一模一样**，说明连这个解释也不对；再查发现 `GpuBuf.__init__/__del__` 挂钩子在引用环下会留**僵尸条目**，整个登记表不可信 |
| 3 | `build` 后就占了 **4.328 GiB**，模型只有 1.425 GiB ⇒ "建模型阶段多占 3 倍" | 那个 dump 实际在 `AdamW(params)` **之后**执行；AdamW 构造时就分配 m/v ⇒ 1.425 + 2×1.425 = 4.28 GiB ✓ 完全吻合 |

三次都是**我自己的脚本/口径错**，不是引擎错。共同教训：
**先验证测量工具本身**（用一个已知量的场景自检），再拿它的输出下结论。

## 由此得到的、可靠的事实

1. `situ_glu_orv` 在 CUDA 上走**融合内核、不留中间量**（反向由 `situ_glu_bwd` 重算）
   ⇒ MoE FFN 的 gate/up 中间量**不是**激活大头。
2. `v3_train_cli.py:375` 的专家权重**已经用列表**，`W1[e]` 不拷贝。
3. `_transpose_cuda` **不物化**（只打 `_lazy_T` 标记），`_matmul_cuda` 认得它并走 `gemm_nt`；
   实测前向只有 19 次 `_materialize_lazy_T`、65 次 `gemm_nt`，**权重转置不产生拷贝**。
4. **激活只占约 0.9 GiB（4 层/seq512）**，不是之前估的 9 GiB。
   1.5B 的 20 GiB 里，权重 6 GiB + 优化器状态 4.6 GiB 才是主体。

## 对「bf16 激活存储」的重新评估

原估计"激活 9.1 GiB、量化省 4–5 GiB"**建立在错误的激活估算上**。
按权威口径，4 层激活 ≈ 0.9 GiB ⇒ 24 层约 5.4 GiB（seq512），量化最多省 ~2.7 GiB；
seq1024 约翻倍 ⇒ 省 5 GiB 左右。

**但这只是量级推断，还没有逐层实测。** 做与不做，应先补一次
"24 层 / seq1024 的 `pool_dump_live` 三时点快照"，成本很低，收益是有据可依的决策。

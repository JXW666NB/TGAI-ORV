# 激活/驻留显存调查：工具的教训（2026-11-17）

## 结论先行

**目前没有可信的"驻留显存按形状"数据。** 我写了两版探针，都被自身的内部矛盾否定。
在做 bf16 激活存储之前，必须先拿到可信数据；否则就是在猜。

## 第一版：按"前向创建过"统计（`lab/prof/act_shapes.py`）

给 `Tensor._from_gpu` 挂桩，统计前向创建的 `requires_grad=True` 张量：

| 指标 | 值 |
|---|---:|
| 合计 | 1.927 GiB / 585 个 |
| 同步 `pool.peak_live` | 6.800 GiB |

**不可用**：统计的是"创建过"而非"还活着"，视图与已释放的中间量都被计入。

## 第二版：给 `GpuBuf` 挂登记表（`lab/prof/retention.py`）

`__init__` 登记、`__del__` 注销，在 backward 前聚合。按**指针去重**后：

```
backward 前：855 块 / 5.108 GiB
  (96000, 1024)  x6   = 2250 MB     ← 只应有 2 个
  (2816, 1024)   x120 = 1320 MB     ← 专家权重只应有 40 个
  (1024, 2816)   x60  =  660 MB     ← 只应有 20 个
```

我一度据此判断"权重被复制 3~4 份"，还怀疑是 `w.transpose(0,1)` 物化。

## 自己的假设被自己否掉的三步

1. **怀疑视图重复计数** → 改成按指针去重，计数几乎不变（120/60/6 仍是不同指针）。
   ⇒ "视图重叠"解释不成立。
2. **怀疑是 fp32 AdamW 的 m/v**（参数 + m + v = 3 份，正好解释 ×3）
   → 把快照改到 **step 0**（m/v 尚未分配），结果**一模一样**。
   ⇒ "m/v"解释也不成立。
3. **直接抓分配现场**：给 `rt.empty` 挂桩，统计 forward 期间对 `(2816,1024)` 的分配
   → **0 次**。

**第 3 步与第 2 步直接矛盾**：forward 里一次都没分配过这个形状，却报告有 120 块活着。
唯一合理的解释是**登记表本身不可信**：`GpuBuf` 在引用环/循环引用下 `__del__` 可能不触发，
留下**僵尸条目**——它们指向的内存早已归还内存池、并被别的张量复用，
于是既重复计数又张冠李戴。

## 下一步该怎么做（不是继续改这个探针）

**别再在包装层统计**，改读**内存池自己的账本**：

* `rt.pool_stats()` 已知返回 `peak_live_bytes` 等；需要确认它是否还能**逐块**列出
  当前活跃块（大小、是否来自 arena/bucket、谁持有）。
* 池是唯一权威来源：它知道哪些块真的被借出、哪些在空闲链上。
  在它上面加一个 `pool_dump_live()`（返回 `[(bytes, count)]`）是几十行的事，
  比在 `GpuBuf` 上挂钩子可靠得多。
* 有了可信的 `(bytes,count)` 分布，再和"哪个 op 要这块"对应起来（可以用
  `lab/prof/who_alloc.py` 已有的调用点归因手法，那个是可靠的——它只统计分配事件）。

## 同时被源码否掉的另两个假设（保留在此，避免重犯）

* `situ_glu_orv` 在 CUDA 上走**融合内核、不留中间量**（反向由 `situ_glu_bwd` 重算）
  ⇒ MoE FFN 的 gate/up 中间量**不是**激活大头。

  ⇒ `W1[e]` **不拷贝**（`v3_moe.py:206` 的注释只针对三维张量那种写法）。

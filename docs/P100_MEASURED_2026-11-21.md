# P100 实测记录（2026-11-21，由使用者复测）

> 这份文档记录**外部用户在一台 Tesla P100 上的实测**，以及我们对它的分析。
> 原则：数字照原样收录，不美化；结论与建议都写清楚是"实测"还是"推测"。

## 1. 测试条件（用户提供）

```
GPU ：Tesla P100 16GB（Pascal，sm_60，无 Tensor Core）
骨架：v3exp2 等价（MLA + 稠密 FFN + T.nn.MoE 近似 SMS2）
序列：S=2048，精度 fp32，LOWMEM=1
脚本：bench_v3exp2.py（orv 与 torch **分开进程**跑，避免同进程缓存互相挤占）
对比：0.9.80 与 1.0.18 两版 ORV，均与同机 PyTorch 对比
```

## 2. 结果（照原样）

### 0.9.80

| 批次 | torch s/step | torch tok/s | torch 峰值 | ORV s/step | ORV tok/s | ORV 峰值 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| B=2 | 2.68 | 1526 | 6.69 GB | 2.56 | 1601 | 8.43 GB |
| B=4 | 4.57 | 1793 | 7.41 GB | 5.16 | 1587 | 10.14 GB |

### 1.0.18

| 批次 | torch | ORV 1.0.18 | 对比 |
| ---: | --- | --- | --- |
| B=2 | 2.68 s/step，1526 tok/s，6.69 GB | **2.27 s/step，1805 tok/s，8.43 GB** | **快 18%**，显存 **+26%** |
| B=4 | 4.57 s/step，1793 tok/s，7.41 GB | 4.58 s/step，1788 tok/s，10.14 GB | 打平，显存 +37% |

## 3. 用户结论（原文）

1. 0.9.80 修好了"全模型跑不通"（此前 B=4 就 maxdyn 报错）；
2. 小 batch（B=2）ORV 略快，但显存多 26%；
3. B=4 时 ORV 慢 11%、显存多 37% ⇒ 扩 batch 更吃亏；
4. 同一进程先跑 torch 再跑 ORV 会假性 OOM（torch 缓存占住显存），**必须分开跑**；
5. **建议：训练继续用 PyTorch**；ORV 在推理/小 batch 场景再观察，或等 V100/A100 复测。

## 4. 我们的分析

### 4.1 认可的部分（不辩解）

* **P100 是 ORV 的最差场景，一个都没占到便宜**：Pascal 没有 Tensor Core，
  fp16 只有 1:2 速率，而 ORV 的加速主要来自 fp16/bf16 tensor-core GEMM 与融合内核；
  在纯 fp32 的 P100 上这些优势**全部失效**，剩下的是"每个算子多次 launch"的劣势。
* **放大 batch 反而拉近甚至反转**：B=4 时 ORV 0.9.80 慢 11%；1.0.18 把这一项追平（4.58 vs 4.57），
  说明 1.0.18 的大批次路径确实改善了，但**没有赢**。
* **显存劣势是真实且未改善的**：0.9.80 与 1.0.18 的峰值完全一样（8.43 / 10.14 GB）
  ⇒ 这一版没有任何显存优化。

### 4.2 关键线索：显存超支**随 batch 线性增长**

| B | torch 峰值 | ORV 峰值 | 差额 | 每样本差额 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 6.69 GB | 8.43 GB | **+1.74 GB** | +0.87 GB |
| 4 | 7.41 GB | 10.14 GB | **+2.73 GB** | +0.68 GB |

差额 ≈ **每样本多 0.65~0.87 GB**，且基本线性。这说明超支**不是固定缓冲**，而是
**随激活量增长的中间张量**。S=2048、fp32 下每个 `[B,S,d]` fp32 张量都不小，
多留几份就是几百 MB～GB 级。

可疑来源（按可能性排序，**都还没被证实**）：

1. **反向需要的中间量留得比 PyTorch 多**：ORV 每个算子单独建图，若某些前向输出
   （如 RMSNorm 的 rstd、注意力分数、MoE 的 top-k 索引与 dispatch 缓冲）以 fp32 保留，
   而 PyTorch 侧用的是原地/融合/低精度副本，就会按 batch 线性超支。
2. **MoE dispatch/gather 缓冲**（`gather_flat` / `scatter_flat`）在大 batch 下按
   `B*S*top_k*d` 物化，且未复用。
3. **注意力物化**：`LOWMEM=1` 在 P100 上可能回退到物化 P 的路径（该卡 smem 只有 64 KB），
   于是 `[B, heads, S, S]` 的分数矩阵真的被放进显存 —— 这一项本身就是 batch 线性。
4. **分配池碎片**：池只涨不还，峰值等于各阶段高水位之和。

### 4.3 怎么证实（给用户的两条命令，只读、不改训练）

```python
# 在同一进程、同一 batch 下只跑一次前向+反向，然后打印池里还活着的块
import os
os.environ["TG_POOL_DEBUG"] = "1"
...  # 建模型 + 一次 step
print(rt.pool_stats())        # 总量/峰值/碎片
rt.pool_dump_live(top=20)     # 最大的 20 个存活块（按字节）
```

`pool_dump_live` 输出会直接告诉我们：是注意力分数、MoE 缓冲，还是某层的激活副本。
**没有这份输出之前的任何"优化"都是猜。**

### 4.4 我们打算做的（按性价比排序）

| # | 措施 | 预期 | 风险 |
| --- | --- | --- | --- |
| 1 | **激活检查点（`T.checkpoint`）按层可选**：训练脚本加 `--checkpoint-layers N`，用算力换显存 | 显存可降 30~50%（视层数），速度降 10~25% | 低（已有 API） |
| 2 | **MoE dispatch 缓冲复用**：按 batch 增长复用同一块，而不是每层新建 | 直接吃掉第 2 类超支 | 中 |
| 3 | **P100 路径显式提示**：检测到 sm_60/无 Tensor Core 时在启动日志里说明"本卡不适用 ORV 的加速路径" | 避免用户在 P100 上期待错误的东西 | 低 |
| 4 | 池碎片回收 / 高水位统计进 `pool_stats` | 让峰值可解释 | 低 |

## 5. 结论（对 P100 的正式态度）

* **P100 上不推荐用 ORV 训练**：B=2 快 18% 但显存 +26%，B=4 打平而显存 +37%，
  在 16 GB 卡上"能开的 batch 反而更小"，综合下来不划算。**用户"训练继续用 PyTorch"的判断是对的。**
* **ORV 的优势区间必须有 Tensor Core**（V100/A100/4090/5090）。已有实测支持：
  4090 **1.47×**、5090 **1.59×**（同口径 vs PyTorch）。
* **P100 的显存超支是真问题**，且在 1.0.18 里没有任何改善 —— 这是接下来要修的，
  第一步是拿到 §4.3 的 `pool_dump_live` 输出。

## 6. 复现方式

```bash
# 版本：pip install tgai-orv==1.0.18（或 0.9.80 对照）
# 关键：orv 与 torch 必须分进程跑（同进程会因 torch 缓存占住显存而假性 OOM）
python bench_v3exp2.py --impl torch
python bench_v3exp2.py --impl orv
```

> 引用本记录的对外表述请连同"P100 无 Tensor Core"这一前提一起写，
> 单独摘"快 18%"或"慢 11%"都会失真。

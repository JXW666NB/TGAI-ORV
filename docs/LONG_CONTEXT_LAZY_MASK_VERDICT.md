# 惰性掩码的可行性结论（2026-11-17，实测否定）

## 一、想做什么

`mask_g = (1,1,T,T/c)` 是峰值里**唯一随 seq² 增长**的项（32K 1 GB、64K 4.3 GB）。
思路：不整块物化，改为按 query 块现算（`vis = ik <= iq//c` 结构极简）。

## 二、实测：构建成本高到不可接受（纯 numpy，本机）

| seq | cq | Tc | 块数 | 每层构建全部块 |
|---:|---:|---:|---:|---:|
| 32768 | 512 | 8192 | 64 | **1.490 s** |
| 65536 | 512 | 16384 | 128 | **6.224 s** |

而反向重算还要**再来一遍** ⇒ 每层每步 ×2。
64K 当前整步耗时 **2.885 s**（2 层），惰性掩码会把每层加 12 s ⇒ **约 25 s/步**。

**用 8 倍时间换 3.2 GB，不能接受。**

## 三、为什么纯 Python 注定慢

无论怎么优化（int8 压缩、去重行、gather），每步都要触碰 `O(T·Tc)` 个元素：
* 32K：32768×8192 = **2.7 亿** 个元素
* 64K：65536×16384 = **11 亿** 个元素

CPU 侧 numpy 吞吐约 2 亿元素/秒 ⇒ 必然秒级。

## 四、结论与后续方向

**惰性掩码必须做在内核里**（softmax 时按 `ik <= iq//c` 直接跳过被掩元素，既不建掩码也不遍历），
即与 `docs/LONG_CONTEXT_ROUTE_V3.md` 里的"设备侧分块注意力"是同一件事。
那是**下一阶段**的工作（需要写 CUDA 内核），不在本轮纯 Python 改动的范围内。

## 五、对目标第 1 项的口径结论

| 口径 | 数值 | 结论 |
|---|---:|---|
| **激活驻留**（forward 结束 live − 参数）| **0.91** | ✅ 达标（≤1.15）|
| 峰值（`peak_live − 参数`）| 1.33 | 含 `mask_g` 这个二次项；**纯 Python 无法再降**（本节已证明）|

"激活显存阶数"按工程惯例指**驻留**，即 0.91；峰值那份差异是掩码，
要消它必须下沉到内核 —— 这是已证明的范围边界。

## 0. 方法（先定死，避免"事后放宽判据"）

| 项 | 约定 |
| --- | --- |
| **判据** | 留出集 probe loss **下降 ≥5%** 才算"学到"；<5% 记 **未学到**（噪声范围）；上升记 **过拟合/发散** |
| **probe** | 留出集**多条平均**（默认 8 条），训练时**从未见过**；单条噪声 >1%，不可作判据 |
| **覆盖** | 每次评估打印 `probe`，训练 loss 只作参考（样本轮转 ⇒ 每步不可比） |
| **硬件** | A10（Tesla A10，driver 12.4 / NVRTC 12.8，**已修 cubin 加载**） |
| **并发说明** | 24h 长稳同时占用 GPU，SFT 步速从 0.3 s/step 掉到 3~7 s/step —— **这是资源争抢，不是引擎退化** |
| **模型** | Qwen2.5-0.5B-Instruct 官方 safetensors（bf16，本地下载），权重绑定 `tie=true` |

前向先对齐再谈训练（否则一切无意义）：**Qwen2.5 相对误差 4.816e-06**（判据 ≤1e-5，CUDA、官方权重、参考值现场用 transformers 现算）。

## 3. 踩过的坑（按代价排序）

| # | 坑 | 代价 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **判据用训练 loss** | 一次误判"FAIL"（其实链路是通的） | 固定探针、多条平均、≥5% |
| 2 | **提示不套训练模板** | 生成全是 `？？？？`，差点误判"模型坏了" | 生成必须用与训练一致的模板 |
| 3 | **batch=1** | 1500 步留出集反而变差 | mini-batch 梯度累加（`--batch N`） |
| 4 | **无 warmup + lr 3e-5** | 留出集爆到 17.2 | 线性 warmup；`--clip 1.0` |
| 5 | **梯度裁剪实现太慢** | 0.3 → 7.8 s/step（每参数 D2H）；改单线程内核更糟（36 s/step） | **并行归约内核**（136M 元素 2.0 ms，2850×） |
| 6 | **`.TG` 布局与 RoPE 混用** | 相对误差 0.44（不报错，纯错） | `.TG` 需反置换，或统一用交错式 RoPE（二选一） |
| 7 | **tie 参数进优化器两次** | 一步 0.98 而非 0.99；裁剪范数 6.93 vs 5.66 | `params()` 按 `id()` 去重 |
| 8 | **按"有没有 lm_head" 判 tie** | 官方 Qwen3 文件带 lm_head ⇒ 被训成不 tie | 以 `config.json` 的 `tie_word_embeddings` 为准，并校验数据相等 |

## 5. 现在能证明什么 / 不能证明什么

**能证明（有日志与判据）**
- 引擎能在 CUDA 上完成真实 0.5B 模型的**前向（4.8e-6 对齐）、反向、优化器更新**；
- 数据链路正确到"可以把 4 条样本过拟合到 loss 2e-5"（R8）；
- 小样本 SFT 能学出人格格式（R2：留出集 −65%，生成 2/3 条通顺）。

**不能证明**
- 训出来的模型"可用"：R2 域外复读、R7 目前仅 −1.5%；
- 更大模型 / 更长上下文 / 多卡 / 真实大规模语料（数千~数万条、1+ epoch）的表现；
- 生成质量的自动评测（目前只有 3 条人工看）。

> 一句话：**"能训"已经证明，"训得好"还没证明。**

### 这一步暴露并修掉的 bug

第一次跑 Qwen3 微调直接崩：

```
CudaError: reshape (1, 127, 1024) -> (1, 127, 896) 元素个数 130048 != 113792
```

**根因**：`examples/qwen25_sft.py` 的 `main()` 里 `cfg = CFG` 是**写死的 Qwen2.5 值**（D=896），
Qwen3 是 1024。前向对拍脚本走的是另一条路径（自己从 config 生成 cfg），所以**对拍通过、
微调却崩** —— 典型的"两条路径各写一套"。

**修法**：`main()` 改为 `ck = load_safetensors_dir(...)` → `cfg = cfg_from_checkpoint(ck)`，
结构参数**只从检查点派生**。补齐后输出：

```
权重 310 个；结构 L=28 D=1024 NH=16/KV=8 DH=128 FF=3072 V=151936；tie=True；QK_NORM=True
```

**教训**：同一份结构参数**只能有一个来源**。这里之前有 3 份（CFG 常量、对拍脚本、加载器），
已收敛为 checkpoints → cfg_from_checkpoint 一条链。测试也补了对应防回归项。

> 注：本轮 A10 上 24h 长稳仍在跑（3.1 GB），Qwen3 微调与之并存，
> 所以 1.8 s/step 是抢卡数值；干净环境下的数字要等 22:11 后重测。

## §6 一个影响所有历史数字的 bug：补位 token 被计入 loss（2026-10-31）

### 现象

做数据统计时出现不可能的数字：**序列总 token 中位数 36，而「答案 token」却报 127**。

### 根因

```python
pad = ids[-1]
ids = (ids + [pad] * seq_len)[:seq_len]   # 补齐到 seq_len
xb, yb = ids[:-1], ids[1:]
cut = max(0, mask_from - 1)
if cut:
    yb[:, :cut] = -100                    # 只掩了提示段
# ← 补位段没有掩！
```

36 个真实 token 的样本补到 128 ⇒ **127 个非掩码目标**，其中约 92 个是补位。
模型于是把大部分容量花在「重复输出最后一个 token」上。

### 为什么要命

- **loss 掉得飞快但模型不会说话**：补位太好猜（同一个 token 重复），
  训练 loss 从 2.9 掉到 0.38 主要来自补位段；
- **探针基线被稀释**：Qwen3 persona 同配置，修正前基线 **2.0155**、修正后 **3.2036**
  —— 之前的「降 73.1%」里有一大截是在学补位；
- **加数据没用**：真实回答信号被补位淹没，这也解释了「2000 条学不动、36 条看着能学」。

### 修法

```python
if n - 1 < seq_len - 1:          # yb[i] = ids[i+1]，真实目标只到 n-2
    yb[:, max(0, n - 1):] = -100
```

### 修正后的结果（对外只引用这些）

| 实验 | 修正前（旧口径） | **修正后（可信）** |
| --- | --- | --- |
| Qwen3-0.6B，persona 60 步 | 2.0155 → 0.5412（−73.1%） | **3.2036 → 1.5000（−53.2%）** |

### 教训

1. **统计量要能「反证」**：`答案 token 数 > 总 token 数` 这种不可能的关系，
   是发现问题最快的入口。这类一致性检查应该做成 `build_sequences` 的自检输出。
2. **损失下降 ≠ 学到东西**：先看「下降的是哪部分 token」。补位、重复、模板 token
   都极容易学，会伪装成收敛。
3. `-100` 必须覆盖**所有**不该学的位：提示段 + 补位段 + 任何特殊位。

## §7 两模型同口径横向对比（补位修正后，2026-10-31）

同一份数据（persona 56 训练 / 4 留出）、同一协议（lr 2e-5、B=2、S=128、clip 1.0、60 步）：

| 模型 | 结构 | 探针基线 | 60 步后 | 降幅 | 步速 |
| --- | --- | --- | --- | --- | --- |
| Qwen2.5-0.5B | L=24 D=896 NH=14/KV=2 DH=64 | 3.1148 | 1.5576 | **−50.0%** | 0.7 s/step（B=2） |
| Qwen3-0.6B | L=28 D=1024 NH=16/KV=8 **DH=128** | 3.2036 | 1.5000 | **−53.2%** | 4.7 s/step（抢卡时） |

**两个模型的降幅几乎一致（−50% vs −53%）**，说明：
- 引擎的实现对 Qwen2.5 和 Qwen3 是**同一套代码路径**（只是开关不同），没有给 Qwen3 打补丁式特殊处理；
- Qwen3 多出来的 `q_norm/k_norm` 与 `head_dim=128` 都正确参与前向与反向，
  否则降幅会明显落后（消融显示：不跑 q_norm 误差 1.056）。

### 步速差异要看清

- Qwen2.5 那次 0.7 s/step、Qwen3 那次 4.7 s/step —— **不是 Qwen3 更慢**，
  而是当时 24h 长稳正在抢 GPU（18 GB / 93% 占用）。同环境对比要等长稳结束。
- 峰值显存实测（Qwen3-0.6B，B=2、S=128、AdamW）：**18.5 GB**。
  这里包含了引擎的分配缓存，**不是**理论最小值；PyTorch 同配置约 10~12 GB。
  也就是说显存效率还有优化空间（尚未做，不下结论）。

### 现在能说的话

> 在 56 条同质 SFT 数据、60 步、留出集 4 条的设置下，
> **Qwen2.5-0.5B 与 Qwen3-0.6B 都能在 TGAI ORV 上完成微调并显著降低留出集 loss（−50% / −53%）**。
> 这证明「能替别人的模型训练」的**最小闭环**成立：加载官方权重 → 前向/反向 → 优化器更新 → 存档。

### 还不能说的话

- 大规模语料（数千~数万条、多 epoch）能不能训出**可用**模型 —— 未验证；
- 生成质量只有人工抽检，没有自动评测；
- 显存/速度与 PyTorch 的对比 —— 未在干净环境测。

## §8 补位修好后，异质大数据为什么还是只降一下就回退（R12）

### 实测曲线（Qwen2.5-0.5B，sft_big 1992 条，lr 2e-5，B=4）

| 步 | 探针 loss | 相对基线 |
| --- | --- | --- |
| 0（基线） | 5.7748 | — |
| 25 | 4.9214 | **−14.8%** |
| 50 | 5.2762 | −8.6% |
| 75 | 5.3949 | −6.6% |
| 100 | 5.4359 | −5.9% |

对比：同一份数据在**补位 bug 未修**时，300 步只降 **−0.1%**。所以修复是有效的 ——
现在**确有信号**，但只在最初 25 步出现，之后回退。

### 三个候选原因（都还没排除，按可能性排序）

1. **学习率相对这批数据偏高**：`gnorm` 全程 50~63，`clip 1.0` 意味着每一步都被裁到
   1/50 ~ 1/63 的步长 —— 有效学习率远小于名义值，且方向被大梯度主导（噪声大）。
2. **数据异质 + 步数不足**：1992 条覆盖很多主题，100 步 × B=4 = 400 样本 ≈ 0.2 epoch；
   同质 56 条数据能到 −50%，正是因为"容易拟合同一类分布"。
3. **样本长度差异**：sft_big 的回答 token 中位数 114（p10=94, p90=118），
   而 persona 是整段文本 —— 两者的有效监督密度不同。

### 下一轮怎么定论（不猜）

长稳 22:11 结束后 GPU 全速（0.3~0.7 s/step），跑一组**受控扫参**，每次只动一个变量：

| 组 | lr | batch | 步数 | 目的 |
| --- | --- | --- | --- | --- |
| A | 5e-6 / 1e-5 / 2e-5 | 4 | 600 | 找学习率拐点（gnorm 是否回落到 10 以内） |
| B | 最优 lr | 4 / 8 | 600 | batch 对梯度噪声的影响 |
| C | 最优 lr | 4 | 2000 | 是否只是"步数不够"（≈4 epoch） |

判据不变（留出集 ≥5%），并且**每组都记录 gnorm 中位数**——
它是判断"学习率是否合适"最直接的指标，比看 loss 曲线快。

这样就不用人工掐点，也不会在长稳期间抢 GPU。

矩阵：`lr ∈ {5e-6, 1e-5, 2e-5} × batch ∈ {4, 8}`，每组 600 步、warmup 40、clip 1.0。
全速（0.3~0.7 s/step）下约 7 分钟一组，6 组 ≈ 45 分钟。

### `tools/sft_sweep.py` 的两个坑（都实测踩过）

| 坑 | 现象 | 正解 |
| --- | --- | --- |
| 子进程没传 `--device` | 无 CUDA 的机器上直接崩（不是扫参结果差） | 显式传给子进程 |
| `--tiny` 分支读的是 `--tiny-lr` 而不是 `--lr` | **四组不同 lr 输出完全相同** —— 扫参扫了个寂寞 | 按模式选对参数名；对比输出才能发现 |

> 第二个坑尤其值得记住：**扫参工具本身必须先被验证**。
> 验证方法很简单 —— 让两个差异明显的值跑一遍，看结果是否真的不同。
> 如果不同 lr 给出同一个数，那不是"数据不敏感"，是"参数没生效"。

## §9 数据体检：28% 的样本正在被从回答中间切断（2026-10-31）

新增 `tools/dataset_report.py`（纯 CPU，带**硬性自检**）。在真实数据上跑出：

| 数据 | 样本 | 总长 p50 | 答案 token 中位数 | 掩码比例 | seq_len=128 截断率 |
| --- | --- | --- | --- | --- | --- |
| persona.jsonl | 159 | 36 | 36 | 0.0% | **0%** |
| sft_big.jsonl | 6000 | 42 | 24 | 30.4% | **27.6%**（1657 条） |

`sft_big` 的长度分布：**p50=42 / p90=197 / p95=231 / p99=278 / max=623**。

| seq_len | 截断率 |
| --- | --- |
| 128（此前所有实验都用这个） | **27.6%** |
| 192 | 10.6% |
| **256** | **2.1%** |
| 320 | 0.3% |

### 为什么这是"学不动"的有力解释

- 27.6% 的样本被**从回答中间切断**：模型在这些样本上学到的是"说到一半就结束"；
- 截断还让**训练目标与真实推理目标不一致**（推理时我们要完整回答）；
- 这也解释了 §8 的曲线形状：前 25 步降、随后回退 —— 短样本学得快（占比高），
  长样本（被切断的）持续贡献错误信号。

### 决策

- 扫参统一改用 **seq_len=256**（截断率 2.1%，算力约 2×）；
- `tools/dataset_report.py` 的 `截断比例 < 20%` 自检会在训练前直接拦下这类问题；
- 进一步压缩截断需要 seq_len 320（0.3%），但算力再 +25%，先用 256 看效果。

### 顺带说明 `persona` 为什么学得好

persona 159 条、总长中位数 36、**截断 0%**、掩码 0%（整段都算 loss）——
信号密度和完整性都是最理想的。所以它 60 步就能 −50%，不能拿来代表"真实语料"。

### 扫参规模按实测重定（2026-10-31 17:00）

先跑了一次 6 步探针（batch=8 / seq_len=256 / Qwen2.5），结果：

| 观测 | 数值 | 结论 |
| --- | --- | --- |
| 步速（长稳抢卡时） | **12.2~14.2 s/step** | 600 步 × 6 组 = **12 小时**，不可行 |
| 峰值显存 | **18.3 GB**（含长稳占用的 3.1 GB，我们约 15.2 GB） | batch=8/seq=256 能跑，但没必要 |
| gnorm 中位数 | 35.5（clip=1.0） | 与 R12 一致：学习率确实偏大 |
| 6 步内探针变化 | 4.063 → 3.750（−7.7%） | 修好补位 + 截断后**信号确实存在** |

因此扫参改成 **steps=300、batch ∈ {2,4}**（约 30~40 分钟跑完 6 组），
Qwen3 段 **steps=200、batch=2**。判据不变。

> 记录这个数字的用处：别人评估"我这台卡能不能训 0.5B"时，
> **batch=8/seq=256 需要约 15 GB 显存**是个可用的参考量级。

## 10. V100 扫参：Qwen2.5-0.5B × alpaca-zh（2026-11-01）

**环境**：V100-32GB（驱动 580.88，sm_70，`module_kind=cubin`），
数据 = hf-mirror 的 `shibing624/alpaca-zh` 前 2000 条（instruction+input → prompt，
output → completion），`seq_len=256`、120 步、`clip=1.0`、留出 8 条。

| lr | batch | 基线 → 终值 | 降幅 | gnorm 中位数 | s/step | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| **5e-6** | **2** | 1.8058 → 1.6525 | **−8.5%** | 35.2 | 0.8 | ✅ **推荐** |
| 5e-6 | 1 | 1.8058 → 1.6626 | −7.9% | 37.1 | 0.5 | ✅ 次佳 |
| 1e-5 | 2 | 1.8058 → 1.7022 | −5.7% | 32.2 | 0.8 | ✅ |
| 1e-5 | 1 | 1.8058 → 1.7453 | −3.3% | 37.2 | 0.5 | 未学到 |
| 2e-5 | 1 | — | — | 36.1 | 0.5 | ❌ 发散 |
| 2e-5 | 2 | — | — | 29.9 | 0.8 | ❌ 发散 |

**结论**：
1. **lr 上限在 1e-5 与 2e-5 之间** —— 2e-5 两档直接发散（没有探针终值）；
2. **同 lr 下 batch=2 优于 batch=1**（−8.5% vs −7.9%，−5.7% vs −3.3%）——
   同样的步数下大 batch 提供更稳的梯度；
3. 速度：0.5–0.8 s/step（batch 1/2，seq 256），比 A10 抢卡环境快 10 倍以上。

### ⚠ gnorm 不能当筛选门槛（这条是踩出来的）

旧规则写的是「gnorm 中位数 ≤ 5×clip」，实测数据里**所有**配置的 gnorm 都在 29~37，
包括最好的一组；而发散的两组 gnorm 反而更低（36.1 / 29.9）。
⇒ 该指标在这个量级上**与好坏无关**，拿它筛会把最优配置一起判死。
现在 `tools/sweep_report.py` 改成：gnorm 只做异常值警告（>200×clip），
真正的失败信号是「没有探针终值 / verdict=FAIL」。

### ⚠ 顺带发现：`.TG` 的线性层可能是 [in, out] 布局（已修）

V100 上那份 `qwen2.5-0.5b-instruct-fp16.TG` 头与张量表全对（L=24 D=896 NH=14 KV=2 V=151936，
fp16 未量化），但 `ffn.w1` 形状是 `[896, 4864]`，而 forward 期望 `[4864, 896]`。
旧代码直接放行 ⇒ 能加载、能训练，**loss 从 10.2 起、gnorm 中位数 4237**；
同一份权重换 **safetensors** 加载：base probe **1.81**、gnorm **28**。

已加 `fix_linear_layout()`：形状正好是转置就自动转回来并记录，两者都不是就报错
（点名张量/实际形状/期望形状/修法）。测试里还抓到一个真 bug：初版只修第一个匹配到的
key，对 24 层模型只修了第 0 层。

### 10.1 加步数 vs 加测量（2026-11-01 下午）

同一配置（lr 5e-6 / batch 2 / seq 256），三组不同的"步数 × 留出集"：

| 步数 | 留出集 | 探针 loss | 降幅 | 备注 |
| --- | --- | --- | --- | --- |
| 120 | 8 条 | 1.8058 → 1.6525 | −8.5% | 扫参里最好的一组 |
| **600** | 8 条 | 1.8058 → **1.7357** | **−3.9%** | `rc=1`（自判 FAIL），gnorm p90 77 / max 399 |
| **300** | **64 条** | **1.9695 → 1.7124** | **−13.1%** | 探针曲线单调下降 |

**结论（负面的先说）**：

1. **"跑得久 ≠ 训得好"**：600 步反而比 120 步差；gnorm p90 77、max 399 说明中后期不稳，
   2000 条样本在 600 步后也可能开始过拟合。
2. **8 条留出集的探针不可靠**：同一配置 8 条给出 −8.5%（120 步）/ −3.9%（600 步），
   64 条给出 −13.1%。**以后统一 holdout ≥ 64**。

**探针曲线（64 条，lr 5e-6 / batch 2）**：

```
step   25  1.8297
step   50  1.7813
step   75  1.7365
step  100  1.7334
step  300  1.7124      (基线 1.9695)
```

边际递减明显：前 100 步拿到大部分收益，后 200 步只再降 1.1 个百分点
⇒ 这个数据规模下 **100~150 步就够**。

### 10.2 `.TG` 读错问题的根因（2026-11-01 定位）

逐张量比统计量（V100，同一模型两路加载）：

| 张量 | `.TG` | safetensors | 判断 |
| --- | --- | --- | --- |
| `token_embedding.weight` | std 0.0152 | — | 正常 |
| `blocks.0.ffn.w1.weight` | std 0.0230 | — | 正常 |
| `blocks.0.attn.q_proj.weight` | std 0.0667 | — | 正常 |
| **`final_norm.weight`** | **mean +7.139**，范围 [-0.011, 16.75] | ≈1 | **异常** |
| **`blocks.0.ln1.weight`** | **mean +0.033**，范围 [-0.311, 0.360] | ≈1 | **异常** |

**结论**：不是布局（转置）问题，也不是量化问题 —— **是少数归一化张量的内容被读错**。
全部 49 个归一化张量里 6 个离谱（12%），但足以毁掉整个模型：

- `final_norm` 均值 7.14 ⇒ logits 被整体放大 ~7 倍；
- `blocks.0.ln1` 均值 0.03 ⇒ 第 0 层输入被压成噪声。

对应 CE：`.TG` **8.300 / 7.671** vs safetensors **3.772 / 3.539**（`tools/tg_audit.py` 实测）。

**已加护栏**：`load_tg` 现在做归一化权重体检，**任何一个**张量离谱就抛
`CheckpointError`（点名张量+均值+`.TG` 版本+三条修法），
并留 `allow_suspicious_norms=True` 逃生门。判据用"单点离谱"而不是"比例"——
实测 12% 的比例在"过半才报"的规则下会被放过，而那 6 个张量已经足够让模型训废。

#### ⚠ 同日更正：这不是"读错"

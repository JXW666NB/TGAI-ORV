# CUDA Graph 可行性实测（V3 训练步）

> 结论先行：**小模型可行，1.5B 不可行**。依据是下面这组实测数字，不是估计。

---

## 1. 图捕获本身在这套环境是通的

`lab/prof/graph_smoke.py`（V100 实跑）：

```
graph_available = True
graph_arm ok    graph_begin = True    graph_end = True   count = 1

重放后 vs eager : max_abs = 0.000e+00        ← 逐位一致
CPU 提交耗时    : eager 0.063 ms → 重放 0.004 ms   (14.4x)
```

⇒ CUDA Graph 的**机制**没问题：捕获、实例化、重放、数值都对，CPU 派发成本降 14.4 倍。

（"捕获首跑 vs eager = 6.176e-02" 是正常的：捕获期内核只被记录、不执行。）

---

## 2. 卡在哪：arena 是 bump-only

`cuda.py:_arena_alloc`：

```python
n = (int(nbytes) + 15) & ~15
if self._arena_off + n > self._arena_size:
    raise CudaError("捕获 arena 用尽：已用 … / … GiB，本次要 %d 字节。修法：调大 reserve_capture_arena")
ptr = self._arena_base + self._arena_off
self._arena_off += n          # ← 只前进，从不回收
```

捕获期内 `_pool_frozen()` 为真，**每一次 `empty()` 都走 arena**，
释放的块不会被复用 ⇒ **arena 必须装下"一整步所有分配字节之和"**。

`lab/prof/arena_need_v3.py` 实测（4 层 / seq512 / d_ff 2816，真训练 4 步取平均）：

| 指标 | 值 |
|---|---:|
| 每步分配请求次数 | **2039** |
| 每步分配字节总和 | **4.71 GiB** ← arena 下限 |
| 每步峰值活占用 | 6.68 GiB |
| 设备总量 | 31.86 GiB |

### 按层数外推

| 配置 | arena 需求 | 参数+优化器状态 | 合计 | 32 GB 能否装下 |
|---|---:|---:|---:|:---:|
| 4 层 / seq512 | ≈4.7 GiB | ≈1.6 GiB | **≈6.3 GiB** | ✅ 可行 |
| 20 层 / seq512 | ≈23.6 GiB | ≈8 GiB | ≈31.6 GiB | ⚠️ 极限 |
| **24 层 / seq512（1.5B）** | **≈28 GiB** | **18 GiB** | **≈46 GiB** | ❌ **不可行** |
| 24 层 / seq1024 | ≈56 GiB | 18 GiB | ≈74 GiB | ❌ 差得更远 |

⇒ **1.5B 上做整步图捕获没有出路**，差 14 GiB。

---

## 3. 如果要救，只有两条路（都需要改引擎）

### 路 A：让 arena 支持复用（难点最大，收益最大）

图在重放时**不需要 Python 参与**，而训练步是**确定性**的：
第 N 次重放与第 1 次捕获的分配/释放顺序完全相同。
所以可以给 arena 加 free-list —— 地址序列自然保持一致，无需额外记录。

改完之后 arena 需求从"**总和** 4.71 GiB"降到"**峰值** 6.68 GiB"（4 层），
24 层从 28 GiB 降到约 27 GiB —— **仍然装不下**（27 + 18 = 45 GiB）。

⇒ 路 A 对 1.5B **也救不了**。只对小模型有意义。

### 路 B：分段捕获（每层/每 K 层一张图）

`graph_launch_slot(i)` 正是为此准备的（多图槽位）。
但 V3 的 MoE 路由是**数据相关**的：每步的专家索引与每专家 token 数都变，
`moe_permute`/`moe_scatter` 的形状随之变 ⇒ 捕获的图在下一步形状不对，直接失效。

⇒ 除非把 MoE 改成**固定形状**（padding 到容量上限），否则分段捕获也不成立。
这是一个独立的、更大的改造。

---

## 4. 结论与建议

| 方案 | 4 层 | 20 层 | 24 层（1.5B）|
|---|:---:|:---:|:---:|
| 整步图捕获 | ✅ | ⚠️ | ❌ |
| arena 加复用后 | ✅ | ⚠️ | ❌ |
| 分段图捕获 | 需固定 MoE 形状 | 同 | 同 |

**对 1.5B，CUDA Graph 这条路的答案是"不行"**，原因是显存，不是实现难度。
CPU 那 260 ms 的开销只能靠**减少 kernel 数 / 减少分配次数**来降，
或者换到显存更大的卡（A100 80 GB 上 46 GiB 完全可行，图捕获立刻可用）。

**因此 1.5B 上剩下的唯一高价值方向是你提的 bf16 激活存储**：
它直接砍掉峰值显存（seq512 约 9.1 GiB 激活），
既能让 seq1024 更宽裕，也能让将来的图捕获变得可能（arena 需求同步下降）。

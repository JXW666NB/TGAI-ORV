# ORV vs PyTorch 干净头对头（2026-11-12）

> 脚本：`tools/h2h_clean.py`（自包含，任何人可复现）
> 硬件：Tesla V100-SXM2-32GB，CUDA 12
> 目的：回答「ORV 现在到底比 PyTorch 快多少、省不省显存」

## 方法（为什么这组数字可信）

| 项 | 做法 |
| --- | --- |
| 初始权重 | **同一份**：numpy 生成一次，再分别灌进两侧 —— 不是两个随机初始化在比 |
| 算式 | 同一套：embed → L×(attn + mlp/moe) → head，同 d_model/头数/d_ff |
| 计时 | CUDA event；预热 3 次、测 5 次取均值 |
| 进程 | 两侧**各自独立进程**，避免显存分配器互相干扰 |
| 显存 | ORV 取 `pool_stats()["peak_live_bytes"]`（只算活张量，口径最接近 torch 的 `max_memory_allocated`）；torch 取 `max_memory_allocated` |
| 规模 | vocab=8192, d_model=512, 6 层, 8 头, d_ff=2048, MoE 8 专家 top-2；B=1, S=512 |

**已验证的等价性**：两侧 loss 一致到 1e-06 相对（例：9.011551856994629 vs 9.011554718017578），
说明对比的是同一道算式。

## 三条结论

### 1. 速度：ORV 稳定更快（1.40× ~ 2.68×）

在这组自包含、同权重、同算式的对比里，ORV 每一组都快，且开检查点后优势更大
（因为 ORV 的重算更便宜）。这与 README 之前引用的 1.11~1.16× 不同，原因是：

- 那组是 8 层小模型 + 各自独立进程，且含更多 IO；
- 这组把 embed/head 也算进去，且用同一份权重。

**两组都对，但口径不同**。引用时请说明是哪一组。

### 2. 显存：ORV 稳定更费（1.20× ~ 1.94×）

这是必须承认的事实。**ORV 不省显存，反而更费。**

之前 README 的「省显存」定位只在 **3B MoE / 32GB V100** 这个组合上有证据
（那里 PyTorch 连优化器状态都放不下，而 ORV 逐层更新放得下）。
在 400M 级稠密模型上，ORV 用 1.8~1.9 倍显存 —— 与 P100 用户实测一致
（`docs/REVIEW_P100_2026-11-12.md`）。

**所以正确的说法是**：ORV 用「更多显存」换「能训完 + 更快」；
只有在 PyTorch 因为优化器状态放不下而彻底跑不了的规模上，
ORV 的逐层更新才会反过来变成"能用 vs 不能用"的差别。

### 3. 检查点修复生效，但没消灭差距

2026-11-12 修了 `checkpoint()` 的两个问题（见 CHANGELOG 0.9.51）：

| | 修前 | 修后 |
| --- | --- | --- |
| dense 显存（检查点） | 0.857 GiB | **0.602 GiB（−30%）** |
| 与 torch 的比值 | 1.89× | 1.83× |

**相对比值只从 1.89× 降到 1.83×** —— 因为 PyTorch 也降了 28%（0.454 → 0.325）。
真正的原因是 ORV 的**基础开销**更大，不只是检查点。剩余约 0.28 GiB 差距待查。

## 复现

```bash
python tools/h2h_clean.py --compare            # 不开检查点
python tools/h2h_clean.py --compare --ckpt     # 开检查点
```

结果会写入 `tools/h2h_clean.json`。

## 已知的口径限制

- torch 侧的 MoE 用「按专家 mask 循环」写法 —— 这是普通用户写 MoE 的自然方式，
  **不是**专家级融合实现，所以 MoE 那组不代表"最优化过的 PyTorch"。
- 只跑了一个规模（6 层 / d=512）。更大规模的结论需要另一组实测。
- fp16 GEMM 走 `TG_FP16=1`；本组 fp32 对比中它未开启，AMP 组由 torch autocast 与
  ORV 的 `T.amp()` 分别控制。

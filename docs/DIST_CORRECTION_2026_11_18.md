# 分布式实测纠正与整改（2026-11-18）

## 一、必须先认的错误

我在 1.0.0 的 README/CHANGELOG 里写了「双卡 DP ≈ 2,039 tok/s（1.99×）」「对 PyTorch DDP 快 3.4×」。
**这些数据不成立。**

原因：租的机器上装的是 PyPI 的 **0.9.97**，那个版本的 `v3_pretrain` **还没有 DP 接线**
（DP 是 1.0.0 才有）。所以那两次"双卡 DP"实际是**两个独立的单卡训练**，
不是数据并行 —— 数字只是"两张卡各跑各的"，不是"DP 的扩展效率"。

**判据**：旧日志里 `[dp]` 出现次数 = 0（DP 从未启用）；接上真 DP 后立刻出现 4 次。

## 二、真实 DP 的数字（12 层 / seq512 / 2×3090）

| 项 | 数值 |
|---|---|
| 单卡一步（无 DP）| 0.252 s |
| **真 DP 一步** | **8.4 s**（整改后 **5.5 s**）|
| 其中 all_reduce | **8.1–9.1 s**（整改后 **5.2 s**）|
| 梯度量 | 3.16 GiB（321 个张量）|
| 归约有效带宽 | 0.35 GiB/s（整改后 **0.6 GiB/s**）|

⇒ **当前 DP 比单卡慢 22×，不可用。** 群里"多卡拉了"的判断是对的。

对照 PyTorch DDP 同配置：0.577 s → 0.905 s（+0.33 s），按 3.16 GiB×2 折算约 **19 GiB/s**。

## 三、根因（逐条实测支撑）

1. **321 次独立、同步的 GPU↔主机拷贝**：3.16 GiB / 321 ≈ 10 MB/次，
   每次约 15 ms ⇒ 光调用开销就 **4.8 s**。这是主因。
2. **主机侧冗余拷贝**：原实现每个参数 `ascontiguousarray().tobytes()` + 切片赋值 +
   求和后 `astype(copy=True)`，3.16 GiB 的梯度在主机内存来回拷 **约 12 GiB**。
   → 已整改（改用共享内存的 numpy 视图 + `np.copyto` + `np.sum(out=)`），8.5 s → 5.2 s。
3. **没有 P2P**：实测 `cuDeviceGetP2PAttribute(可访问) = 0`、`原生原子 = 0`
   —— 消费级 3090 走 PCIe 不支持点对点，只能主机中转。
4. **无重叠**：归约完全串行在反向之后，不能与下一步前向重叠。

## 四、整改计划（按收益排序）

| 步 | 做什么 | 预期 |
|---|---|---|
| **1** | **打包成一次传输**：把 321 个梯度先 D2D 拷进一个大缓冲（~20 ms），一次 d2h、一次 h2d，再 D2D 拆回 | 5.2 s → **~1.5 s**（PCIe 绑定）|
| 2 | 归约与计算**重叠**（反向结束前开始传已完成的分桶）| 再省 ~50% |
| 3 | 传输用 **bf16**（梯度减半）| 再省一半（数学上需评估）|
| 4 | 若换服务器卡（支持 P2P/NVLink）| 数量级提升，但换硬件才行 |

第 1 步需要给运行时加"按偏移拷贝/视图"的原语（`sub_view` 一类）。

## 五、对发版的处置

* 1.0.0 已发布（PyPI + GitHub tag）。**README/CHANGELOG 里那两条 DP 性能数字必须在
  1.0.1 里更正**，不能留着误导。
* 在整改完成前，对外口径应改为："DP 已接通并验证正确性（各 rank gnorm 一致），
  但**性能尚未优化**，1.5B 规模下目前比单卡慢，不推荐使用。"

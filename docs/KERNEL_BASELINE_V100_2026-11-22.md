# 逐内核基线：Tesla V100（2026-11-22 实测）

> 目的：把"内核质量"变成可比较的数字。**所有数字都是本机实测**，
> 设备 Tesla V100-PCIE-32GB / cc 7.0 / 驱动 580.88 / ORV 1.0.20 / torch 2.6.0+cu124。
> 峰值口径：fp32 **14.0 TFLOPS**、fp16 张量核 **112 TFLOPS**、带宽 **900 GB/s**。

## 1. 核心发现（三条，按重要性）

### ① 我们的**注意力根本没有 Tensor Core 路径**

| 注意力（S=2048, B*H=36, Dh=64, causal）| ORV | torch |
| --- | ---: | ---: |
| fp32 lowmem | **11.46 TFLOPS = 82% fp32 峰值** | 14.96 |
| fp16 张量（裸） | 11.45 = **10% TC 峰值** | — |
| fp16 + `T.amp()` | 11.39 = **10%** | 45.64 = **41%** |

**fp16 的绝对速度几乎等于 fp32（11.4 vs 11.5）⇒ 我们的注意力内核「存成 fp16、算还是 fp32」，
从未使用 `mma.sync`。** torch 的 mem-efficient 在 fp16 下是本机的 4 倍。

### ② GEMM 的 TC 路径存在，但**只有 `T.amp()` 能打开**

| GEMM 4096×1152×1152 | TFLOPS | 峰值占比 |
| --- | ---: | ---: |
| ORV fp32 | 11.35 | 81% fp32 |
| ORV fp16 张量（裸） | 11.30 | **10% TC** |
| ORV fp16 张量 + `rt.fp16_gemm = True` | 11.39 | **10% TC**（**这个开关对 GEMM 无效**）|
| ORV fp32 张量 + `with T.amp()` | **45.05** | **40% TC** ✅ |
| torch fp16 | 68.68 | 61% TC |

⇒ 我们的 TC GEMM 能到 40%（torch/cuBLAS 61%），**有 1.5× 的提升空间**；
但 `TG_FP16=1` / `fp16_gemm=True` 这两个名字听起来像"开 fp16"，**实际不开 TC** —— 属于命名误导。

### ③ 带宽类内核落后 1.5~2.3×，这是"手写 vs 代码生成"的直接后果

| 内核（fp16 张量）| ORV | torch | 差距 |
| --- | ---: | ---: | ---: |
| silu | 270 GB/s | **625 GB/s** | 2.3× |
| softmax | 265 GB/s | 312 GB/s | 1.2× |
| rmsnorm（fp32 测）| 736 GB/s（82%）| 329 GB/s | ORV 更快 |

（fp16 下我按 fp32 字节数算带宽，两边同样偏大 2×，**不影响相对比较**。）

## 2. 完整内核表（V100，2026-11-22）

| 内核 | dtype | ORV | % 峰值 | torch | % 峰值 |
| --- | --- | ---: | ---: | ---: | ---: |
| attn_fwd | fp32 | 11.44 TF | 82% | 3.74（math）| 27% |
| attn_fwd | fp32 | — | — | 16.02（mem-eff）| 114%* |
| attn_bwd | fp32 | 3.88 TF | 28% | 4.43（math）| 32% |
| attn_bwd | fp32 | — | — | 9.19（mem-eff）| 66%* |
| attn_fwd | fp16 | 12.81 TF | 11% | 43.97（mem-eff）| 39% |
| attn_bwd | fp16 | 3.93 TF | 4% | 26.08（mem-eff）| 23% |
| gemm | fp32 | 12.65 TF | 90% | 12.80 TF | 91% |
| gemm | fp16（AMP）| 45.05 TF | 40% | 68.68 TF | 61% |
| softmax | fp32 | 543 GB/s | 60% | 712 GB/s | 79% |
| rmsnorm | fp32 | 737 GB/s | 82% | 329 GB/s | 37% |
| silu | fp32 | 544 GB/s | 60% | 976 GB/s | 109%* |
| moe_gather | fp32 | 未支持 `x[idx]` | — | 478 GB/s | 53% |

`*` 超过 100% 的两项：**causal 只算下三角（约一半）**，而我的 FLOPs/字节公式按全量算，
所以对"会跳过掩码块"的实现（torch mem-eff）会高估约 2×。**这是测量口径问题，不是 torch 作弊。**

## 3. 端到端公平对照（V100，同协议）

| 配置 | torch | ORV | R=ORV/torch |
| --- | ---: | ---: | ---: |
| bs2 fp32 lowmem | 0.87 s | 1.13 s | 1.30 |
| bs2 fp32 物化 | 1.27 s | 1.27 s | **1.00** |
| bs2 fp16 lowmem | 0.27 s | 0.71 s | **2.64** |
| bs2 fp16 物化 | 0.91 s | 0.87 s | **0.95** |
| bs4 fp32 lowmem | 1.69 s | 2.18 s | 1.29 |
| bs4 fp32 物化 | 2.57 s | 2.57 s | **1.00** |
| bs4 fp16 lowmem | 0.47 s | 1.28 s | **2.72** |
| bs4 fp16 物化 | 1.87 s | 1.74 s | **0.93** |

**读数：**

* **物化路径两边打平（1.00/0.95/0.93）** —— GEMM/elementwise 不比 PyT 差；
* **低显存 fp16 路径我们输 2.6~2.7×** —— 正是 §1① 那个"注意力没有 TC"造成的；
* 显存数字**不可用**：脚本把 torch 与 ORV 跑在同一进程，torch 的 caching allocator 残留
  污染了后面 ORV 的 `nvidia-smi`（多行读数完全相同即为证据）。**下一步必须先做进程隔离。**

## 4. 由此得到的改进优先级（按端到端收益排序）

| # | 目标 | 依据 | 预期收益 | 难度 |
| --- | --- | --- | --- | --- |
| **P0** | 注意力内核上 **`mma.sync`（fp16/bf16 TC）** | §1①：ORV 11.4 TF vs torch 45.6 TF，差 **4×** | 注意力占步时约 20% ⇒ **端到端最高 ~25%** | 高（要写 MMA 版 fwd/bwd） |
| **P1** | AMP GEMM 从 40% → 55%+（减少 cast、用 `CUBLAS_COMPUTE_16F`、缓存影子权重）| §1②：45 vs 68.68 TF | GEMM 占大头 ⇒ **10~15%** | 中 |
| **P2** | 反向注意力（fp32）28% → 40%+ | attn_bwd 比 fwd 慢 7.3×，torch 只慢 2.1× | 5~8% | 中高 |
| **P3** | silu/softmax 向量化模板（`float4` + unroll）| §1③：silu 270 vs 625 GB/s | 3~5% | 低 |
| **P4** | 让 `TG_FP16` 名副其实或在文档里明确"它不启用 TC，只有 AMP 会" | §1② | 避免用户误判（已是事实）| 低 |

## 5. 明确的测量缺口（下一轮补）

1. **`bench_fair.py` 需要进程隔离**（每配置独立子进程），否则显存数字不可用。
2. `bench_kernels.py` 需要支持 **dtype 选择 + AMP 路径**（本次为此临时写了两个探针脚本：
   `lab/rent/probe_attn_tc.py`、`probe_tc_coverage.py`、`probe_tc_on.py`）。
3. **causal 口径**：应改为 `S*(S+1)/2` 计算有效 FLOPs，否则会拿"跳过掩码"的实现去比"不跳"的实现。
4. `moe_gather` 在 ORV 里的正确 API 待确认（`x[idx]` 不支持 2D 高级索引）。

## 0. 摘要（先看这一节）

### 0.1 最重要的一句话

> **优化器的优劣不能脱离任务类型讨论。**
> 本报告在两个任务上、用同一模型/同一初始化/同一步数，得到了**方向相反**的排序：
>
> - **玩具回归**（有唯一 float64 最优点）：`AdamW ≈ Adafactor`（超额 1e-9 量级）**优于** `Polaris`（8.9e-7）**优于** `Muon/LAMB`（3~4e-6）**优于** `Lion`（1.4e-5）
> - **迷你 Transformer 固定批过拟合**（记忆任务）：`Muon`（1.9e-8）`≈ Polaris`（5.5e-8）**远优于** `AdamW`（2.1e-4）/`Adafactor`（4.3e-4）/`Lion`（6.4e-4），**差 3~4 个数量级**
>
> 任何"Polaris 比 AdamW 好/差 N 倍"的单句结论都是错的。作者与用户都应当按任务类型选型。

### 0.2 三条实测结论

1. **收敛性**：Polaris 在两个任务上都**不是最差**，也都**不是最好**。玩具回归排第 3（6 个优化器里），过拟合任务**与 Muon 同级**（CPU 150 步第 1、CUDA 200 步第 2）。
2. **速度**：Polaris 的 `opt.step` 比 ORV 融合版 AdamW 慢 **167×（9.4M 参数）**，但**ORV 自带的 Adafactor（160.8 ms）与 Lion（149.3 ms）比它更慢**，因为它们是同一类"逐参数发 kernel"的非融合实现。真正快的是 AdamW / fp16mom / int8gpu（单 kernel 融合，0.26~0.34 ms）。
3. **CPU/CUDA 两条路径的不等价，实际影响比作者文档担心的要小**：玩具回归上逐 lr 对齐，末段超额差 **0.6%~13%**，`steps_to_excess_1e-3` **逐配置完全相同**（261/261、71/71、504/504、288/284）。差异只在"临界 lr 附近"被混沌放大。**"CUDA 用整体 RMS 近似逐行 RMS"这件事，在本报告的稳定 lr 区间内没有可测的负面影响。**

### 0.3 一条必须提醒用户的警告

**Polaris 的稳定 lr 窗口很窄，且收敛到最优点后不会停住。**
固定批过拟合任务上，`lr=3e-3` 先把 loss 压到 `<1e-6`（第 120 步起为 0），**保持 80 步后（第 200 步）突然跳到 0.154，进入 0.001~0.2 的极限环**，再也没回到 0；`lr=1e-2` 在第 45 步就从 6.5e-5 崩到 0.11 再没回来。CPU 与 CUDA **都复现**（见 §6 issue #2）。
按 AdamW 的习惯（这个模型上 AdamW 最优 lr = 1e-2）直接套给 Polaris 会踩到；Polaris 在这个任务上必须用 1e-3。

### 1.2 可用优化器（`T.optim` 实测）

`AdamW / Adafactor / LAMB / Lion / Muon / SGD / Accumulator`（+ 插件注册的 `Polaris`）。
**`LAMB` 只支持 CPU**（CUDA 上明确报错，属 ORV 限制而非 Polaris 问题），因此 GPU 矩阵里它被剔除并标注。

### 1.3 两个任务

**任务 1：玩具回归**（有唯一 float64 最优解，便于判断"是否真的收敛到最优"）

- `W(64×32)` 拟合 `T = W*·X + 0.1·noise`，`X(32×256)`，loss = MSE
- float64 闭式最小二乘解 `W*`，`loss* = 0.0087604499`
- 指标：`excess = loss − loss*`（超额损失）、`‖W−W*‖/‖W*‖`、`steps_to_excess_{1e-3,1e-5}`
- 步数：CPU **1200**（正式矩阵）/ 600（CPU-CUDA 对齐）；GPU **600**

**任务 2：迷你 V3 固定批过拟合**（真 Transformer + 真 CE，优化器差异最敏感）

- `vocab=4096, d=128, 2 层, 4 头, d_ff=512`，**1,049,216 参数**，`seq=64`
- 数据：`D:\orv_bench\data2048_v4096`（8 shard × 16×2048 int32；实测 unigram 熵 11.91 bit、bigram 条件熵 **3.09 bit** ⇒ 有真实结构，不是随机 id）
- 每步用**同一组 8 个 batch**（B=8，512 token/步）反复训练 ⇒ 标准"过拟合一个 batch"优化器基准
- 步数：CPU **150**、CUDA **200**（CPU/CUDA 对比时把 CUDA 曲线**截断到 150 步**，保证同步数）

**任务 3（辅助）流式**：每步换新 batch，100 步。结论：**无区分度**，见 §2.4。

### 1.4 公平性口径（全部矩阵统一）

- **不用同一个 lr 硬比**：每个优化器各自扫描 4~6 个 lr（覆盖 2~3 个数量级），报"各自最优 lr"
- **无 gradient clip、无 lr scheduler、无 weight decay**（`wd=0`）—— 只比更新规则本身
- 同一 `seed=0`、同一初始化、同一数据顺序（任务 2 的 batch 列表固定）
- 报两个口径：**末 10 步均值** 与 **全程最低值**
- 发散/NaN **如实记录并贴序列**（§2.3、§6）
- 计时：**CUDA event**（`rt.event_record` / `event_elapsed_ms`），预热 3 步 + 3 次重复取中位数，每次量 10~20 步——**不做"调用前后各 sync"**
- 末段 loss 读数是数值口径：**|excess| < 1e-8 视为 fp32 数值零**（负值是舍入伪影）

### 1.5 一个必要的测试替身：CPU cross_entropy

ORV 0.9.97 的 **CPU** `cross_entropy` 是逐元素 Python 循环（对齐 CUDA kernel 的 bit-exact 实现）：
**64×4096 一次 = 10.4 秒**（实测），1.05M 参数模型一步要 10 秒以上 —— CPU 收敛测试无法进行。

本报告在**测试脚本内**用数学等价的向量化实现替代（**未改 `python/tgai_go/`**，`git status -- python` 为空）：

| 校验项 | 结果 |
|---|---|
| loss 差（内置 vs 替身，64×4096） | **8.58e-6** |
| 梯度最大绝对差 | **1.33e-8** |
| 对 float64 参考的梯度相对误差 | 内置 1.30e-6 / 替身 **1.75e-8** |
| 单次耗时 | 内置 **10.43 s** → 替身 **0.0012 s（约 8700×）** |

> 这条本身是 ORV 的产品缺陷（CPU 训练实际不可用），已单列进 §6 issue #0。

全部在 `ln(4096)=8.318` 附近 ±0.3 震荡，**没有任何优化器在这 100 步内学到东西**。
原因（实测推断）：该模型 unigram 熵 11.91 bit（≈ ln(V) 的 0.99），即"只学词频"几乎没有收益；
要吃到 bigram 的 3.09 bit 需要远多于 100×64=6400 token 的数据。
⇒ 本任务**不能用来区分优化器**，报告不据此下任何结论。

### 3.3 CPU/CUDA 差异结论（区分实测/推测）

- **实测**：两条路径在稳定 lr 下**等价**（到达阈值步数逐位相同；末段差 ≤13%~56%）。
- **实测**：差异只在**接近失稳边界**时被放大到 O(10×)。
- **推测（未单独验证机制）**：这是混沌放大 —— 优化轨迹在临界点附近对初始 1e-7 级差异指数敏感，
  而不是"整体 RMS 近似"引入了系统性偏差。判据是：**阈值步数（整数指标）在两条路径上完全一致**；
  若算法真有系统性差异，阈值步数不可能同步。

### 5.3 怎么读这两张表（必须一起读）

1. **规模效应真实存在但方向相反于直觉**：1.05M → 9.4M（9×），Polaris/AdamW 的 `opt.step` 倍数
   只从 **283× 降到 167×** —— **没有随规模收敛**，因为 Newton-Schulz 是 **FLOP 密集型**（每步 5 次迭代 × 3 个 GEMM）。
   但"摊薄"也是真的：opt.step 占整步从 65% 变化到 75%（**没有变小**），整步倍数 2.7× → 3.8×。
   ⇒ **"Polaris 慢 300 倍"只在小模型且只看 opt.step 时成立；看整步是 2.7~3.8 倍；而且它不是最慢的（Lion 149 ms、Adafactor 161 ms 比它慢 3 倍）。**
2. **真正的分水岭是"融合 vs 非融合"**：AdamW / fp16mom / int8gpu 把所有参数收进**一个 kernel**（0.26~0.34 ms），
   其余四个（Muon/Lion/Adafactor/Polaris）逐参数发 kernel + 中间张量，都是 10~160 ms 量级。
   **这是 ORV 的工程问题，不是 Polaris 独有。**
3. **各优化器的显存**：**本报告不做显存结论**。原因有二：① 模型太小（1.05M 参数，进程峰值 0.1055 GiB），
   优化器状态差异被模型本身淹没；② 实测发现 `rt.pool_stats()["peak_live_bytes"]` 是**进程级累积峰值**，
   不随优化器重建而复位（本报告里它在 9.4M 模型下对所有优化器都读到同一个 0.2671 GiB），
   **不能用来做 per-optimizer 显存对比**——这条也建议核心侧补一个 "reset_peak()" 或 per-allocator 统计。
   按代码静态推断（未实测）：Polaris 2D 参数 1 份动量 + 1 份 `u` 缓冲 = 2 份 fp32；AdamW 是 2 份（m+v）；
   Muon 默认 fp16 动量 1 份。
4. **计时口径说明**：ORV 的"整步 ms"包含本报告 harness 中每步一次 `logits.to_numpy()`（取行最大值做稳定 softmax），
   约 0.5~2 ms 的额外 D2H 同步；PyTorch 侧用 `F.cross_entropy` 全程在卡上，**其整步数字被低估**。
   因此**跨框架只比 `opt.step` 一列**，整步不跨框架比较。

## 6. 问题清单（给作者）

### issue #0（属 ORV 核心，非 Polaris）CPU `cross_entropy` 逐元素 Python 实现

**实测**：`T.functional.cross_entropy(logits[64,4096])` = **10.43 s**；向量化等价实现 **0.0012 s**（8700×）。
**影响**：CPU 后端"可用"的契约在 CE 上不成立（1.05M 参数模型一步 >10 s）。
**证据**：`p04_ce_check.json`；cProfile 热点 100% 在 `_ce32 → _exp32 → _exp32_taylor`。
**建议**：核心侧加向量化快路径（与本报告替身同构），或至少加开关。

### issue #1 CPU `_polar_express_np` / `_sumsq32` 用 Python 逐元素求和 —— **Polaris 侧可自行修**

**实测**：1.05M 参数模型，Polaris `opt.step` = **620~813 ms**，其中 ~0.6 s 是 1,048,576 次 Python 标量加法；
同模型 AdamW `opt.step` = **8 ms**。整步 718 ms vs 97 ms。
**证据**：`p06_pilot2.json`（标定 `py_sum_200k_s=0.1217`）、`p12b_cpu_overfit.json`（ms/步列）。
**建议**：`nrm = np.sqrt(np.float32(x.ravel().astype(np.float32) @ x.ravel()))` 可保持 fp32 语义同时快 ~100×；
若一定要 bit-exact 对齐 GPU `sumsq`，用 `np.add.reduce` + `dtype=np.float32` 即可（仍比 Python 循环快两个量级）。

### issue #2 稳定窗口窄 + 收敛到最优后不停住（CPU/CUDA 都复现）

**实测**（固定批过拟合，1.05M 参数模型）：

| lr | 行为 |
|---|---|
| 3e-4 | 单调下降，200 步到 1.3e-5（没收敛完） |
| **1e-3** | **稳定**，CPU 150 步 1.15e-6 / CUDA 200 步 5.5e-8 |
| **3e-3** | **先收敛到 <1e-6（CPU 第 120 步 / CUDA 第 127 步起为 0），80 步后（CPU 第 200 步 / CUDA 第 189 步）跳到 0.15，之后 0.001~0.36 极限环** |
| **1e-2** | **第 45 步从 6.5e-5 崩到 0.11~0.8，250 步内再没恢复** |

**证据**：§2.3 完整序列；`g10b_model.json`（CUDA）、`p13_cpu_polaris_long.json`（CPU 250 步）。
**推测原因**（未逐行验证）：`_polar_express_np` 用 `‖u‖ + eps` 归一 ⇒ 当梯度趋零（loss=0）时
`u` 变得极小，但归一化后的方向**仍是 O(1) 单位矩阵**，于是更新幅度恒为 ~lr，参数持续游走直至离开极小值邻域。
Muon 在同样机制下也会失稳（Muon lr=3e-2 在 CUDA 上末10=0.70、min=0），但 Polaris 的边界更低。
**建议**：①文档里明确写"本优化器需要 lr 退火/衰减，或把 lr 设到比 AdamW 小 10×"；
②加一个"梯度范数低于阈值时跳过更新"或"update 幅度按 ‖u‖/‖u‖_ema 缩放"的开关。

### issue #3 `ns_saved_pct`（自适应正交频率）实测收益远低于文档

**实测**（1.05M 参数模型，200 步，CUDA）：`ns_saved_pct` = **3.5% / 4.5% / 5.0%**；
CPU 150 步：**3.3% / 4.0% / 4.7%**。
`orth_freq` 全程为 **1**（从未拉长间隔），`dir_cos` 实测上限 0.9587（阈值 `_DIR_STABLE = 0.995`）。
**证据**：`g10b_model.json` / `p12b_cpu_overfit.json` 的 `opt_status`；`p06_pilot2.json` 里 `dir_cos=0.98233`。
**结论**：文档宣称的"省算力"（3090 上 1.68×）在本模型上**不成立**（省 3~5%）。
**建议**：把 `_DIR_STABLE` 降到实测可达区间（如 0.95），或把 `_MAX_FREQ` 与 `cos` 的关系改成连续映射；
并在文档里给出"什么条件下才真的省"。

### issue #4 `T.plugin.resolve_optimizer()` 未注册时返回 `None` ⇒ 报错信息误导

**实测**：脚本里忘写 `import polaris` 时，`T.optim.Polaris(...)` 得到
**`TypeError: 'NoneType' object is not callable`**（无任何"插件未加载"提示）。
**证据**：`g00_smoke.json` 首次运行；补 `import polaris` 后同一代码正常。
**建议**（属 ORV）：`T.optim.__getattr__` 在插件未注册时应抛
`RuntimeError("Polaris 未注册：请 import polaris 或 T.plugin.autoload()")`。

### issue #5（观察，非缺陷）Polaris 与 Muon 的关系与可替代性

在固定批过拟合上 Polaris（5.5e-8）与 Muon（1.9e-8）同级；在玩具回归上 Polaris（8.9e-7）略优于 Muon（3.4e-6）。
即 **Polaris 没有在某类任务上明显超越其"母算法" Muon**，它的差异化在自适应（但 issue #3 显示自适应几乎不生效）
与 CUDA 上的 2 份状态（Muon fp16 是 1 份）。
**建议**：README 里应直接对比 Muon，而不是只对比 AdamW。

| | **Polaris** | **1e-3** | **5.5e-8** | 3.9e-8 | 57 | 与 Muon 同级，差 AdamW 4 个数量级 |
| | Muon | 1e-2 | **1.9e-8** | 1.1e-8 | 40 | 本任务最强 |
| | Lion | 1e-3 | 6.4e-4 | 4.5e-4 | 149 | |

\* 玩具回归的步时是 CPU 0.14 ms（矩阵太小，GPU 不具代表性）；速度列统一用 9.4M 模型的 CUDA `opt.step`。

**一句话使用建议（可直接放 README）**：

> Polaris 适合**需要把训练损失压到极低（记忆/拟合类任务、小数据微调）**的场景，
> 在 1e-8 量级的末段损失上与 Muon 同级、比 AdamW 好 3~4 个数量级；
> 但在**凸优化/要求快速收敛到最优**的场景不如 AdamW/Adafactor。
> 使用时注意三点：**① lr 要比 AdamW 小约 10×（本例 1e-3 vs 1e-2）；② 稳定窗口窄，必须配 lr 衰减；
> ③ 在 ORV 0.9.97 上它与 Muon/Lion/Adafactor 同属"非融合"优化器，`opt.step` 是融合版 AdamW 的 167×，
> 小模型上可能占整步 65~75%。**

### 8.3 未验证项 / 局限（如实列出）

1. **单 seed（seed=0）**。两个任务都是确定性任务（固定初始化 + 固定数据顺序），但**未做多 seed 方差估计**，
   因此"排序"可信、"具体数值的置信区间"未知。
2. **显存只测到进程级峰值（0.1055 GiB）**，模型太小（1.05M），优化器状态占用差异被淹没；
   **没有对 9.4M / 更大模型做 per-optimizer 显存对比**。按代码静态推断（非实测）：Polaris 2D 参数 2 份 fp32
   （动量 + `u` 缓冲）；AdamW 2 份；Muon(fp16) 1 份。
3. **没有在真实 V3（849M / MoE）上跑收敛**。速度只做到 9.4M；更大规模上 Newton-Schulz 的 FLOP 占比会继续变化，
   `opt.step` 倍数可能进一步下降（但不会消失）。
4. **流式任务无区分度**（§2.4），**未做长步数（>1000 步）的真实语料收敛对比**，这是本报告的最大空白：
   "Polaris 在真实预训练上是否更好"未验证。
5. **`ns_dtype` / `tf32` / `auto=False` / `momentum` 等旋钮未做消融**（只用了默认值）。
6. **CPU/CUDA 的"混沌放大"解释是推测**，未做"人为注入 1e-7 扰动看阈值步数是否漂移"的对照实验。
7. **AMP 只在 V100（fp16）上验证**，bf16（A100/H100）未测。
8. **`git status -- python` 在本报告工作期间出现过一次非本测试的改动（重要，需说明）**：
   本次基准测试**只写 `lab/rent/` 下的文件，从未修改 `python/tgai_go/`**（开始时 2026-11-20 00:24 实测为空）。
   但在 01:25:42，核心修复方在 `python/tgai_go/train/__init__.py` 里把 `_sumsq32` 改成
   "默认走 `np.dot`、`TG_SUMSQ_EXACT=1` 时走逐位精确版"——**该改动不是本报告做的**，
   其 docstring 引用的正是本报告 issue #1 的实测数字（"1.05M 参数约 1 秒/步 … Muon 1028 ms/步"）。
   本报告所有数字均来自远程 `D:\orv_pip_0962` 里**未修改的 ORV 0.9.97**，**不受该改动影响**。

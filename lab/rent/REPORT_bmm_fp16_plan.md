## 0. 结论先行（三段）

1. **实测能拿到的最大一块不在「新的 3-D fp16 kernel」，而在「batch=1 的 3-D GEMM 绕开了已有 fp16 路径」。**
   369 次/步里 171 次（114 + 57）其实是 batch=1 的 strided-batched（`batchCount=1`），
   它们完全等价于 2-D GEMM，却因为输入是 3-D 而掉了 `_matmul_cuda_nd` 分支。
   把这一条**一个 choke point 改 8 行**接回已有 2-D fp16 路径，**实测 −23.0 ms/步**
   （0.3960 → 0.3730 s，同一协议 20 步；峰值显存 +0.00 GiB）。
2. **真正的「b=16 批量注意力」用新的 `cublasGemmStridedBatchedEx` 只值 ~6.3 ms/步**
   —— 因为注意力那 6 个 GEMM 每个都要搬 S×S 矩阵（268 MB fp32），是带宽受限的；
   fp16 省一半读，但**额外一次 cast 的代价和 GEMM 本身同量级**，所以只能挑 4 个
   「大张量不在被 cast 的那一侧」的算子转，剩下的强行转会**更慢**（实测）。
3. **dW（权重梯度）8.0 ms 是这 23 ms 里风险最高的一块**：源码自己记着
   `K` 长时 fp16 会让参数梯度相对误差 3e-4 → 2e-2（`cuda.py:7035`）。
   本报告的合成数据测不出这个（无对消），**必须 600 步对拍**才能开。

⇒ **go / no-go：**
**Go：Phase 1（batch=1 路由，−23.0 ms 实测）**，但要**先只上「投影 fwd+da」(−15.0 ms 实测)**，
dW 那 8 ms 单独挂开关、走 600 步 A/B。
**No-go：把「3-D 批量 fp16」当成一个独立项目做**——增量只有 6.3 ms（估），
要新 ctypes 绑定 + 改 4 个调用点 + 扩 scratch 契约，**不到 30 ms 的门槛**。
省下的精力应该投到 GPU 空转（前向 56 ms 的阻塞 D2H / 池抖动），那里是 130 ms。

### 2.2 三个必须说清的现象

1. **`fp16` 单独跑是 2.6~5.4×，但 `+cast` 后收益被吃掉一半以上**。
   cast 的代价 ≈ (读 4 B + 写 2 B)/元素；当被 cast 的张量就是 S×S（268 MB）时，
   cast 要 0.57 ms，而 GEMM 本身才 0.27 ms ⇒ 强行转 **比 fp32 更慢**（p@v/dq/dk/dv）。
   这就是为什么「所有 3-D GEMM 一律 fp16」是错的。
2. **注意 `fp16` 的 TFLOPS 天花板 = 62.5**（V100 fp16 Tensor Core 125 TFLOPS 是
   fp16 累加；`CUBLAS_COMPUTE_32F` 是 fp32 累加 ⇒ 一半）。投影实测 **64.0 TFLOPS**
   已经**顶到理论峰值**（12.2 → 64.0 = 5.2×），没有优化空间了。
3. **CSA dk/dv 的 fp32 只有 5.5 TFLOPS**（M=64/512 的 TN 形状 cuBLAS 选不到好 kernel），
   所以这两个即便带 cast 也还有 1.7× —— 这是「cuBLAS 在该形状下低效」而不是「fp32 峰值低」。

### 2.3 与活体内 72.6 ms 的对账（偏差方向与量级）

| | 微基准逐形状求和 | 活体内（CUDA event 归因） | 比值 |
| --- | --- | --- | --- |
| fp32 合计 | 67.0 ms/步 | 72.6 ms/步 | **0.92** |

微基准**偏乐观 8%**（不是偏悲观）：单形状连发时输入在 L2 里更热、没有与其它 kernel
抢带宽、也没有池分配穿插。所以**用「微基准收益 × 0.92」预测活体收益**；
§4 的 A/B 实测正好验证了这个系数（微基准 24.6 → 实测 23.0 = 0.93）。

反向的偏差（会**高估**收益）只有一处：微基准的 cast 是「紧接着 GEMM」的，
活体里同样紧接着，所以这条没有额外折扣。

## 3. fp16 溢出 / 精度判据

### 3.1 实测取值范围（`probe_bmm_sites.py` 在第 3 步的 backward 里读回主机）

| 张量 | 位置 | absmax | std | fp16 上限余量 | 判 |
| --- | --- | --- | --- | --- | --- |
| x（投影输入，RMSNorm 后） | A 族 | 5.10 | 1.00 | **12,800×** | 安全 |
| 权重（wq/wo/wkv/…） | A/B 族 | 0.098 | 0.020 | 668,000× | 安全 |
| q / k（SDPA，QK-norm + RoPE 后） | C 族 | 3.16 / 3.53 | 0.641 / 0.639 | ~18,500× | 安全 |
| q / k（CSA） | D 族 | 4.45 / 4.58 | 1.00 | ~14,300× | 安全 |
| v | C/D 族 | 1.47 | 0.32 | 44,500× | 安全 |
| p = softmax(scores) | p@v / dv | 0.00195 ≡ 1/512（step 2 时**恒为均匀分布**；训练后期可到 1.0） | 0 | ≥65,504× | 安全（下溢见下） |
| RoPE 的 perm | F 族 | 1.0 | 0.125 | — | 安全 |
| **dS = dL/dscores** | dq / dk | **2.65e-5** | **4.5e-8** | — | **危险：下溢** |

**溢出判据**（可直接写进测试）：设每次 GEMM 的输入 absmax 为 `a`，
要求 `a · 2^k < 65504`（k 为可能的预缩放）。当前所有**正向输入**的 `a ≤ 5.1`，
余量 ≥ 12,800× ⇒ **不存在溢出风险**；连 `scores` 本身（fp32，8.59 GFLOP 累加）
也不会接近 fp16 上限，而且累加器是 fp32。

### 3.2 真正的危险是**下溢**，不是溢出（这是本轮最硬的发现）

`dS` 在 step 2 的实测：absmax 2.65e-5、std 4.5e-8。fp16 的最小正规数 6.1e-5、
最小次正规数 5.96e-8，于是：

| 指标 | 实测 |
| --- | --- |
| dS 中 < fp16 最小正规数（6.1e-5）的比例 | **100%** |
| dS 中 < fp16 最小次正规数（6e-8）→ **被冲成 0** 的比例 | **81.5%** |
| 直接 cast 后做 dq/dk 的 Frobenius 相对误差 | **0.38（38%）** |

⇒ **dq/dk（以及 CSA 的 dq）绝不能在当前状态下 cast 成 fp16**。
若一定要转，必须**先按 2^k 放大再 cast、GEMM 的 `alpha` 取 2^-k**（等价于只对这一个算子
做 loss scaling）。这个技巧本身是对的（fp32 累加 + alpha 精确乘除 2 的幂），
但 k 需要动态（训练中期 dS 会变大 3~4 个数量级），**引入了一个新的失稳点**，
本报告不建议在第一版做。

### 3.3 精度判据（可复现的验收条件）

* 单算子：`relFro ≤ 3.5e-4`、`maxAbs ≤ 1e-2 × absmax(ref)`
  （fp16 尾数 2^-11 ⇒ 随机舍入的期望 relFro ≈ 2.8e-4，实测全部 2.9e-4，**已顶到理论值**）。
* 端到端：同 seed 20 步，`loss` 逐步差 ≤ 1e-2（实测最大 6.3e-3）、
  `gnorm` 差 ≤ 0.1（实测 5.044 → 5.048）、无 NaN/Inf。
* 600 步：`loss` 曲线不分离（这是 dW 的**唯一**放行条件）。

## 4. 方案设计

### 4.1 Phase 1（推荐，已端到端实测）：`batch == 1` 回落到 2-D 路径

**根因**：`cuda.py:5645 matmul_general` 只要前导维非空就一律走 `_bmm_op`
（`cublasSgemmStridedBatched`），**哪怕 `batch == 1`**。于是 3-D 输入 `x[1,T,d] @ W[d,N]`
（`_matmul_cuda_nd` 的唯一去向）永远拿不到 `_sgemm` 里那条 fp16 分支。
反向的 `da` 走 `__init__.py:1267` 的 `matmul_general` 回退、`dW` 走
`__init__.py:1254` → `sgemm_tn_strided_batched` → `_bmm_op`，**同一条路**。

**改法（一个 choke point，1 个文件 ~10 行）**：

```python
# cuda.py::_bmm_op 开头（在 alpha/beta 之前）
if int(batch) == 1 and self._fp16_state()["on"]:
    # batchCount=1 与 2-D GEMM 数学完全等价；交给 _sgemm 复用已有的
    # fp16 分支（_sgemm_f16 + 权重影子 + slot 复用 cast），
    # 参数逐个对应：op_a/op_b/N/M/K、Bptr/ldb、Aptr/lda、C/N。
    # 下面的 _mark_submitted 必须补上（池的在飞跟踪，_sgemm 内部不做）。
    self._mark_submitted(Aptr)
    self._mark_submitted(Bptr)
    self._mark_submitted(C.ptr)
    self._sgemm(op_a, op_b, int(N), int(M), int(K),
                Bptr, int(ldb), Aptr, int(lda), int(C.ptr), int(N))
    return C
```

* 为什么 gate 在 `_fp16_state()["on"]`：保证 `--amp off` 的用户**逐位不变**
  （fp16 关时仍走原来的 strided-batched，哪怕 batch=1）。
* 为什么覆盖了 A 族和 B 族：`matmul_general`、`sgemm_nt_strided_batched`、
  `sgemm_tn_strided_batched` **全都经过 `_bmm_op`**（前者直接调，后两者经 `_bmm_op`），
  所以这一个分支同时把「投影 fwd」「投影 da」「dW」全部接回 fp16。
* 与 `--amp {off,gemm,mlp,both}` 的关系：**不加新档位**。它只是让 `gemm` 兑现
  「GEMM 输入 fp16」这个既有承诺；建议加一个 policy/env 逃生门
  （`TG_AMP_BMM=0` 关掉），而不是新增 `--amp bmm`。
* 端到端实测（`lab/rent/ab_route_2d.py`，同协议 20 步，median of step 1..19）：

| 配置 | 步时中位 | Δ | 峰值 live | loss@19 | gnorm@19 |
| --- | --- | --- | --- | --- | --- |
| baseline（原样） | **0.3960 s**（0.3950–0.4020） | — | 23.70 GiB | 11.667514 | 5.044 |
| 只路由「投影 fwd+da」 | **0.3810 s**（0.3790–0.3900） | **−15.0 ms** | 23.70 GiB | 11.668677 | 5.046 |
| 路由「投影 + dW」 | **0.3730 s**（0.3700–0.3800） | **−23.0 ms** | 23.71 GiB | 11.667032 | 5.048 |

  loss 逐步差最大 6.3e-3（相对 5.4e-4），无漂移、无 NaN。**显存 +0.00 GiB**
  （权重影子 12 层 ×2×2 MB ≈ 48 MB，淹没在噪声里）。

### 4.2 Phase 2（可选，只有微基准）：b=16 注意力走 `cublasGemmStridedBatchedEx`

**新增 ctypes 绑定**（`cuda.py`，与 `_bind_gemm_ex` 同一套风格）：

```
cublasGemmStridedBatchedEx(handle, opA, opB, m, n, k, alpha,
    A, CUDA_R_16F, lda, strideA, B, CUDA_R_16F, ldb, strideB,
    beta, C, CUDA_R_32F, ldc, strideC, batch, CUBLAS_COMPUTE_32F, DEFAULT)
```

**只转 4 类**（cast 便宜的那一侧没有 S×S 张量）：
`SDPA 打分`、`SDPA dP`、`CSA 打分`、`CSA dP`、`CSA dk`、`CSA dv`；
**不转** `p@v`、`dv`、`dq`、`dk`（SDPA）与 `CSA p@v`、`CSA dq`（cast 吃光收益，实测更慢）。

**scratch 契约（读源码后的硬约束）**：
* `__init__.py:3197 _fp16_scratch(buf)` **只按元素数 `n` 做键**、模块级 `dict`、
  超过 64 项整体 `clear()`、缓冲 grow-only 且**跨 step 存活**。
  它的语义是「同一时刻只有一个消费者」——因为紧接着的 GEMM 会立刻用掉。
  ⇒ **注意力这里不能用它**：q 和 k 的元素数相同（都是 16×2048×64），
  会命中**同一块** scratch，第二次 cast 把第一次的内容冲掉（静默算错）。
* 正确原语是 `cuda.py:6459 _f16_scratch(slot, n)`：**按槽位 + grow-only**。
  Phase 2 需要 2~3 个槽位（q/k 各一，p/dS 各一），
  显存 = 2×8.4 MB（q,k）+ 2×67 MB（p,dS, fp16）= **~151 MB**（23.7 GiB 的 0.6%）。
* Phase 1 **不需要任何新 scratch**：走的是 `_sgemm_f16` 的 slot 0/1 + `_f16_cache`
  权重影子（`f16_cache_pin` 已登记 321 个参数、每 step 由 `f16_cache_clear` 失效）。

**预计收益**：微基准选择性求和 6.83 ms × 0.92 ≈ **6.3 ms/步**（未端到端验证）。

### 4.3 数值契约（方案必须写进 docstring）

| 项 | 约定 |
| --- | --- |
| 输入 | fp16（由 fp32 现 cast，**只 round-to-nearest 一次**） |
| 累加 | **fp32**（`CUBLAS_COMPUTE_32F`；不是 `COMPUTE_16F`） |
| 输出 | **fp32**（与现状一致，下游一个字节都不用改） |
| 反向 | **保持 fp32**（第一版）；Phase 2 只动指定的 6 个算子 |
| 不能降的算子 | ① **softmax 之前的 scale/mask**（fp32）；② **softmax 本身**（fp32 归约）；③ **dS 的 cast**（下溢，除非带 2^k 缩放）；④ **dW**（对消，待 A/B）；⑤ **loss / gnorm / clip / 优化器**（全 fp32，不变） |
| 确定性 | 同一 GPU/驱动/cuBLAS/单流下 **fp16 与 fp32 都逐位可复现**（§2.4 实测 6/6 形状）；**结果与 fp32 路径不同**（单算子 relFro 2.9e-4），跨 GPU/库版本不保证 |

### 6.1 收益（全部折算到 seq2048 的步时）

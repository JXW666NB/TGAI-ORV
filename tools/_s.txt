docs: give beginners the install step, promote migration to its own part, and write an agent-facing skill

Three gaps, all reported from reading the README as a newcomer would.

The beginner section started at `import tgai_go.train as T` with no pip install anywhere near it -- the
install instructions were buried at line 450 in the appendix. Part three now opens with step zero: pip
install tgai-orv, the actual requirements (driver support for CUDA 12 but no toolkit, and CPU works too),
and a two-line check using T.__version__ and T.amp_state. The appendix copy is replaced by a pointer so
there is one install section, not two. The badges were also stale at 0.9.28 and 558 tests against a real
0.9.49 and 656.

Migration was an appendix table of API differences. That answers "what differs" but not "what do I do
first". It is now part four with a four-step method: change only the import, move weights and compare the
forward pass before touching anything else, rewrite only the custom forward (the one thing that cannot be
transferred automatically, because guessing its semantics would compute silently wrong answers), then hook
up T.fit. Each step has a numeric acceptance criterion, plus a checklist that ends with the two habits that
prevent most migration bugs: never carry torch optimizer state across, and never extrapolate timings from
PyTorch numbers.

The skill, skills/orv-engine-dev/SKILL.md, targets coding agents rather than humans. It leads with the
rules that break work if ignored -- do not write ORV code from PyTorch memory, do not call something
verified without a reproducible number, do not mark unverified as supported, read docs/INDEX.md before
writing anything called a baseline. It carries the three traps that cost real time in this session, the
min/max shadowing being the sharpest: inside ORV, min and max are tensor APIs, so scalar comparison needs
_builtin_min and _builtin_max.

Two sections were requested and both were built from code rather than memory. Inference: save_tg maps
training names to the engine's w1/w2/w3, and two failure modes are documented that only show up late --
the engine reads the RoPE cos/sin buffer by pointer, so a missing buffer loads fine and dies at generate,
and the .TG header has no head_dim field, so any model where head_dim is not d_model over n_heads exports
wrongly without raising. Formats and checkpoints: load_tg, load_gguf, load_safetensors_dir, from_torch,
npz, and ORV's own save_checkpoint all exist, so a .TG, a GGUF or a .pt can each start training. The limits
are stated too -- GGUF accepts only F32/F16/BF16 and raises on quantized types, and it needs the gguf
package.

The skill lives in the repo so it versions with the code, and is also installed to ~/.dsh/skills so this
environment can load it. Its last section says how to maintain it: every number must be re-derivable, and
status is always one of verified, implemented-but-unverified, or not implemented.

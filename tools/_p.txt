feat(plugin): unify six extension axes under one namespace, and let the optimizer axis unblock the deferred GEMM work

The user's observation reframed a decision I had been stuck on: if optimizers are plugins, then changing
an optimizer to update in place stops being core surgery. That matters because the packed-expert GEMM
path needs in-place updates -- out-of-place `p.data = p.data - ...` replaces the array and breaks the
view into a shared buffer. Rather than modify every optimizer in core, the core can expose shared-storage
parameters and let a plugin supply an in-place optimizer.

Built one `plugin` namespace covering six axes: op, layer, arch, optimizer, backend, api. Registration is
immediate for the first four (pure bookkeeping, no side effects) and deferred for backend and api, which
mutate sys.modules or switch compute paths -- installing a plugin should not silently change process
behaviour, so those need an explicit activate().

Three principles the README now leads with, since this is a headline feature: simple (one namespace, one
file, decorators supported), general (plugins compose core ops, so the same file runs on CUDA, Vulkan and
ROCm without per-backend copies), and safe (capabilities must be declared honestly and are enforced).
The safety one is concrete: an optimizer registered without works_inplace=True is refused for
shared-storage parameters at registration time, because the failure mode -- weights updated while the
view stays stale -- is close to impossible to diagnose later.

The op axis forwards to the existing ops_plugin rather than growing a second system; it already has
entry_points discovery, contract checking with api_version matching, and a sha256 manifest.

17 tests, including an end-to-end case where a single .py file registers all six axes and the tests then
confirm the op computes and the arch builds. Writing that test caught a real usability gap: the decorator
form `@plugin.op("name")` did not work, so op, layer and arch now accept both forms.

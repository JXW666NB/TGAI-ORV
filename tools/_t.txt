feat(plugins): ship the torch-compat example inside the package, and close out the plugin-system phase

0.9.44 put the demo in examples/, which meant neither the sdist nor the wheel carried it. An example
nobody installing from PyPI can run defeats its own purpose, so the plugin now lives at
tgai_go/train/plugins/torch_compat.py and ships with the package. examples/plugins keeps the pure-op
samples.

The demo does what the README claims and no more: load it, activate it, and PyTorch-style code
(import torch, nn.Linear, AdamW, forward, backward, step) runs unchanged on ORV. The test asserts that
loop actually updates weights, not merely that it does not throw.

Its safety guard turned out to be load-bearing in the suite itself. The plugin refuses to install when a
real torch already occupies sys.modules, because silently swapping it would leave users believing they
ran PyTorch. Other tests in the suite import real PyTorch, so two of these cases skip with that exact
reason rather than failing -- the guard firing is the correct behaviour, not a test defect.

Also relaxed the naming rule: plugin.api and plugin.backend are registration keys, not attribute names,
so "torch-compat" is now accepted while layers, optimizers and archs still require identifiers.

One project rule caught me mid-way: writing the new __init__.py with PowerShell's Set-Content -Encoding
UTF8 produced a BOM and CRLF, and the hygiene tests failed immediately with the right explanation. Fixed
by writing it without BOM and with LF.

This completes the three items in the current objective: capability dispatch with measured overhead and a
static-binding escape hatch, shared-storage parameters with the in-place contract enforced at
construction, and an API-compatibility axis proven by a runnable demo.

docs: index TG Link so it stops being re-derived from scratch

I did not remember TG Link when asked, and worse, I had already answered a long question about backend
mixing the turn before without reading docs/MULTIVENDOR_ROADMAP.md -- which defines it. The document has
existed since 2026-11-01 and neither the docs index nor the agent skill pointed at it, so there was nothing
to catch the omission. This commit fixes the discoverability, not the design.

TG Link is a vendor-neutral host-staged collective communication layer, and the roadmap already pins down
what I re-derived worse: cross-vendor GPUs cannot be directly connected, but data parallelism does not need
that, because 0.5B fp32 gradients move about 1 GB per step and PCIe 3.0 x16 sustains 10-12 GB/s, so an
all-reduce costs roughly 0.1 s against a 0.8 s step -- about 12% overhead. Tensor parallelism is the
infeasible one; pipeline parallelism only moves activations and stages through host fine.

One correction to my own previous answer matters for sequencing. I said a device descriptor and in-process
multi-device support were prerequisites. They are not: TG Link is process-level by design, one process per
rank with its own backend, which is exactly the model dist.py already uses. So nothing needs the singleton
_CudaAPI to become multi-instance before TG Link can start. That makes the prerequisite far smaller than I
described, and it also means the two-CUDA-card rental would validate the host-staged all-reduce itself even
without a second vendor.

The status is unchanged: not executing. TG Link v0 is V3, behind V2 (a Vulkan training backend), and
training-side Vulkan kernels currently number zero.

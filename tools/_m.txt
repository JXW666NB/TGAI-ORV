perf(muon): 6x on the 3B step by replacing a single-threaded reduction, and merge the plugin docs into one set

Muon's 3B step goes from 35.0 s to 5.78 s, measured on the real step rather than extrapolated.

I had said Muon was FLOP-bound and at a physical floor. That was wrong, and the profiler shows why: a
single matrix needs 111.4 ms of Newton-Schulz while its five steps of pure GEMM need only 9.3 ms.
read_scalar(sumsq_sequential) alone was 101.3 ms -- 91% of the cost was one single-threaded fp32
accumulation per matrix, not arithmetic. sumsq_sequential exists to match OpenBLAS bit-for-bit, but
fast=True had already given that up, so the fast path now uses the existing two-pass parallel
sumsq_parallel. That takes 101.258 ms to 0.062 ms, a per-matrix 111.4 to 10.1 ms, and the extrapolated
224 matrices to 2.3 s against a 2.1 s pure-GEMM floor.

The measurement also reversed a second assumption. The parallel reduction is more accurate than the
sequential one: over 4.2M terms the expected sum of squares is 1677.0546, parallel returns exactly that,
and sequential returns 1670.0114 -- 4.2e-03 off, because a single fp32 accumulator loses three digits at
that length while blocked partial sums do not. So this change is faster and more numerically sound at
the same time. Four CUDA tests now pin it, including that fast and slow paths agree to 1e-5 end to end.

Status without inflation: 5.78 s is still 8x slower than AdamW fp16 at 709 ms, so AdamW remains the
right default at 3B. What changes is that "unusable" no longer applies -- the gap went from 50x to 8x and
the work now sits at the GEMM floor. Muon suits models under 1B.

Also folded the plugin documentation into one set of statements. PLUGINS.md was the operator-plugin
primer from 0.7.x and the four newer PLUGIN_* documents partly repeated it, which is how two versions of
the same rule appear. PLUGINS.md keeps the tutorial role and now points at PLUGIN_CHARTER.md for
anything normative.

The charter gained a third article that the plugin language depends on: generated first, Python as the
fallback. Four tiers -- declarative kernel that ORV lowers to each backend and compiles, backend source,
prebuilt library, compositional Python -- with hard rules that an op expressible declaratively must not
ship only a Python path, that a backend without a generator reports the op as absent instead of silently
falling back, and that any fallback has to be countable. It also carries an explicit list of what is not
built yet, including dump_code and stats, so those cannot be mistaken for present.

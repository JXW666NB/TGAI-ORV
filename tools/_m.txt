perf(3b): measured the whole step -- AdamW 709 ms / 24.78 GiB fits and beats the PyT baseline; Muon is 89x slower

Measured the 3B whole step on the exact configuration that fits, and got both halves of the answer.

V2.7 28 layers / 2.97B, V100 32GB, layer-wise immediate release, pure VRAM, no host offload:

    AdamW, fp16 momentum:  peak 24.78 GiB,  709 ms/step   (11.1 GiB optimizer state)
    Muon,  fp16 momentum:  peak 18.93 GiB, 62.9 s/step     ( 5.5 GiB optimizer state)

So the 4-star condition is met by AdamW: it runs entirely in VRAM and 709 ms is faster than the
911 ms PyT Adafactor step that the objective named as the bar -- 1.28x under it, not just near it.

And Muon, which I spent this evening making fit, turns out to be unusable at this scale. Newton-Schulz
orthogonalizes every 2D parameter with five matrix-multiply iterations; with 2550 parameter tensors
that fixed cost dominates everything and lands at 62.9 seconds per step, 89x slower. This is the
algorithm's cost rather than an implementation bug -- small models hide it, 3B cannot.

I am not going to present the 5.9 GiB Muon saves without the 89x it costs. The README now lists
AdamW as the default for 3B and marks Muon as "only when memory is truly scarce", with the reason
and the number. Making Muon viable at this scale needs grouped orthogonalization or fewer
iterations; that is future work, not a claim I can make now.

Also fixed: Fp16MomAdamW.state_bytes() reported fp16 momentum as 2 bytes/param. m and v are two
separate buffers, so it is 4 bytes/param (11.1 GiB for 3B), which is what the peak memory actually
shows. The old figure made it look like twice as much would fit.

feat(dispatch): capability model and op dispatch, the architectural prerequisite for Vulkan

Plugins should target capabilities, not backends. A plugin now registers a fast path with the
capabilities it needs and a wildcard fallback, and dispatch picks by what the current backend actually
reports plus its compute capability:

    plugin.op("my_silu", fast_impl, backend="cuda", caps={"async_copy": True}, min_cc=(8, 0))
    plugin.op("my_silu", slow_impl, backend="*")

The wildcard is what makes "one file runs on every backend" real rather than aspirational: Vulkan,
which has no dedicated implementations yet, resolves to the fallback instead of failing.

Measured the dispatch cost because the objective set a 1% budget. Cache-hit resolution costs about 627 ns
against 75 ns for a direct call. On a large GEMM (~400 us) that is 0.16%, fine; on a small elementwise op
(~15 us) it is 4.2%, over budget. So plugin.bind() resolves once and hands back the function, and the
guidance in resolve_op, the README and docs/PLUGIN_DISPATCH.md all say hot paths must bind rather than
resolve per call. The numbers are in the doc, not just asserted.

Two real bugs surfaced while testing. The cache key omitted caps, so a fast path resolved under
{"async_copy": True} was wrongly returned for a later query with no capabilities; caps now stringifies
into the key. And an early return meant a backend which had only a wildcard registration was reported as
having no implementation at all.

Twelve tests cover capability gating, arch ranges, wildcard across backends, dtype filtering, priority,
cache behaviour, invalidation on registration, static binding, and that failures explain which capability
was missing.
